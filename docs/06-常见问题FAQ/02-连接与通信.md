# 02 连接与通信

[返回文档首页](../README.md) · [03-接口详细文档](../03-接口详细文档/) · [07-补充内容](../07-补充内容/)

> 本篇收录 ROS master、Topic 与 Service 层面的连接与通信故障。逐层定位的原则是：
> 先确认服务端节点存活，再看数据是否存在，最后才考虑客户端 timeout。
> 环境识别与只读自检见 [01 安装与环境](01-安装与环境.md)。

---

## 1. 问题：ROS master 无法连接

**原因**
- `ROS_MASTER_URI` 指向的 master 未启动，或指向了错误的环境（宿主机 / 容器两套）。
- `ROS_IP` 与 `ROS_HOSTNAME` 同时设置且相互冲突。
- 宿主机与容器未处于同一网络，容器没有使用 host 网络。

**现象**：`Unable to communicate with master`、连接拒绝或持续超时。

**判断命令**

```bash
echo "$ROS_MASTER_URI"
echo "$ROS_IP"
echo "$ROS_HOSTNAME"
rosnode list
```

**解决方案**

本机 master 的常见配置：

```bash
export ROS_MASTER_URI=http://localhost:11311
roscore
```

宿主机与容器联合运行时，Docker 应使用 host 网络，双方必须访问同一个 ROS master。不要同时设置互相冲突的 `ROS_IP` 与 `ROS_HOSTNAME`。

**成功标准**：`rosnode list` 能返回节点列表。

**日志位置**：`~/.ros/log/latest/`；先看 roscore 和第一个退出节点。

## 2. 问题：Topic 没数据或频率过低

**原因**：服务端节点未启动、命名空间写错、上游节点退出、设备或仿真时钟异常，或新旧 `devel` 消息类型不一致。

**判断命令**

```bash
rostopic list
rostopic info /目标topic
rostopic type /目标topic
rostopic echo -n 1 /目标topic
rostopic hz /目标topic
rosnode info /发布节点
```

**逐项对照**

- Topic 不存在：服务端节点未启动或命名空间错误；
- Topic 存在但没有 publisher：上游节点已退出；
- 有 publisher 但没数据：检查设备、仿真时钟和节点日志；
- 类型不一致：重新加载同一工作空间的消息包，不要混用旧 `devel`。

**成功标准**：`rostopic hz` 稳定输出预期频率，`rostopic echo -n 1` 能取到一帧有效数据。

**日志位置**：`~/.ros/log/latest/`，先看发布节点的第一条 `ERROR/FATAL`。

> 若现象是「控制频率过高导致积压」而非话题无数据，见 [06 性能与稳定性](06-性能与稳定性.md)。

## 3. 问题：Service 超时或不存在

**原因**：服务端节点不存在或未启动；`kuavo-ros-opensource` 与 SDK 版本不匹配导致服务名不一致。

**判断命令**

```bash
rosservice list | grep '<服务关键字>'
rosservice info /目标service
rosservice type /目标service
rosnode info /服务节点
```

**解决方案**

如果 `/humanoid_controller/get_controller_list` 不存在，先确认控制器节点是否存活，再核对 `kuavo-ros-opensource` 与 SDK 版本。反复调用客户端或增加 timeout 不能修复未启动的服务端。

**成功标准**：`rosservice list` 中能看到目标服务，`rosservice info` 能返回节点与类型。

### 案例：`LegJointSdkMove` 报“设置 MPC 模式失败”

**日志顺序**：先报 `com_height parameter not found`、`/humanoid_get_current_gait_name` 超时；到 `LegJointSdkMove` 时，`/humanoid_controller/get_controller_list` 超时，SDK 提示 `change_manipulation_mpc_ctrl_mode failed: can only be executed in MPC mode`，随后 `LowLevelSDKManager` 报“设置 MPC 模式失败”，节点返回 `FAILURE`，父级 `Sequence` 依次失败。对应运行日志中，底盘导航与头部控制此前已成功。

**直接失败点**：下肢节点在发布腿部轨迹前，先调用 SDK 的 `set_manipulation_mpc_mode(ArmOnly)`；调用失败就不会继续下发腿部轨迹。控制器列表服务超时与 MPC 拒绝是此处最直接的线索。`com_height` 参数和步态服务缺失也需要排查，但仅凭这组日志不能断言它们就是 MPC 切换失败的根因。

**先排除 SDK 导入环境问题**：若同一终端另行执行 `from kuavo_humanoid_sdk import KuavoRobot` 报 `ResourceNotFound: kuavo_common` 或 `ModuleNotFoundError: No module named 'robot_version'`，先加载工作空间并补齐 Python 路径（以下以 Ubuntu 的 `~/LeTools` 为例）：

```bash
cd ~/LeTools
source /opt/ros/noetic/setup.bash
source infrastructure/ros_packages/devel/setup.bash
export PYTHONPATH="$PWD/infrastructure/ros_packages/src/kuavo_common/python:$PWD:$PYTHONPATH"
rospack find kuavo_common
python3 -c 'import robot_version; print(robot_version.__file__)'
python3 -c 'from kuavo_humanoid_sdk import KuavoRobot; print("SDK Ready")'
```

若 `devel/setup.bash` 不存在，先按 [环境安装](../02-环境安装/03-安装步骤.md) 编译 LeTools 的 ROS 工作空间。导入修复后必须重新运行场景；只有“SDK Ready”不能证明 MPC 控制器服务已可用。本次日志已进入 `set_manipulation_mpc_mode(ArmOnly)`，因此不能仅凭另一条导入报错认定它就是这次 MPC 切换失败的直接原因。

**再查控制器服务**（在运行 LeTools 的终端执行；若仿真在容器中，也执行 ROS 查询并对照两边结果）：

```bash
echo "$ROS_MASTER_URI"
rosnode list | grep -E 'humanoid_controller|mobile_manipulator'
rosservice list | grep -E 'humanoid_get_current_gait_name|get_controller_list|mobile_manipulator_mpc_control'
rosservice info /humanoid_controller/get_controller_list
rosservice info /humanoid_get_current_gait_name
rosparam list | grep com_height
python3 -c 'import kuavo_humanoid_sdk; print(kuavo_humanoid_sdk.__file__)'
```

在下位机容器中另查其源码版本（以下以 `/root/kuavo_ws` 为例）：

```bash
git -C /root/kuavo_ws describe --tags --always --dirty
```

**按检查结果处理**：

- 容器能看到控制器服务、LeTools 终端看不到：让两端连接同一个 ROS master，重新加载各自的 ROS 工作空间后复查 `ROS_MASTER_URI` 和 `rosservice list`。
- 两端都看不到：检查实际启动的控制器节点及其日志。即使下位机源码（例如 1.4.5）含有 `get_controller_list` 的注册代码，也不代表当前仿真已启动该服务。
- 轮臂仿真本来就不提供该服务：核对 **LeTools 实际导入的 SDK 路径**及其轮臂兼容逻辑，再按 [03 SDK 与版本](03-SDK-与版本.md) 对齐 SDK；仅看到 `/mobile_manipulator_mpc_control` 不能代替 `/humanoid_controller/get_controller_list`。
- 服务存在但仍超时：检查提供服务的节点日志和 ROS 通信，而不是只增加客户端 timeout。

这里没有从现有日志确认一条通用的“更新 SDK 即修复”命令。修复后重新运行场景，确认 `LegJointSdkMove` 不再报 MPC 模式失败、腿部动作实际执行。

## 4. 问题：消息包 md5 不一致导致订阅失败

**原因**：`kuavo_msgs`、`ocs2_msgs` 在多个仓库中各有副本，副本内容不同步时 md5sum 不一致，订阅方收不到数据、也不会报出明显错误。

**判断方式**

```bash
rosmsg md5 kuavo_msgs/<消息名>
rosmsg md5 ocs2_msgs/<消息名>
```

两侧分别执行并比对；同时确认 `rosmsg show` 的字段定义一致。

**解决方案**：将「消息包源头仓库」的 `kuavo_msgs`、`ocs2_msgs` 复制到对侧仓库的 `src/` 下重新编译，不要手工改一侧的字段定义去凑 md5。

**成功标准**：两侧 `rosmsg md5` 输出一致，话题订阅后 `rostopic hz` 有数据。
