# 01 扩展总则与分层规范

开始任何扩展前，先确定这次改动属于哪一层。本篇给出落层判定方法和已知例外的规避方式。

## 一、分层规则

分层模型、各层允许的 import、典型运行调用流程以及已知例外清单，统一维护在
[`../01-介绍/04-系统架构与分层.md`](../01-介绍/04-系统架构与分层.md)，本篇不再重复。新增代码需遵守其中的依赖规则，要点：

- 上层可以 import 下层，下层不应 import 上层；
- `skills` 通过构造时注入的 `IHardware` 使用硬件能力，不直接 import `adapters` 中的具体实现；
- `kuavo_humanoid_sdk` 只在 `adapters` 内部使用；
- 已有实现中的例外（E1–E3）单独记录，不作为新增代码的设计依据。

## 二、落层判定

「我想做的事 → 该改哪个目录」的判定流程如下：

| 我想做的事 | 该落的层 | 落点 |
|---|---|---|
| 新增一个所有层通用的数据结构或返回值约定 | `core` | `core/domain/` 新增 dataclass |
| 新增一个能力抽象（相机、感知、硬件） | `core` | `core/interfaces/` 新增 `I*.py` |
| 新增一组枚举 / 领域异常 | `core` | `core/domain/enums.py`、`core/common/exceptions.py` |
| 接入一个新硬件或新厂商后端 | `adapters` | `adapters/hardware/<vendor>/`，并在 `factory.py` 登记 |
| 给现有硬件加一种能力 | `adapters` | `adapters/hardware/.../mixins/` 新增 Mixin，在组装点挂上 |
| 新增一个具体动作（如「头部转 30°」） | `skills` | `skills/atomic/<domain>/` 新增 Skill 类 |
| 新增一个行为树节点（把技能接入树） | `orchestration` | `orchestration/nodes/` 新增 `BaseAction` 子类 + `@define_manifest` |
| 新增一条任务流程 | `orchestration` | `orchestration/scenarios/<scene>/` 新增场景 JSON |
| 新增一个可独立执行的验证脚本 | `apps` | `apps/<测试目录>/` 复用同目录 `_scaffold.py` |

一条经验法则：**改的是「大家共同遵守的约定」→ `core`；改的是「跟某块硬件怎么说话」→ `adapters`；改的是「做一件什么事」→ `skills`；改的是「这些事按什么顺序做」→ `orchestration`；只是「跑起来看看」→ `apps`。**

## 三、已知例外的规避方式

例外的位置、成因和复现命令见 [`01-04` 第四节](../01-介绍/04-系统架构与分层.md#四已知分层例外e1--e2--e3)。新增代码按下表规避：

| 例外 | 内容 | 新增代码的做法 |
|---|---|---|
| E1 | `skills` 直接 import `adapters` 中的具体类或模块级函数；现存 **9 个文件**（按开源发布范围统计，不含 `tests/`） | 新技能只依赖 `core.interfaces.i_hardware.IHardware`，具体适配器由 `HardwareFactory` 创建后注入；`IHardware` 缺少所需能力时，先补接口与适配器实现，而不是 import 具体类 |
| E2 | `skills` import `orchestration` | `@define_manifest` 是当前唯一被接受的技能→编排依赖，保持不动；新增技能不得依赖 `orchestration.scenarios.*` 的场景局部工具或 `orchestration.engine.*`——通用逻辑下沉到 `core/common/`，属于某场景的保留在该场景目录内 |
| E3 | `adapters` / `orchestration` import `apps` | `apps` 只承载验证脚本，`adapters` / `orchestration` 的正常执行链不得依赖它；现有的惰性 import 不得扩散 |

评审时若发现新写的 `skills` / `adapters` 代码 import 了具体适配器或更上层模块，按上表拦下，不以历史遗留作为先例。
