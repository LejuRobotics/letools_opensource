## 总览

## 0. 一次性准备

### 0.1 编译

```bash
cd <仓库根>/infrastructure/ros_packages
source /opt/ros/noetic/setup.bash
catkin_make -DCATKIN_BLACKLIST_PACKAGES="apriltag_ros;ar_control;dynamic_biped;kuavo_camera;realsense2_camera;kuavo_vision_object"
```

⚠️ **黑名单不能省，`--pkg` 也不能替代它**：`catkin_make --pkg <包名>` 只限制**编译**
哪些包，**configure 阶段仍要解析全部包的依赖**，照样栽在 `find_package(apriltag)` 上
（本机没装 AprilRobotics 的 apriltag 库，而现版本用不上它）。

⚠️ **它是 cache 变量**，会写进 `build/CMakeCache.txt`、**下次不传 flag 时静默沿用**。
这个工作空间是共享的，**编完清掉**：

```bash
cd <仓库根>/infrastructure/ros_packages
rm -f build/catkin_make.cache
sed -i 's/^CATKIN_BLACKLIST_PACKAGES:STRING=.*/CATKIN_BLACKLIST_PACKAGES:STRING=/' build/CMakeCache.txt
```

（**两个缓存要一起清**：只清 `CMakeCache.txt`、留着 `build/catkin_make.cache` 时，
catkin_make 判定"参数没变"、跳过带 `-D` 的那次 cmake，紧接着用**空黑名单**重新
configure，照样报 apriltag 错。）

编译完成后 source 一次：

```bash
source /opt/ros/noetic/setup.bash
source <仓库根>/infrastructure/ros_packages/devel/setup.bash
```

验证三个消息包都在：

```bash
python3 -c "from pallet_detection_msgs.msg import PalletDetection; print('pallet_detection_msgs OK')"
python3 -c "from box_detection_msgs.msg import BoxDetection; print('box_detection_msgs OK')"
python3 -c "from pallet_servo_msgs.msg import PalletServoError; print('pallet_servo_msgs OK')"
python3 -c "from pallet_servo_msgs.srv import SetServoSlot; print('SetServoSlot OK')"
```

四条都打印 OK 才算准备好。

### 0.1b 设 CPU 线程数（**不设会慢一倍**）

**你自己开终端直接跑东西之前**，先 export 这一对：

```bash
export OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
```

**为什么**：OpenCV / OpenBLAS / onnxruntime 默认按核数开线程，而这个负载
（480×640 的图、几个小矩阵）开多线程是**纯开销** —— 线程调度比计算还贵，还会和
ROS 的回调线程抢核。

**实测**（现场那台机器，托盘检测单帧）：不设 **~1800ms**，设了 **~1150ms**。

**哪些进程已经替你设好了、哪些没有** —— 分清楚就不用每次自己想：

| 进程 | 谁管的 | 你要不要 export |
|---|---|---|
| 三个检测器（`roslaunch` 起的）| **各自的 launch 里 `<env>` 设好了** | 不用 |
| **行为树**（`start_behavior_tree.sh`）| **脚本自己设**（2026-09-30 起）| 不用 |
| 你在终端里手敲的（离线脚本、`rosrun` 单跑、诊断工具）| 没人管 | **要** |

`roslaunch` 的 `<env>` 是**覆盖**继承来的环境（`setup_env()` 里先 `d = env.copy()`
再逐条 `d[name] = value`），所以你 export 不 export，三个检测器都是 1 线程。

**行为树进程是唯一需要盯的**：它是 `python3` 直接起的、前面没有 `roslaunch`，
而它里面的 OpenBLAS 活不少 —— `node_pallet_servo` 的**叠加图渲染**（`cv2` + `numpy`）
与 `pallet_frame` 的窗平均都在它里面跑。**现在 `start_behavior_tree.sh` 会自己
export**（在 `source` 之后、`python3` 之前），所以走 §3 或 §3c 都不用管；
自己写脚本调 `run_behavior_tree_json.py` 时要自己加。

> 那一对被 **脚本覆盖**、不是"有就不用设"：`start_behavior_tree.sh` 里是无条件
> `export …=1`。所以外面设成 8 也会被压回 1（实测过）。

### 0.2 参数：改 `board.json`，别改 `py_tree.json`

场景的全部可调参数在 **`<仓库根>/orchestration/scenarios/pallet_servo_real_v1/board.json`**
（24 个键，三组 `pallet` / `box` / `servo`）。**改完重启行为树生效。**

```bash
grep -n '"key"' <仓库根>/orchestration/scenarios/pallet_servo_real_v1/board.json
```

| 想改什么 | 改哪个键 |
|---|---|
| 木托盘台面尺寸 | `pallet_size_mm`（`[长, 短]` 毫米）|
| 伺服用哪两条边 | `ref_edges`（**绝对毫米**写法，见 §0.3）|
| 箱子尺寸 | `box_size_mm` |
| 选箱偏好 | `z_near_mm` / `z_far_mm` / `score_w_conf` / `score_w_area` / `score_w_depth` |
| **台面高度的 z 带** | `deck_z_mm`（`"lo,hi"` 毫米，base_link 的绝对高度；空 = 不约束）|
| **法向自检** | `fit_normal`（默认 true）/ `normal_refit`（默认 false，动腰才要改）|
| 配对与平滑 | `max_dt_s` / `pair_cache` / `window` |

⚠️ **`pallet_size_mm` 与 `ref_edges` 要一起改** —— `ref_edges` 写的是绝对毫米，
边界的边就落在尺寸上，只改一个会让边落到台面外（启动时就会报 `ref_edge_out_of_range`）。

### `deck_z_mm` —— 排除"高度上不可能"的东西

相机装在头上、光轴朝下，**你手里抱着的纸箱**会同时出现在画面里，而且它面积大、
离得近，很容易被当成台面。`deck_z_mm` 用**绝对高度**把它挡掉。

现场实测（相机在 base_link 高约 1.2m）：

| 东西 | base_link 的 z |
|---|---|
| 托盘台面 | **+43 mm** |
| 地面 | −107 mm |
| **手里抱着的纸箱** | **+600 mm** |

所以填 `"-40,130"` 就够了（实测四角误差 28px → 15px）：

```json
{ "key": "deck_z_mm", "value": "-40,130" }
```

⚠️ **它是绝对高度，依赖 TF 的平移** —— 换工位、换托盘、相机装高变了都要重标。
带错了**不会崩**，只是"带内选不出台面" → 拒帧（日志里 `deck_h_rel_mm=None`）。

启动时日志会写明它有没有生效：

```
[pallet_detection] 台面 z 带=[-40.0, 130.0] mm（相机在 base_link z=1195mm）
```

空串时会打 `台面 z 带=**未启用**`；配了但 TF 查不到相机位置会打 WARNING 并**退回无约束**。

### `fit_normal` / `normal_refit` —— 法向不再信 TF

⚠️ **这是 2026-09-29 现场踩出来的**：TF 链给出的台面法向**会静默偏掉**，而托盘
检测对法向极其敏感（法向就是投影平面本身，偏 ε 时台面在"高度"坐标里变成一条
斜坡，跨度 ≈ `tan(ε) × 台面尺寸`）。

现场实测（`test_jia4`，37 帧）：

| 量 | 值 |
|---|---|
| 地面平面 vs 托盘台面平面 | 差 **1.14°**（两者都水平）|
| **TF 链给出的法向 vs 地面** | 差 **12.52°** |
| 37 帧里 TF 法向的变化 | **0.000°**（静态偏差，不是抖动）|
| 用 TF 法向 detect | `too_few_edges` **37/37 全拒** |
| 用拟合法向 detect | **37/37 全过**（支撑边 3~4/4）|

所以现在的默认行为是：**TF 只当搜索初值，法向从当前帧深度拟合**。

```json
{ "key": "fit_normal",   "value": true  }
{ "key": "normal_refit", "value": false }
```

`normal_refit: false` = **只在首帧拟合一次，之后一直复用**。依据是伺服时机器人
**只做平面内平移**（前后左右，**不动腰**）—— 相机相对 base 的朝向不变、base 的 z
与地面法向的关系也不变，**法向是这个过程中唯一的常量**。实测 37 帧里只有首帧花
13ms，后 36 帧 0ms。

⚠️ **动了腰、或者换了工位，要把 `normal_refit` 设成 `true`**（或者重启节点）。
不设也不会崩 —— 只是拿一个过期法向继续算，而**法向偏了不会报错**，只会换一个
score 继续"如实拒绝"。所以启动日志里每次都会写明这一帧用的是哪个来源：

```
[pallet_detection] 法向来源=fit   normal=[+0.0431, -0.3493, -0.9360]（fit_normal=True normal_refit=False）  与 TF 初值差 12.89°（内点 832，13ms）
[pallet_detection] 法向走**缓存**（首帧拟合的结果）—— 伺服只做平面内平移时这是对的；**动了腰或换了工位**要把 ~normal_refit 设成 true
```

四个来源的含义（`diag` 里的 `normal_source=` 字段）：

| 标签 | 含义 |
|---|---|
| `fit` | 这一帧真的从深度重新拟合了 |
| `cache` | 复用首帧那次拟合的结果（**默认走这条**）|
| `tf` | 拟合失败（内点不够），**回退到 TF 初值** —— 初值本来就在夹角窗内，只是没被纠正 |
| `param` | 用了 `~normal` 参数，**完全没查 TF 也没拟合** |

### 0.3 坐标系与参考边

**调参考边之前先看 `skills/atomic/perception/pallet_servo/README.md` 里那张
台面坐标系图**：原点在**画面左下角**、`+x` 沿 `E1` 朝**画面右**、`+y` 沿 `E2` 朝
**画面上**。四条边：

```
       (0,H) ●───────────────● (W,H)        y=0 → 近边（画面里靠下）
             │      台面      │              y=H → 远边（画面里靠上）
             │  [0,W]×[0,H]  │              x=0 → 左边
       (0,0) ●───────────────● (W,0)        x=W → 右边
             └───────────────→ +x
          原点 = 画面左下角
```

⚠️ **轴向是相对相机定的，不是相对托盘物理定的** —— **换工位后必须在叠加图上
重新确认一次**（`/pallet_servo/overlay` 上黄线的标签就是你写的那两条原文）。


```bash

```

**默认一直跑**（`run_for` 的 `duration_sec` = 86400 秒 = 24 小时）。想提前收工
按 Ctrl+C，或者改 `py_tree.json` 里 `run_for` 的 `duration_sec`。

> ⚠️ **`rosservice call /pallet_servo/slot "slot: 0"` 不会让树结束** —— 它只把节点
> 置回"未激活"（话题上继续发 `valid=false` 的「伺服未启动」），树照跑。要真结束
> 用 Ctrl+C。

### 3b. 告诉节点现在处理第几个箱子

⚠️ **节点启动时是「未激活」的 —— 不 call 就一帧有效数都不出**（话题上全是
`valid=false` 的「伺服未启动」）。开工时 call 一次：

```bash
rosservice call /pallet_servo/slot "slot: 1"
```

`slot` 是**箱位号，从 1 数**，对应 `board.json` 里 `ref_edges` 的第几组。
`slot: 0` 表示本次伺服结束。**越界调用返回 `ok=false` 且不改当前状态。**

## 3c. 或者：一条命令起停全栈

上面 §1 三个终端 + §3 那一套，可以合成一条命令（**不含 roscore 与相机**）：

```bash
cd <仓库根>/orchestration/scenarios/pallet_servo_real_v1
export ROS_MASTER_URI=http://localhost:11311
export ROS_IP=<这台机器的 IP>
bash start_all.sh
```

脚本会：检查 `roscore` → **把上一轮残留的检测器杀掉重启** → **从 `board.json` 读值**、
起三个检测器并等三路话题出数 → 前台跑行为树。**Ctrl+C 把三个检测器一起收掉。**

> ⚠️ **[2/4] 那一步会真的 `rosnode kill` 掉同名节点。** 如果同期还有别人
> （另一个会话 / 另一台机器）在跑这三个检测器，会被这个脚本杀掉 —— 单机单人用没问题，
> 多人共用一台机器时留意。

> `start_all.sh` 起的检测器**参数来自板子**；§1 里单独 `roslaunch` 起的那种用的是
> 各 launch 自己的默认值。要改检测器参数，用这个脚本。

## 4. 看结果（终端 4）

### 4.1 三个数（实时话题）

```bash
source /opt/ros/noetic/setup.bash
export ROS_MASTER_URI=http://localhost:11311
export ROS_IP=<这台机器的 IP>

rostopic echo /pallet_servo/dis
```

一条消息长这样：

```yaml
header:
  seq: 412
  stamp:
    secs: 1758701234
    nsecs: 567000000
  frame_id: "camera_color_optical_frame"
valid: true            # ← 先看这个
reject: ""
e_bottom_px: -33.9
e_right_px: 67.4
theta_rad: -0.0052
```

**`valid` 必须先判。** `valid: false` 时三个量是 `NaN`、`reject` 里写着原因；
那时 `header.stamp` 是**这条无效消息的发布时刻**（不是 0），所以消费者可以直接
拿它判"最后一条消息多久没来了"。

**话题上一条消息都没有才是异常**（roscore 挂了 / 话题名写错 / 节点没跑）——
节点保证任何时刻都有一条不超过 1 秒的消息，算不出来的时候也发。

### 4.2 叠加图

```bash
rosrun rqt_image_view rqt_image_view /pallet_servo/overlay
```

或者：

```bash
rosrun image_view image_view image:=/pallet_servo/overlay
```

图上：**黄线** = 托盘参考边（**标签就是你写的那两条原文**），**青框** = 托盘台面，
**绿线** = 箱子的边，**红线** = 垂距，**蓝箭头** = 内法向。

**调参考边时这张图是唯一的判据** —— 看黄线贴不贴托盘、标签上的边号对不对。
