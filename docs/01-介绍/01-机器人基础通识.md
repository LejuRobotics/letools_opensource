## 1.1 搬箱逻辑与通用框架（必修）

### 人是怎么搬箱子的

想象仓库里要把箱子从 A 点搬到 B 点，一个工人通常会：

1. **看**：找到箱子，确认箱子上的标识（例如二维码 / AprilTag）在哪。
2. **想**：决定先走过去，再伸手，不能隔着三米就挥胳膊。
3. **做**：走过去 → 弯腰/抬臂 → 夹住 → 抬起 → 走到目的地 → 放下 → 松手 → 退开。

这三步在机器人领域里分别叫 **感知（Perception）**、**决策/规划（Planning）**、**执行（Execution）**。
本项目要做的，就是让机器人自主完成这三步。

### 本项目是「会走路的机械臂」

| 机器人类型 | 特征与能力 | 代表场景 |
|---|---|---|
| 机械臂 | 位置固定，只能在手臂可达范围内操作 | 工业流水线装配 |
| 移动机器人 (AGV/AMR) | 只有底盘可移动，没有灵活的双手 | 仓库物料搬运 |
| 自主移动操作机器人 | 既要移动（底盘），又要操作（手臂、夹爪） | Kuavo 轮臂机器人 |

**区分**：本项目是**「会走路的机械臂」**——底盘负责「到哪儿」，手臂负责「抓什么」。

Kuavo 轮臂的机体自上而下为：**头部 + 相机 → 左/右臂 + 躯干 → 折叠臂（可折机构）→ 移动底盘**。
硬件型号与末端类型在运控仓库的配置文件中定义，例如
`kuavo-ros-opensource/src/kuavo_assets/config/kuavo_v62/kuavo.json` 中的 `EndEffectorType`
（取值如 `qiangnao` / `lejuclaw` / `qiangnao_touch` / `linker_hand` / `none`）。
**不要想当然按夹爪编写**——按现场实际配置来。

### 一次搬箱的通用框架

把上面「看 → 想 → 做」展开成一条与具体场景无关的通用流水线：

```text
感知：找到 Tag / 识别箱体位姿
  ↓
规划：算出底盘目标点、手臂抓取位姿
  ↓
执行：底盘走过去 → 手臂到位 → 末端闭合 → 抬起
  ↓
收尾：搬到目标点 → 放下 → 松手 → 底盘/头/臂复位
```

这条流水线在代码里由以下几个模块承担，从上到下依次是场景 JSON、行为树引擎、节点、Skill、硬件适配器和运控。表中括号前的名称只是帮助记忆的类比：

| 分层角色 | 代表模块 | 职责 |
|---|---|---|
| 剧本 (Scenario) | `orchestration/scenarios/<scene>/py_tree.json` | 主树 JSON：阶段顺序与子树引用 |
| 调度 (Orchestrator) | `BehaviorTreeFactory` / `BehaviorTreeController` | 解析 JSON、以 50Hz `tick()` 推进 |
| 节点 (Node) | `orchestration/nodes/*.py` | 薄薄一层：解析参数、调 Skill、返回 SUCCESS / RUNNING / FAILURE |
| 司机 (Skill) | `skills/atomic/refactored_sdk/*.py` | 原子动作；由节点在 `initialise()` 中实例化 |
| 遥控器 (Hardware) | `adapters/hardware/`、`IHardware` | 把统一指令翻译成 ROS 话题 / 服务或 SDK 调用 |
| 电机 (Actuators) | 运控 / 驱动 | 真机关节与底盘控制 |

与上表对应的调用链是：**场景 `py_tree.json` → `BehaviorTreeFactory` 构树 / `BehaviorTreeController` 推进 → `orchestration/nodes/*.py` 中的节点 → `skills/atomic/refactored_sdk/*.py` 中的 Skill → `adapters/hardware/`（实现 `IHardware`）→ 运控 / 驱动**。

其中，节点通过 `update()` 推进动作，Skill 通过 `execute()` 执行动作；硬件适配器内部使用 ROS 话题 / 服务或 SDK 与运控通信。`Node.update()`、`Skill.execute()` 是调用方法，`IHardware` 是接口契约，SDK 是适配器内部使用的库，并不是表格中额外的分层模块。

> **小结**：搬箱任务永远可以拆成「感知 → 规划 → 执行」；代码里的每一层都在为这三步服务，别把「让机器人动」和「决定怎么动」混成一件事。

## 1.2 坐标系与 TF（必修）

机器人所有动作都依赖一个问题：**东西在哪、相对谁在哪**。

### 常用坐标直觉

不同模块各自使用不同坐标系；系统必须**不断换算**，否则会出现「地图里点对了，手却伸到别处」。

- **地图坐标系（Map Frame）**：全局世界坐标，底盘导航的目标点（如 A 点、B 点）在此坐标系下定义。
- **里程计坐标系（Odom Frame）**：用于描述连续的局部运动，原点不随机器人移动，但位置估计会累计漂移。
- **机器人本体坐标系（Base Link）**：固定在机器人本体上，随机器人移动而移动。
- **末端 / 相机坐标系（End-Effector / Camera Frame）**：以相机镜头或末端中心为原点，用来描述「物品相对于夹爪/眼睛」的位置。

### TF（Transform，坐标变换）

**TF 是 ROS 里专门维护「这些坐标系之间谁相对谁、差多少」的一套机制**。它把每对坐标系之间的关系拆成
**父 frame → 子 frame** 的一条条边，串成一棵树（TF tree）。有了这棵树，任意两个 frame 之间的位姿都能
一次查询算出来，你不用手推矩阵。

一条典型的抓取数据流：

1. 相机拍到 tag；
2. 得到 tag 在**相机坐标系**下的位姿；
3. 经 TF / `ar_control` 换算到**地图坐标**；
4. 程序计算「底盘还要走多远、手臂从哪下手」。

### URDF：机器人各部件怎样连接

**URDF（Unified Robot Description Format，统一机器人描述格式）**是描述机器人结构的 XML 文件。它用 `link` 表示部件、用 `joint` 表示部件间的连接，记录连接位置、关节轴及运动限制。

URDF 定义机器人本体的连接关系；`robot_state_publisher` 结合 URDF 与关节状态，将各部件之间的变换发布到 TF。固定关节通常发布到 `/tf_static`，可动关节随关节状态更新。因此，完整 TF 链需要机器人结构、关节状态，以及定位和视觉模块提供的变换。

### frame 父子链长什么样

下面保留原有 TF 链示意；相机的实际挂载父节点、标签的发布父节点及具体 frame 名，以该型号 URDF 和现场 `view_frames` 输出为准，不应直接照此图配置：

```text
map ──► odom ──► base_link ──► torso_link ──► 各臂关节链 ──► camera_link
                                      │
                                      └──► tag_<id>（由 ar_control 广播的标签系）
```

- `map → odom`：一般由导航/定位模块给出；`odom` 会随时间漂移，`map` 才是全局稳定的。
- `odom → base_link`：由底盘里程计给出。
- `base_link` 往下：由 `robot_state_publisher` 根据 URDF 与关节状态发布机器人本体各部件的变换。
- `camera_link → tag_<id>`：由视觉节点（`ar_control`）广播。

### 常用 tf2 命令

装好 ROS 后可直接用这些命令排查坐标问题：

```bash
rosrun tf2_tools view_frames.py            # 生成 frames.pdf，一眼看清父子链
rosrun rqt_tf_tree rqt_tf_tree             # 图形化 TF 树（需 rqt）
rosrun tf tf_echo map base_link            # 持续打印 map→base_link 的实时变换
rosrun tf tf_echo camera_link tag_4        # 查看某个 tag 相对相机的位置
rosrun tf tf_monitor                       # 看各 frame 的发布频率与延迟
rostopic echo /tf                          # 动态坐标变换数据
rostopic echo /tf_static                   # 静态坐标变换数据（独立话题）
```

> **提示**：`/tf` 与 `/tf_static` 是两个独立话题。`/tf` 通常持续发布动态坐标变换；`/tf_static` 发布静态坐标变换，在 ROS 1 中使用锁存（latched）机制，发布者存活时，新订阅者也能收到其保留的消息，无需周期性重发。查看静态变换请订阅 `/tf_static`；查看两个坐标系之间的变换可使用上面的 `tf_echo`，它会结合动态与静态变换计算结果。

### 真机 / 仿真 / 干跑三种姿态

**真机**：头部扫视 + `NodePercep` 等感知节点把 tag 写入黑板键（如 `latest_tag_<id>`），由 `ar_control_node.py`
广播坐标链。

**仿真 / 干跑**：可在场景 `board.json` 设 `use_virtual_tag: true`，由 `NodeWaitForBlackboard` 注入虚拟位姿，
不依赖真实相机与完整 `ar_control` 链（详见 [`1.7 行为树入门`](#17-行为树入门必修) 与场景
`refactored_sdk_single_tag_pick_v0/README.md`）。

仿真里还需要一个 **TF republisher**（`infrastructure/ros_packages/start_tf_republisher.sh`）把坐标关系重新广播出来，
启动方式见 [`../02-环境安装/03-安装步骤.md`](../02-环境安装/03-安装步骤.md)。

> **小结**：地图点、相对机器人、相对手/相机——三种坐标要经常换算；这棵树叫 TF，缺了它导航和抓取会整体偏移。

## 1.3 SLAM 与导航（选读）

> 本节是**选读**。只做 SDK、手臂动作、行为树编排的读者可以跳过，不影响后续章节。

### SLAM 的基本概念

SLAM 是 **S**imultaneous **L**ocalization **A**nd **M**apping 的缩写，中文称 **同步定位与建图**。
它描述移动机器人 / 无人车在一个未知环境中移动时，需要同时完成的两项核心任务：

- **定位（Localization）**：知道「我现在在哪里」；
- **建图（Mapping）**：知道「周围环境是什么样」。

两者相互依赖：没有地图很难判断位置；不知道位置也无法把不同时刻采集到的环境信息拼成地图。
所以 SLAM 的本质是：**通过传感器不断观察环境，在估计自身位置的同时逐步构建并更新地图。**

### 为什么需要 SLAM

很多移动设备无法始终依赖 GPS 或预先制作好的地图：

- 室内仓库 GPS 信号弱或不可用；
- 家庭服务机器人需要适应不同户型；
- 工业机器人需要适应临时变更的工厂布置。

### SLAM 系统的基本组成

- **传感器**：激光雷达、摄像头、深度相机、IMU、轮式编码器等；
- **前端（数据匹配与运动估计）**：根据连续传感器数据，估计设备短时间内的运动变化；
- **后端（全局优化）**：对前端位姿和观测结果做全局优化，降低累计误差；
- **建图模块**：把传感器数据转换为可用的环境地图（栅格地图、点云地图等）；
- **回环检测模块**：识别机器人是否回到曾访问过的区域，一旦发现回环就校正长期累积的位姿误差。

### SLAM 与导航的关系

**SLAM 负责「认路」和「画地图」，导航负责「规划怎么走」**。一个完整的导航系统通常包括：

```text
传感器/定位(SLAM) ──► 地图 ──► 路径规划 ──► 避障 ──► 运动控制 ──► 底盘
```

导航的核心任务是：根据当前位置、目标位置和地图信息，规划一条安全有效的路线，并控制机器人移动。

### 在本项目里怎么落地

- 导航类行为树场景（如 `jibot_nav_v1`）依赖下位机的调度 / 导航服务；没有等价仿真实现时**不能直接在 MuJoCo 运行**。
- 导航依赖的消息包 `leju_mobile_base_msgs` **不在** `kuavo-ros-opensource` 默认发行包列表中，
  需要在 LeTools 侧的 `infrastructure/ros_packages/` 编译。

> **小结**：SLAM 解决「我在哪、周围是什么样」，导航解决「怎么走过去」——先认路，再走路。

## 1.4 ROS 是什么（必修）

### 定义

**ROS（Robot Operating System，机器人操作系统）不是 Windows 那种「整机操作系统」，而是运行在 Linux 上的中间件**：
帮许多程序以统一方式**发现彼此、传数据、调功能**。

可以把它想成公司里的**内部电话与广播系统**：

| 概念 | 类比 | 说明 |
|---|---|---|
| **Node（节点）** | 公司里的员工 | 一个独立可执行进程 |
| **Topic（话题）** | 广播台 | 一个节点发广播（Publisher），多个节点收听（Subscriber），如 `/camera/image_raw` |
| **Service（服务）** | 双向电话 | 客户端发起请求，服务端处理后返回结果，如 `/reset_arm` |
| **Message（消息）** | 广播稿模板 | Topic 中传输的数据结构，如 `kuavo_msgs/*` |
| **Action** | 带进度的服务 | 长任务（如导航到点），可反馈进度、可取消 |

### 为何总要 `source setup.bash`

ROS 程序依赖**环境变量**才能找到消息定义、库路径：

```bash
source /opt/ros/noetic/setup.bash     # 加载系统自带的 ROS 环境
source ~/kuavo_ws/devel/setup.bash    # 加载你编译过的工程环境
```

顺序不能颠倒：先系统，后工作空间。`source` 没做，典型报错是：找不到包、找不到消息类型、节点启动失败。

> **命名说明**：教程里 `kuavo_ws` 是运控工作空间的习惯写法，实际目录名可能是 `kuavo-ros-opensource`。
> 以本机 `devel/setup.bash` 的真实路径为准。

### launch 文件：一次启动一组节点

`roslaunch` 读取 `.launch`（XML）文件，按文件描述一次性拉起多个节点、设参数、定命名空间。
不用 launch，你就得在十几个终端里逐个 `rosrun`。

一个最小 launch 文件长这样：

```xml
<launch>
  <!-- 启动一个节点，节点名 arm_control，来自包 ar_control -->
  <node pkg="ar_control" type="ar_control_node.py" name="ar_control" output="screen"/>

  <!-- 设置参数 -->
  <param name="camera_frame" value="camera_link"/>

  <!-- 被 include 的 launch 会先展开再启动 -->
  <include file="$(find humanoid_controllers)/launch/load_kuavo_real_wheel.launch"/>
</launch>
```

常见写法要点：

- `pkg` / `type` / `name`：包名 / 可执行文件名 / 运行时的节点名（`name` 可与 `type` 不同）；
- `output="screen"`：让节点日志直接打到当前终端，调试时几乎必加；
- `param` / `rosparam` / `arg`：参数、参数文件、可变参数；
- `include`：复用其它 launch。

### 常用命令实操

```bash
roslaunch humanoid_controllers load_kuavo_mujoco_sim_wheel.launch   # 启动一组节点
rosrun ar_control ar_control_node.py                               # 启动单个节点

rosnode list                        # 当前有哪些节点在跑
rosnode info /ar_control            # 看某节点发布了什么、订阅了什么
rostopic list                       # 列出所有话题
rostopic echo /kuavo_arm_state      # 持续打印某话题的消息
rostopic hz /camera/image_raw       # 看发布频率
rosservice list | grep mobile_manipulator
rosservice call /enable_lb_arm_quick_mode "quickMode: 2"   # 调一个服务
rosmsg show kuavo_msgs/CmdVec       # 查看消息结构
```

> 💡 **最常见的「脚本报错」原因**：ROS 里没有对应的服务端节点在跑，消息就石沉大海——这就是你看到
> `ROS 服务不可用` / 连接超时的根因。先 `rosnode list` 确认节点在不在，别急着改代码。

### catkin build 在做什么

Kuavo 运控大量代码是 C++，消息定义（如 `kuavo_msgs`）需要**编译**成头文件和 Python 绑定。

- `catkin build`：在 catkin 工作空间里编译包，产物在 `devel/` 目录下；
- 本项目有**两个 catkin 工作空间**：运控 `kuavo-ros-opensource`（习惯名 `kuavo_ws`）+ LeTools 的 `infrastructure/ros_packages/`。

> ⚠ **易错点**：`kuavo_msgs` 必须与运控侧编译版本一致。若 LeTools 的 `infrastructure/ros_packages/devel`
> 与运控 `devel` 混用且版本不一致，可能导致 import 异常甚至**段错误**。改了 `.msg` 后，必须对对应包
> `catkin clean` 再重编。

> **小结**：ROS 是节点之间传消息、调服务的框架（不是整机 OS）；launch 启动一组节点、Topic 是数据流、Service 是一次性请求；两个 catkin 工作空间的 `devel` 别混用。

## 1.5 仿真与真机（必修）

### 同一套逻辑，不同的「替身」

LeTools 的搬箱 / 取放业务以 **行为树场景** 为主（如 `refactored_sdk_single_tag_pick_v0`），
同一套 JSON 既能在 **MuJoCo 仿真**上跑，也能在**真机**上跑，区别只在底层「替身」是谁。

### 真机是一台由多台「电脑」组成的公司

| 计算机角色 | 对应部门 | 主要职责 |
|---|---|---|
| 上位机 | 业务与感知 | 运行 LeTools：业务编排、行为树、技能及 SDK 调用；按部署配置运行视觉识别与 Tag 检测 |
| 下位机 | 运动控制 | 运行 `kuavo-ros-opensource`：运控、机器人状态及底层 ROS 话题 / 服务 |
| 底盘 / 运控 | 执行部 / 小腿与手 | 底盘移动、机械臂电机驱动、底层 MPC/WBC |

三台设备通常在同一局域网内，通过网络通信。

真机部署时，两个工作空间分别位于**下位机和上位机**（名字因 clone 方式略有差异）：

- **下位机**：运控工作空间 `kuavo-ros-opensource` / `kuavo_ws`：基础控制、消息定义（`kuavo_msgs`）、仿真环境、基础硬件接口；
- **上位机**：工具链工作空间 `LeTools` / `letools_opensource`：高级应用编排、技能库（Skills）、行为树、SDK 接口。

> **提示**：LeTools 内部的 `infrastructure/ros_packages/` 是独立的 catkin 工作空间，位于上位机的 LeTools 目录中，不属于下位机的运控工作空间。

### 为什么需要 Docker 和 MuJoCo

**Docker 解决环境一致性问题，MuJoCo 解决没有真机时的物理仿真问题**，两者用途不同：

- **Docker**：提供隔离、可复用的 Ubuntu + ROS + 依赖环境，减少开发机之间的版本差异；它本身不模拟机器人运动。
- **MuJoCo**：模拟机器人关节、动力学和接触，让控制器在软件模型上运行，用于检查部分运动与控制逻辑；它不能替代真机的负载、视觉与安全验证。

为什么先在 MuJoCo 中验证？开发时可能没有真机可用，或者需要反复修改动作与时序。MuJoCo 提供可重复运行的机器人模型，让同一套控制程序先获得关节状态等反馈、观察动作结果，减少占用真机和现场试错。仅执行 Python 或检查 JSON，无法验证这些物理运动；但仿真通过后仍需真机验证。

为什么还要用 Docker？MuJoCo 提供物理仿真能力，却不会替你配好项目所需的 Ubuntu、ROS、Python 包和系统库。直接在每台开发机安装这些依赖，容易出现版本不一致或与现有环境冲突。Docker 将配套环境封装起来，便于复用同一套依赖和启动方式；它本身不会让机器人产生物理反馈。

两者并非必须绑定使用：依赖已正确安装时，MuJoCo 也可直接运行在宿主机上。本项目教程采用 Docker，是为了统一开发环境；在其中运行 MuJoCo，是为了提供真机的软件替身。

本项目的 PC 仿真教程把两者组合使用：

- 用 Docker 容器提供统一的 Ubuntu + ROS + 依赖环境；
- 容器内同时跑物理仿真（kuavo-ros-opensource）与控制器；
- 真机上不同机器的职责，在开发机上被**压缩进一个开发环境**。

因此仿真教程里会出现「进容器 → 编译两个 catkin 工作空间」。

### 三层就绪：先运控 → 再坐标链 → 最后行为树

联调时本质是**三层就绪**（真机常对应多终端；仿真可在 Docker 内压缩）：

| 层 | 真机 | 仿真 |
|---|---|---|
| 1 运控 / 站立 | `roslaunch humanoid_controllers load_kuavo_real_wheel.launch` | `roslaunch humanoid_controllers load_kuavo_mujoco_sim_wheel.launch` |
| 2 坐标 / Tag | `rosrun ar_control ar_control_node.py` 或 TF republisher | 仿真用 TF republisher；干跑可 `use_virtual_tag` 跳过 |
| 3 业务 | `python3 apps/test_upper_init/run_behavior_tree_json.py --scenario <scene>` | 同左 |

真机常用一步：`rosservice call /enable_lb_arm_quick_mode "quickMode: 2"`（服务定义见 `kuavo_msgs`）。

> 顺序不能颠倒：先有力学与坐标链，再跑行为树。硬件预热在 `run_behavior_tree_json.py` 的 `rospy.init_node` 之后、
> `start_behavior_tree` 之前调用 `get_shared_hardware()`（失败则 **exit 1**，避免首个 tick 才初始化阻塞）。

### 完整启动命令序列

**仿真（MuJoCo）**

**真机**

```bash
source devel/setup.bash

# ② 坐标链：新终端起 TF / ar_control

# ③ 业务：新终端跑行为树场景
```

**干跑（无 ROS、无硬件）**

```bash

export PYTHONPATH=$PWD:$PYTHONPATH

  --scenario orchestration/scenarios/studio_smoke_v1 \
```

### 为何「仿真优先」

- 改代码成本低，不会砸坏真机、夹伤人或撞破箱子；
- 可用虚拟 tag 跳过敏感知调试，专注调试运动逻辑；
- 导航点、手臂轨迹等参数在仿真迭代后再迁到真机标定。

### 安全提示

> ⚠ **读完通识 ≠ 可以独立操作上真机。** 涉及站立、手臂运动、底盘移动、夹爪闭合前，必须：
>
> - 阅读对应迁移指南的安全规范与回滚章节；
> - 现场必须有人监护，并提前准备好急停开关；
> - P0/P1 级操作（改站立链、重启底盘服务等）须按团队规范提交审批。

### 能力边界：仿真能证明什么、不能证明什么

| 阶段 | 可以验证 | 不能证明 |
|---|---|---|
| dry-run | Python、JSON、节点、子树、board | ROS 服务和运动 |
| MuJoCo | ROS/SDK 链路、时序、数据流、部分运动 | 真实安全、负载、视觉和抓取精度 |
| 真机 | 动力学、负载、精度、安全和稳定性 | — |

`jibot_nav` 等场景依赖 JiBot 调度服务，没有等价仿真实现时**不能直接在 MuJoCo 运行**。
fake tag 只能验证后续流程，**不能证明真实视觉通过**。

> **小结**：仿真用软件替身、真机每一步都有对应的硬件链与启动顺序；上真机前必须先接受安全培训。

## 1.6 SDK 与 LeTools 分层（必修）

> 本节分两半：前半讲 **LeTools 分层**（谁真正动手），后半讲 **SDK 到底是什么、有哪几套**。

### 1.6.1 LeTools 分层与数据流

角色表见 [`1.1`](#11-搬箱逻辑与通用框架必修)。要点的数据流是：

```text
场景 py_tree.json → BehaviorTreeFactory / BehaviorTreeController
  → orchestration/nodes/ → skills/atomic/refactored_sdk/
  → adapters/hardware/（实现 IHardware）→ 运控 / 驱动
```

**仓库内的编排入口**（源码都在仓内）：

| 入口 | 路径 | 用途 |
|---|---|---|
| 推荐调试启动器 | `apps/test_upper_init/run_behavior_tree_json.py` | 加载 `py_tree.json` / `board.json`，支持 `--dry-run`、`--scenario` |
| 产线编排主入口 | `orchestration/main.py` | MES / 网关触发后的主程序（与站立链解耦） |
| 默认应用配置 | `config/app_config.yaml` | `robot_type: leju_wheeled`，`backend` 指定 base_velocity / SDK / 末端等 |

Python 行为树进程通过 `core/common/ros_environment.py` 的 `ensure_local_ros_python_path()` 补齐 catkin 生成包路径；
入口 `run_behavior_tree_json.py` 在 import 工厂前**必须先** `import orchestration.engine.py_trees_compat`
（兼容 py_trees 0.7.x / 2.x 差异）。Ubuntu 20.04 / Noetic 现场常锁定 `py_trees==2.2.3`。

### 1.6.2 SDK 是什么

**SDK（Software Development Kit，软件开发工具包）在这里指的是「乐聚官方提供、把机器人底层能力封装成 Python API 的那个库」**，
包名 `kuavo_humanoid_sdk`（pip 包名 `kuavo-humanoid-sdk`）。

**行为树 / Skill 说「把左手伸到世界坐标 (0.3, 0.3, 0.8)」，SDK 负责把这句人话变成控制器能吃的指令。**
它屏蔽了 ROS 话题名、服务名、消息字段、MPC 模式这些细节。

SDK 的典型用法：

```python
from kuavo_humanoid_sdk import KuavoRobot
robot = KuavoRobot()
# 之后通过 robot 的接口控制头部 / 手臂 / 底盘 / 末端
```

### 1.6.3 有哪几套 SDK / 硬件通道

LeTools 里「SDK」不是一个单层概念，从下到上至少有 4 层，很容易混淆，逐层说清：

| 层 | 位置 | 是什么 | 谁来用 |
|---|---|---|---|
| ① 官方 SDK 本体 | `drivers/leju/kuavo_humanoid_sdk`（submodule，pip 包 `kuavo-humanoid-sdk`） | 乐聚官方 Python API，直接和运控 / 驱动对话 | 只有 `adapters` 会碰它 |
| ② Adapter 内部 SDK 管理服务 | `adapters/hardware/leju_wheeled/services/sdk_manager/` | 统一封装 SDK 初始化、MPC 模式、单位转换、错误处理 | Adapter 内部使用 |
| ③ 硬件适配器实现 | `adapters/hardware/leju_wheeled/hardware.py`（`LejuWheeledArmHardware`，Mixin 组合） | 实现 `IHardware` 抽象，把「标准接口 / SDK 直调 / TimedCmd」三种路径落到同一入口 | Skill 通过 `IHardware` 调用 |
| ④ 统一接口 | `core/interfaces/i_hardware.py`（`IHardware`） | 不依赖其他层的契约：底盘 / 手臂 / 腿部 / 头部 / 力控 / 模式 / 反馈 / 末端执行器 | 全项目都依赖它，**不依赖具体实现** |

**②里的 SDK 管理器又分四个**（`services/sdk_manager/`）：

| 管理器 | 职责 |
|---|---|
| `base_sdk_manager.py` | 基类：SDK 初始化、MPC 模式通用处理 |
| `timed_cmd_manager.py` | `TimedCmdAPI` 管理器（带时间参数的精确运动） |
| `arm_sdk_manager.py` | 手臂高级控制（含 frame 字符串 → 枚举解析） |
| `low_level_sdk_manager.py` | 底层直接控制（`robot_sdk.control.*`），**仅供研究 / 诊断，不推荐生产环境使用** |

> **注意**：`low_level_sdk_manager` 需要调用方自行处理 MPC 模式设置与恢复、角度单位换算（度 ↔ 弧度）与错误处理——
> 这些在 `arm_sdk_manager` / `timed_cmd_manager` 里是自动做的。新手不要从它入手。

此外 `adapters/hardware/leju_wheeled/source_sdk_compat/` 放的是**兼容层**（`ik_compat` / `arm_api_compat` /
`joint_state_compat` 等），负责抹平不同 SDK 版本之间的接口差异，同样只在 `adapters` 内部使用。

### 1.6.4 三条硬件控制路径

`LejuWheeledArmHardware` 同时支持三类控制方式（命名规范：SDK 直调方法带 `_sdk` 后缀，TimedCmd 路径带 `_timed` 后缀）：

| 路径 | 方法特征 | 底层 | 适合场景 |
|---|---|---|---|
| **标准接口（Adapter）** | `send_base_pose`、`control_head`、`arm_reset`（无后缀） | ROS 话题 / 服务或封装后的 SDK | 普通应用、Skill、行为树（**推荐**） |
| **SDK 直调** | `control_head_sdk`、`send_base_velocity_sdk` | Adapter 内部 SDK 管理服务 → `kuavo_humanoid_sdk` | 高频控制、力控 |
| **TimedCmd（Ruckig）** | `send_timed_base_pose`、`*_timed` | `TimedCmdAPI` → ROS 服务，带时间参数 | 时间最优、运动平滑的定点运动 |

> 💡 **新手建议**：从 **标准接口（Adapter）** 起步，它最完整、错误提示最友好。三条路径的完整对照与选型见
> [`../03-接口详细文档/09-控制路径与选型.md`](../03-接口详细文档/09-控制路径与选型.md)。

### 1.6.5 SDK 从哪来、版本怎么锁

SDK **不在** LeTools 仓库里，而是作为 **git submodule** 挂在 `drivers/leju/kuavo_humanoid_sdk`，
指向 `kuavo-ros-opensource` 仓库；`scripts/install_sdk.sh` 会初始化该 submodule，并用 sparse-checkout 只取
`src/kuavo_humanoid_sdk/*`，再执行安装。

配套版本由仓库自带的锁文件记录：

```bash
# scripts/kuavo_humanoid_sdk_tools/sdk_version.env
SDK_REPO_BRANCH="master"
SDK_REPO_TAG="1.4.5"
```

两个字段必须同时设置：`SDK_REPO_BRANCH` 指定来源分支，`SDK_REPO_TAG` 指定实际安装的固定版本。安装脚本会校验 tag 对应的提交是否为该分支当前提交的祖先，或与其相同，不满足条件就退出。分支可以继续更新，不要求它与 tag 指向同一个 commit；实际安装以 tag 为准。

```bash
cd ~/LeTools
chmod +x scripts/install_sdk.sh
./scripts/install_sdk.sh          # 初始化 submodule → 切分支 → 生成配置 → 安装 SDK
python3 -c 'from kuavo_humanoid_sdk import KuavoRobot; print("SDK Ready!")'
```

普通用户**不要**手动改 `sdk_config.sh`；只有临时调试其他版本时才用本地覆盖。

### 1.6.6 找 SDK 相关代码的位置

| 需求 | 去哪看 |
|---|---|
| 装 / 卸 SDK | `scripts/install_sdk.sh`、`scripts/remove_local_sdk.sh` |
| 版本锁定 | `scripts/kuavo_humanoid_sdk_tools/sdk_version.env` |
| SDK 管理服务 | `adapters/hardware/leju_wheeled/services/sdk_manager/` |
| SDK 版本兼容层 | `adapters/hardware/leju_wheeled/source_sdk_compat/` |
| 硬件适配器主类 | `adapters/hardware/leju_wheeled/hardware.py` |
| 统一接口契约 | `core/interfaces/i_hardware.py` |
| 原子技能（调 `IHardware`） | `skills/atomic/refactored_sdk/` |
| SDK 直调示例 | `apps/test_kuavo_5w_sdk_adapter/` |

> **与 `drivers/` 的关系**：`drivers` 层是 `adapters` 的底层支撑，**开发者无需直接调用**。任何应用代码
> 都应通过 `adapters` 暴露的 `IHardware` 标准接口调用，SDK 只出现在适配器内部。参见
> [`01-05-开发者调用路径.md`](05-开发者调用路径.md) 与 [`../03-接口详细文档/07-drivers-与-SDK.md`](../03-接口详细文档/07-drivers-与-SDK.md)。

> **小结**：SDK（`kuavo_humanoid_sdk`）是官方把底层能力封装成人话的 Python 库；它只该出现在 `adapters` 里，应用代码一律通过 `IHardware` 说话；版本由 `sdk_version.env` 锁定。

## 1.7 行为树入门（必修）

若你看得懂**流程图**，行为树就是「可执行、可复用的机器人流程图」。LeTools 用 **`py_trees`** 承载树实例；
JSON 由 **`BehaviorTreeFactory`**（`orchestration/engine/behavior_tree_factory.py`）解析为
`Sequence` / `Selector` / `Parallel` 与 `orchestration/nodes/` 下注册的叶子类。

### 1.7.1 行为树 vs 普通 if-else 脚本

| 特性 | 普通 Python 脚本 (if-else) | 行为树 (Behavior Tree) |
|---|---|---|
| 结构组织 | 代码硬编码，逻辑深层嵌套 | 树状节点组织，高度模块化 |
| 配置复用 | 改流程需改代码并重新编译 | 改 JSON 结构即可重新调整流程 |
| 打断与恢复 | 难以中途打断或优雅回退 | 内置 Selector/Parallel，支持抢占与中断 |

### 1.7.2 三种常见组合节点

- **Sequence（顺序节点）**：从左到右依次执行子节点，只有全成功才算成功，遇到失败即终止。
- **Selector（选择节点）**：从左到右依次尝试，遇到第一个成功的子节点即成功（类似 fallback 备用逻辑）。
- **Parallel（并行节点）**：同时运行多个子节点（如「边底盘走位边扫视头部」），按 `policy` 汇总结果。

> ⚠ **注意**：`Parallel` 默认仍是**单线程依次** tick；要让阻塞动作真正并行，需显式叠加 `Async` 装饰器。

### 1.7.3 叶子节点与黑板

- **节点（Node）**：树上的一个框，对应 `orchestration/nodes/` 里一个 Python 类。工厂按类名 / 蛇形文件名建立索引。
  常用叶节点：`NodeHeadSequence`、`NodePercep`、`NodeWaitForBlackboard`、`NodeWheelWalk`、`NodeWheelArm`、
  `ArmJointTrajSdkMove`、`EndEffectorClose` 等。
- **黑板（Blackboard）**：`py_trees.blackboard.Client`，是节点之间共享数据的全局键值存储；启动器在 tick 前把
  `board.json` 写进去。例如在 `refactored_sdk_single_tag_pick_v0` 中：
  - `NodePercep` 写入 `latest_tag_<id>`；
  - `NodeWaitForBlackboard` 在虚拟 tag 模式下写入站立相对位姿相关键；
  - `NodeComputePickGoal` / `NodeTagToArmGoal` 读 tag 与 `box_*` 几何参数计算目标。

### 1.7.4 JSON 三文件分工

| 文件 | 作用 | 定位 |
|---|---|---|
| `py_tree.json` | 主树：定义整体阶段流转 | 任务顺序 |
| `py_tree_child.json` | 子树库：定义具体阶段内部细节（如抓取阶段） | 可复用段落的仓库 |
| `board.json` | 黑板参数：提供节点运行所需的具体数值 | 运行时数据 / 物理参数与标定常量 |

设计原则（全程一致）：**物理参数与标定常量写 `board.json`，控制逻辑流写 `py_tree.json`。**

节点 `params` 里常见的 `source` 取值：

| source | 含义 |
|---|---|
| `CUSTOM` | 直接写在 JSON 里的常量 |
| `READ_BOARD` | 从黑板键中动态读取（如 `pick_pre_x`） |
| `RESOLVED` | 已由宏替换引擎解析过的值（`${宏}` 替换后） |
| `INPUT` | 未被替换的 `${宏}`（`macro_map` 中没找到） |

> `${宏}` 需在 `interface.inputs` 中声明，加载时替换 `source=INPUT` 的 `${var}`；未声明会产生「变量未定义」告警。

### 1.7.5 一个最小可读的树

```json
{
  "tree": {
    "name": "Sequence",
    "label": "demo_seq",
    "params": {},
    "childs": [
      { "name": "WaitForEnter", "label": "wait", "params": {}, "childs": [], "childBoard": [] },
      { "name": "ChassisShortMove", "label": "go", "params": { "vx": { "value": "0.3", "source": "CUSTOM" } }, "childs": [], "childBoard": [] }
    ],
    "childBoard": []
  },
  "interface": { "inputs": [], "outputs": [], "custom": [], "process": [] }
}
```

这个 `Sequence` 的意思是：先等人工确认，再让底盘小幅前进。改流程 = 改 `childs` 的顺序或内容，**不需要改 Python 代码**。

### 1.7.6 新增自定义节点

`BehaviorTreeFactory` 会扫描 `orchestration/nodes/` 下的 Python 类。JSON 里 `name` 填的类名必须能映射到该目录的实现，
否则构树时报 **找不到节点**。标准做法：

1. 在 `skills/atomic/refactored_sdk/` 增加 Skill；
2. 在 `orchestration/nodes/` 增加继承 `BaseAction` 的节点类；
3. 在场景 `py_tree.json` / 子树中引用该类名。

部分场景在 `orchestration/scenarios/<scene>/utils/` 放纯函数（如 `refactored_sdk_single_tag_pick_v0/utils/`），
由节点 import，**不**替代节点注册目录。

### 1.7.7 搬箱主线的样子

`refactored_sdk_single_tag_pick_v0` 的主树 `py_tree.json` 顺序为：

```text
Sequence(single_tag_pick_v0)
├─ Parallel(head_search_parallel, success_on_one)   扫头 ∥ 感知 ∥ 等/注入 tag
├─ demo_single_tag_walk_and_pick.json               算目标 → 底盘走 → 臂抓 → 末端闭合
├─ demo_single_tag_lift.json                        抬起
├─ WaitSeconds
└─ demo_single_tag_back_and_reset.json              底盘回退 ∥ 头/臂/躯干复位
```

> **小结**：行为树是可执行的流程图，`Sequence` / `Selector` / `Parallel` 是三种核心结构；黑板存数据、JSON 存结构，二者不能互相替代。
