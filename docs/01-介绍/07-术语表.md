## 一、ROS 与环境

| 术语 | 简要说明 | 在哪出现 |
|---|---|---|
| **ROS** | 跑在 Linux 上的中间件，帮程序互相发现、传数据、调功能；不是整机 OS | 全局 |
| **Node（节点）** | 一个独立可执行的 ROS 程序 | `rosnode list` |
| **Topic（话题）** | 持续数据流：一个节点发广播、多个节点收听 | `rostopic echo /topic` |
| **Service（服务）** | 一次请求一次响应 | `rosservice call /srv` |
| **Message（消息）** | ROS 数据结构，定义字段及类型；用于 Topic，也用于 Service 的请求和响应 | `rosmsg show sensor_msgs/JointState` |
| **launch** | 一个 XML 文件，描述一次要启动的一组节点与参数 | `.launch` 文件 |
| **`setup.bash`** | 加载 ROS / 工作空间环境变量的脚本；没 source 就找不到包 | 每个终端开头 |
| **catkin** | ROS 的编译系统，产物在 `devel/` | `catkin build` |
| **Docker** | 容器，用来统一 Ubuntu + ROS + 依赖环境 | 仿真教程 |
| **`ROBOT_VERSION`** | 标记机器人硬件代次的环境变量（如 `45`、`62`、`63`），对应 `kuavo_v62` 等配置目录 | 启动仿真 / 装 SDK 前 |

## 二、分层与架构

| 术语 | 含义 | 出处 |
|---|---|---|
| core | 不依赖项目内其他层的契约层：接口、领域模型、通用工具 | `core/` |
| drivers | 底层驱动层（SDK 封装、末端执行器驱动） | `drivers/` |
| adapters | 硬件适配层：把硬件能力封装成标准接口 | `adapters/` |
| skills | 原子技能层：一个技能 = 一段明确动作 | `skills/` |
| orchestration | 行为树编排层：JSON 描述流程 + 薄节点 | `orchestration/` |
| apps | 示例与验证入口（跑得起来的最小脚本） | `apps/` |
| 依赖方向 | 模块 import 方向 `apps → orchestration → skills → adapters → drivers → core`：上层可以 import 下层。表示代码依赖关系，不是运行时调用顺序 | `01-04-系统架构与分层` |
| 反向依赖 | 下层 import 上层的越界（E2、E3）；E1 是技能直接耦合具体适配器实现。三类历史例外均记录在 `01-04` 第四节 | 同上 |
| Mixin | 一个职责域一个混入类，主类多继承组装（`hardware.py`） | `adapters/hardware/leju_wheeled/mixins/` |
| factory | 按配置分支创建实现的工厂（`HardwareFactory`） | `adapters/hardware/factory.py` |

## 三、行为树与场景

| 术语 | 含义 | 出处 |
|---|---|---|
| 行为树（Behavior Tree） | 以固定周期从根向下推进的任务结构；每拍重新从根走 | `orchestration/engine/` |
| Tick | 引擎以固定周期（默认 50Hz）对整棵树推进一步 | — |
| 复合节点（Composite） | 只决定策略（子节点如何调度与汇总），不直接发关节指令 | `Sequence` / `Selector` / `Parallel` |
| Sequence | 复合节点：顺序执行子节点，全部成功才成功 | `behavior_tree_factory.py` |
| Selector | 复合节点：依次尝试子节点，直到一个成功 | 同上 |
| Parallel | 复合节点：依次 tick 子节点，按 `policy` 汇总成功/失败；默认不代表多线程执行 | 同上 |
| 装饰器（Decorator） | 有且仅有一个子节点，改写其调度或返回值 | `Async` / `ForEach` / `RepeatUntil` / `RunIfIndex` / `PressureDropGuard` |
| Async | 装饰器：把子节点放后台线程 tick，避免阻塞主循环 | `orchestration/nodes/async_decorator.py` |
| 叶子节点（Leaf / Action） | 调用 Skill / 硬件接口的动作单元 | `orchestration/nodes/*.py` |
| `BaseAction` | 节点通用基类；新 Action 节点应继承它 | `orchestration/nodes/base_node.py` |
| 子树（Subtree） | 以 `.json` 结尾的节点名引用的可复用子树，定义在 `py_tree_child.json` | `05-05-扩展-orchestration-层` |
| `policy` | `Parallel` 的成功判定策略：`success_on_all` / `success_on_one` | — |
| `memory` | `Sequence`/`Selector` 的记忆开关：`True` 时记住运行中的子节点，下次从该节点继续；具体规则依节点类型而定 | — |
| 黑板（Blackboard） | 全局键值存储，节点间传递中间变量；初值来自 `board.json` | `orchestration/utils/blackboard_utils.py` |
| `source`（参数来源） | 节点参数的来源标记：`CUSTOM` / `READ_BOARD` / `RESOLVED` / `INPUT` | 节点 `params` |
| `READ_BOARD` | 参数 `source` 取值：从黑板读取；可用 `board_key` 指定键名 | `behavior_tree_factory.py` |
| `${宏}` | `interface.inputs` 声明的变量，加载时替换 `source=INPUT` 的 `${var}` | — |
| `py_tree.json` | 主树：任务顺序（`tree` 必填、`interface` 建议） | 场景目录 |
| `py_tree_child.json` | 子树库：可复用段落的仓库，KV 字典，`.json` 结尾的 `name` 引用 | 场景目录 |
| `board.json` | 运行时数据与物理参数/标定常量，扁平 Dict，顶层 key 即黑板键名 | 场景目录 |
| `hardware_config.json` | 场景级硬件参数覆盖（非行为树字段，真机路径下 merge 进硬件工厂配置） | 场景目录 |
| manifest | 节点元数据声明（`@define_manifest`），供前端与参数校验使用 | `orchestration/utils/manifest_decorators.py` |
| DryRun | `--dry-run` / `STUDIO_DRY_RUN=1`：不初始化 ROS/硬件，仅校验加载 | `05-05-扩展-orchestration-层` |

## 四、技能与硬件

| 术语 | 含义 | 出处 |
|---|---|---|
| 原子技能（Skill） | 一段明确的动作控制逻辑 | `skills/atomic/` |
| `SkillBase` | 技能基类：统一超时监控、日志、异常处理 | `skills/base/skill_base.py` |
| `ISkill` | 技能接口契约 | `core/interfaces/i_skill.py` |
| `IHardware` | 硬件能力统一入口（底盘/手臂/腿部/头部/力控/模式/反馈/末端执行器） | `core/interfaces/i_hardware.py` |
| `Result` | 统一的操作结果封装；适配器层用它代替抛异常 | `core/domain/result.py` |
| `SkillParams` | 所有技能参数的抽象基类（含 `timeout` / `retry_count` / `extra_kwargs`） | `core/domain/skill_params.py` |
| TimedCmd | 经 `TimedCmdAPI` → ROS 服务、带时间参数的精确运动规划路径 | `adapters/.../mixins/timed_command_mixin.py` |
| SDK 直调 | 适配器内部 SDK 管理服务直接调底层 Kuavo API（`_sdk` 后缀） | `adapters/.../mixins/sdk_control_mixin.py` |
| 标准接口 | 符合 `IHardware`、走 ROS 话题/服务的无后缀方法（推荐） | 同上 |
| SDK / `kuavo_humanoid_sdk` | 乐聚底层能力的 Python API 库；按项目分层约定，应用通过适配器调用 | `drivers/leju/kuavo_humanoid_sdk` |
| WBC | 全身控制；属于运控仓库的底层算法 | 运控仓库 |
| MPC | 模型预测控制；LeTools 侧的 `MPCControlMode` 见下方专条 | `core/domain/enums.py` |
| Ruckig | 在线轨迹生成算法，用于 TimedCmd 路径的平滑时间参数 | `core/domain/ruckig_params.py` |
| IK / FK | 逆/正运动学 | `core/common/transform.py` |
| 导航后端路由 | 上层只调无厂商名的标准接口，由 `navigation_chassis_backend` 路由到品牌后端 | `mixins/navigation_chassis_mixin.py` |

### `MPCControlMode` 的当前状态

`core/domain/enums.py` 定义了 `MPCControlMode` 的**五个取值**：`NO_CONTROL(0)` / `ARM_ONLY(1)` / `BASE_ONLY(2)` / `BASE_ARM(3)` / `ARM_EE_ONLY(4)`。

**仓库记录的当前固件中，这五个取值仅被存储，未决定控制分支。具体状态应以所用运控与 SDK 版本为准**：

- 服务端只**存储并回显**模式值，**主循环中消费该模式的 `switch` 整块已被注释**（`kuavo-ros-control` 与 `kuavo-ros-opensource` 两副本一致，均硬编码走 `updateBaseArmControl`）；
- 适配器侧 `adapters/hardware/leju_wheeled/mixins/mode_service_mixin.py` 的 `set_mpc_mode()` 已标注弃用并打印警告，但仍调用 ROS 服务；
- 实际控制行为由 `set_arm_control_mode(2)` + planner 指令类型决定，**真正的活通道是 `flow`**。

因此，在上述固件中，`MPCControlMode` 值不能作为实际控制分支的开关。保留服务调用是为了兼容未来固件恢复消费，以及依赖其软暂停守卫；SDK 包装调用还可能设置控制流。

## 五、机器人、坐标与感知

| 术语 | 含义 |
|---|---|
| 末端执行器（End Effector） | 夹爪 / 灵巧手等执行末端；类型在 `kuavo_assets` 配置（`qiangnao` / `lejuclaw` / `qiangnao_touch` / `linker_hand` / `none`） |
| 底盘（Chassis） | 移动平台；LeTools 侧有两个品牌后端：嘉腾（`jiateng`）与玖物（`jibot`） |
| 躯干（Torso） | 腰/躯干关节组，`TorsoControlMixin` 负责位姿控制与笛卡尔焦点设置 |
| 关节（Joint） | 机械臂/腿部转动的自由度 |
| 位姿（Pose） | 位置 + 姿态（`Pose6D` 在 `core/domain/pose.py`） |
| TF / 坐标系 | ROS 的坐标变换体系；`FrameType` 区分基座/世界/工具坐标系 |
| map / odom / base_link | 地图坐标系 / 里程计坐标系 / 机器人本体坐标系 |
| SLAM | 同步定位与建图：同时估计自身位置并建立环境地图 |
| 导航 | 在地图上规划并执行移动路径；导航类场景由 `ChassisNavigationMove` 节点驱动 |
| AprilTag | 视觉定位标签，`apriltag_ros` |
| 头部 | 头部由 `control_head` / `control_head_sdk` 控制 |

| 术语 | 含义 | 出处 |
|---|---|---|
