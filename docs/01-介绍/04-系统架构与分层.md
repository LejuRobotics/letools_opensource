# 04 系统架构与分层

[返回文档首页](../README.md) · [01-介绍](../01-介绍/) · [02-环境安装](../02-环境安装/)

> 本篇是 LeTools 模块分层的**权威说明**：各层职责、允许的依赖方向、一次典型运行的调用流程，以及当前代码中的已知例外。
> 其他篇目引用本篇，不再重复这些内容。面向贡献者的落层判定与规避方式见
> [`../05-进阶开发指南/01-扩展总则与分层规范.md`](../05-进阶开发指南/01-扩展总则与分层规范.md)。

本篇用两张图描述两种不同的关系，阅读时不要混用：

- **模块依赖关系**（第一节）：哪个目录的代码可以 `import` 哪个目录，用于评审和落层判定；
- **运行调用流程**（第二节）：执行一个场景时，控制命令依次经过哪些组件。

## 一、模块依赖关系

```text
apps            示例与验证入口
  ↓
orchestration   行为树编排（JSON 描述流程 + 薄节点）
  ↓
skills          原子技能（一个技能 = 一段明确动作）
  ↓
adapters        硬件适配器（含 SDK 管理服务），实现 IHardware
  ↓
drivers         底层驱动（SDK 封装、末端执行器驱动）
  ↓
core            接口 / 数据模型 / 通用工具（不依赖项目内其他层）
```

箭头表示 **import 依赖方向**：上层可以 import 下层，下层不应 import 上层。它不是运行时数据经过的顺序——
`core` 画在最底部，是因为它被所有层引用，而不是因为控制命令最后要经过 `core`。

| 层 | 允许 import | 禁止 | 典型文件 |
|---|---|---|---|
| `core` | 标准库、通用第三方库（`numpy`、`scipy`、`PyYAML`、`colorlog`）与 `core` 内部 | `drivers` / `adapters` / `skills` / `orchestration` / `apps` | `core/interfaces/i_hardware.py` |
| `drivers` | `core`、标准库 | `adapters` 及以上各层 | `drivers/leju/end_effector.py`、`drivers/leju/kuavo_humanoid_sdk/` |
| `adapters` | `core`、`drivers`、标准库与第三方驱动 | `skills` / `orchestration` / `apps`（例外见 E3） | `adapters/hardware/leju_wheeled/hardware.py` |
| `skills` | `core`；硬件能力通过构造时注入的 `IHardware` 获得 | `orchestration` / `apps`（例外见 E2）；不宜直接 import `adapters` 中的具体实现（存量见 E1） | `skills/atomic/refactored_sdk/*.py` |
| `orchestration` | `core`、`skills`、`adapters` | `apps`（例外见 E3） | `orchestration/nodes/`、`orchestration/engine/` |
| `apps` | 所有下层 | — | `apps/test_kuavo_5w_sdk_adapter/` |

> **关于 `skills` 与 `adapters`**：`skills` 位于 `adapters` 之上，向下依赖在方向上没有问题；
> 规则限制的是**依赖对象**——技能应依赖 `core.interfaces` 中的 `IHardware` 抽象，
> 具体适配器由 `HardwareFactory` 创建后注入，而不是在技能里 import `LejuWheeledArmHardware` 等具体类或模块级函数。
> 因此 E1 记录的是「耦合具体实现」，E2 / E3 记录的才是真正的反向依赖。

## 二、典型运行调用流程

以 `apps/test_upper_init/run_behavior_tree_json.py --scenario <场景目录>` 在仿真或真机上运行为例：

```text
run_behavior_tree_json.py               解析参数，读取场景目录
  → BehaviorTreeFactory                 orchestration/engine/：py_tree.json + py_tree_child.json + board.json → py_trees 树
  → BehaviorTreeController              orchestration/engine/：按固定频率 tick
  → 行为树叶子节点                       orchestration/nodes/：读取参数与黑板，调用 Skill 或 IHardware
  → Skill                               skills/：执行一段具体动作
  → IHardware 实现                       adapters/：LejuWheeledArmHardware，由 orchestration/shared_hardware.py
                                         经 HardwareFactory 创建，所有节点共享同一实例
  → ROS 话题 / 服务，或适配器内的 SDK 管理服务 → kuavo_humanoid_sdk（drivers/）
  → 运控（kuavo-ros-opensource）→ MuJoCo 仿真或真机
```

- `core` 不是这条链上的一个环节：链上每一环都使用 `core` 定义的接口与数据类型（`IHardware`、`Result`、`Pose6D` 等）。
- `--dry-run` 时不初始化 ROS，也不创建 `IHardware`，流程止于节点层，见
  [`../04-简单案例运行/01-最小可运行示例.md`](../04-简单案例运行/01-最小可运行示例.md)。
- `apps/` 下的单项测试脚本不经过行为树，直接通过 `HardwareFactory` 创建适配器并调用 `IHardware`。

## 三、各层职责

### `core` —— 契约层

放的是**所有人共同遵守的约定**，不依赖项目内其他层，可以被任何一层 import。
它使用少量通用第三方库（`numpy`、`scipy`、`PyYAML`、`colorlog`），但不依赖 ROS、SDK 或具体硬件。

- `core/interfaces/`：`IHardware`（硬件能力统一入口）、`ISkill`、`ICamera`、`IPerception`；
- `core/domain/`：`Result`（统一结果封装，取代抛异常）、`Pose6D`、`JointState`、`Trajectory`、`SkillParams`、各类枚举；
- `core/common/`：`logger`、`config_loader`、`transform`、`ros_environment`（`ensure_local_ros_python_path()`）、异常族。

`core` 不 import 项目内任何其他层，目前没有例外。
判断依赖是否合理时，除了看「谁 import 了谁」，还要看**被依赖的东西承担什么职责**——
`core` 里放的是契约，`adapters` 里放的是与具体硬件/厂商耦合的实现。

### `drivers` —— 底层驱动层

与硬件 / SDK 直接对话的那一层，代表性内容是 SDK submodule（`drivers/leju/kuavo_humanoid_sdk`）
与末端执行器驱动。**开发者无需直接调用**——应用代码通过 `adapters` 暴露的 `IHardware` 调用硬件能力。

### `adapters` —— 硬件适配层（开发者主要调用入口）

把 `core/interfaces/*` 里的抽象方法落到具体机器人平台。核心是 **Mixin 组合**：
一个职责域一个混入类，`adapters/hardware/leju_wheeled/hardware.py` 的 `LejuWheeledArmHardware` 多继承组装。

| 组件 | 作用 |
|---|---|
| `adapters/hardware/factory.py` | `HardwareFactory`：按 `robot_type` 创建 `leju_wheeled` / `leju_bipedal` 适配器 |
| `adapters/hardware/leju_wheeled/mixins/` | 各能力 Mixin：生命周期、底盘、躯干、手臂、力控、模式、末端执行器、状态反馈、TimedCmd、SDK 直调、导航路由、品牌底盘（jiateng / jibot） |
| `adapters/hardware/leju_wheeled/services/sdk_manager/` | SDK 管理服务：`BaseSDKManager` + `TimedCmdManager` / `ArmSDKManager` / `LowLevelSDKManager` |
| `adapters/hardware/leju_wheeled/source_sdk_compat/` | 跨 SDK 版本的兼容层（IK / 手臂 API / 关节状态等） |

适配器同时支持三条控制路径（标准接口 / SDK 直调 `_sdk` / TimedCmd `_timed`），
选型见 [`../03-接口详细文档/09-控制路径与选型.md`](../03-接口详细文档/09-控制路径与选型.md)。

### `skills` —— 原子技能层

一个技能 = 一段明确动作（如「头部转 30°」「手臂走一条关节轨迹」）。基类 `SkillBase`
（`skills/base/skill_base.py`）统一超时监控、日志与异常处理。

```text
skills/
├── base/skill_base.py        SkillBase：超时 / 日志 / 异常的统一实现
└── atomic/
    ├── refactored_sdk/       当前推荐的新 SDK 技能（一文件一技能）
    ├── manipulation/         旧版操作技能
    ├── motion/               旧版运动技能
    ├── perception/           感知技能
    └── grasp_skill.py        旧版抓取技能
```

### `orchestration` —— 行为树编排层

从 JSON 构建 PyTrees 行为树，并把节点执行委托给 `skills`：

| 组件 | 作用 |
|---|---|
| `orchestration/main.py` | 旧/通用行为树入口，可 dry-run 或真机运行 |
| `orchestration/engine/behavior_tree_factory.py` | JSON → PyTrees 的核心工厂 |
| `orchestration/engine/behavior_tree_controller.py` | 行为树控制器（50Hz tick） |
| `orchestration/engine/py_trees_compat.py` | py_trees 版本兼容（须最先 import） |
| `orchestration/nodes/` | 行为树节点（一个节点调用一个 Skill） |
| `orchestration/scenarios/` | 场景 JSON（`py_tree.json` / `py_tree_child.json` / `board.json` / `hardware_config.json`） |
| `orchestration/shared_hardware.py` | 全局硬件单例，所有节点共享同一个 `IHardware` 实例 |

### `apps` —— 示例与验证入口

跑得起来的最小脚本，按测试层级分目录（`test_kuavo_5w_adapter` / `test_kuavo_5w_sdk_adapter` /
`test_kuavo_5w_orchestration` / `test_kuavo_5w_skills` / `test_camera_adapter` / `test_upper_init` 等）。

## 四、已知分层例外（E1 / E2 / E3）

仓库当前存在若干处违反第一节规则的历史遗留：E1 是技能直接耦合具体适配器实现，E2 / E3 是下层 import 上层。
这些是**已存在的事实，不是被认可的做法**；新增代码不得再产生同类依赖。
本节是例外清单的唯一维护位置，[`05-01`](../05-进阶开发指南/01-扩展总则与分层规范.md) 只给出规避方式并链接到这里。

**计数口径**：

- **E1**：`skills/**/*.py` 里 import `adapters` 的**文件数**，**统计开源发布范围内的文件，不含 `tests/`**；
- **E2**：`skills/**/*.py` 里 import `orchestration` 的**文件数**，**统计开源发布范围内的文件，不含 `tests/`**；
- **E3**：`adapters/` 与 `orchestration/` 里 import `apps` 的**文件数**，**统计开源发布范围内的文件，不含 `tests/`**。

三条例外统一按开源发布范围统计、不含 `tests/`。以下数字为 2026-11-06 实测，代码变化后请用各小节的命令重新统计。

### E1：`skills` → `adapters`（直连具体硬件类型 / 兼容层句柄）

**实测规模：9 个文件**（按开源发布范围统计，不含 `tests/`）。

复现：

```bash
grep -rlE '^[[:space:]]*(from|import)[[:space:]]+adapters' skills --include='*.py' \
  | grep -v -e '/tests/' -e '_internal/' | wc -l   # → 9
```

| 位置 | 依赖对象 |
|---|---|
| `skills/atomic/manipulation/torso_pose_control/skill.py` | `adapters.hardware.leju_wheeled.hardware.LejuWheeledArmHardware` |
| `skills/atomic/manipulation/leg_joint_control/skill.py` | 同上 |
| `skills/atomic/manipulation/pos_base_control/skill.py` | 同上 |
| `skills/atomic/manipulation/pos_world_control/skill.py` | 同上 |
| `skills/atomic/manipulation/vel_control/skill.py` | 同上 |
| `skills/atomic/refactored_sdk/bimanual_joint_trajectory.py` | `adapters.hardware.leju_wheeled.source_sdk_compat.ImmediateHandle` |
| `skills/atomic/refactored_sdk/vacuum_control.py`、`vacuum_485.py`、`pressure_drop_detection.py` | `adapters.vacuum_control` / `adapters.vacuum_485` 的模块级函数 |

**成因**：这批旧版 `manipulation` 技能与部分 `refactored_sdk` 技能在 `IHardware` 抽象之外，
直接引用了具体适配器类（做类型判断、构造或复用底层兼容层句柄），而非通过构造注入的 `IHardware` 抽象调用。

### E2：`skills` → `orchestration`（manifest 契约 + 场景局部工具）

| 位置 | 依赖对象 | 说明 |
|---|---|---|
| **39 个技能文件** | `orchestration.utils.manifest_decorators.define_manifest` | **既定契约，不是违规**：技能的 manifest 元数据与节点共用同一套声明机制 |
| `skills/atomic/refactored_sdk/bimanual_joint_trajectory.py` | `orchestration.scenarios.wheel_arm_single_tag_pick_v1.utils.{async_execution,trajectory}` | 复用了某个场景目录下的局部工具 |
| `skills/atomic/refactored_sdk/single_tag_joint_pick_plan.py` | `orchestration.scenarios.wheel_arm_single_tag_pick_v1.utils.source_joint_planner` | 同上 |

复现：

```bash
# import orchestration 的技能文件总数（含 @define_manifest）
grep -rlE '^[[:space:]]*(from|import)[[:space:]]+orchestration' skills --include='*.py' \
  | grep -v -e '/tests/' -e '_internal/' | wc -l   # → 39
# 其中依赖场景 / 节点 / 引擎的越界文件
grep -rlE '^[[:space:]]*(from|import)[[:space:]]+orchestration\.(scenarios|nodes|engine)' skills --include='*.py' \
  | grep -v -e '/tests/' -e '_internal/'           # → 2 个文件
```

> **`@define_manifest` 单独看**：它的实现在 `orchestration/utils/`，但描述的是技能与节点的**公共元数据**，
> 技能必须能引用它才能被注册。它是当前唯一被接受的技能→编排依赖。
> **E2 里真正的越界只有 2 处**（上表后两行）。

**成因**（越界部分）：把本应留在场景目录内的工具函数提到了技能层复用。

### E3：`adapters` / `orchestration` → `apps`（调试路径）

**实测规模：3 个文件。**

```bash
grep -rlE '(from|import)[[:space:]]+apps' adapters orchestration --include='*.py' \
  | grep -v -e '/tests/' -e '_internal/' | wc -l   # → 3
```

| 位置 | 依赖对象 | 加载方式 |
|---|---|---|
| `adapters/hardware/leju_wheeled/inference_bridge.py` | `apps.test_kuavo_5w_sdk_adapter._scaffold` | 函数体内惰性 import |
| `orchestration/nodes/arm_ee_local_timed_move.py` | `apps.test_kuavo_5w_sdk_adapter._scaffold` | 函数体内惰性 import |
| `orchestration/nodes/boxcarry.py` | `apps.test_kuavo_5w_adapter._scaffold` | 函数体内惰性 import |

**成因**：三处都只在「脱离正常启动流程、直接以脚本方式调试某个节点」时才会走到。
**行为树的正常控制路径不加载 `apps`**。

### 小结

| 类别 | 含义 | 实测规模 |
|---|---|---|
| E1 | `skills` → `adapters` 具体实现（绕过 `IHardware` 抽象） | **9 个文件** |
| E2 | `skills` → `orchestration`（manifest 契约 + 场景局部工具） | `@define_manifest` 被 **39 个**技能引用，属**既定契约**；真正越界 **2 处** |
| E3 | `adapters` / `orchestration` → `apps`（调试路径） | **3 个文件** |

**共同约束**：新增代码不得再产生同类依赖。评审时若发现新写的 `skills` / `adapters` 代码 import 了具体适配器或更上层模块，
按 E1–E3 的口径拦下，不以历史遗留作为先例。

第一节要求 SDK 只在 `adapters` 内部使用，但以下文件直接 import 了 `kuavo_humanoid_sdk`（多为函数体内 import SDK 的数据类型或策略模块），
目前未纳入 E1–E3 统计，新增代码同样不应照做：

```bash
grep -rlE '^[[:space:]]*(from|import)[[:space:]]+kuavo_humanoid_sdk' skills orchestration/nodes orchestration/engine \
  --include='*.py' | grep -v '/tests/'
```
