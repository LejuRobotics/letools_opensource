## 一、模块分层：让改动落在确定的位置

### 解决的问题

当感知、规划和硬件控制逻辑集中在同一个脚本中时，调整任务流程或更换硬件，通常需要同时修改多处代码。
LeTools 按职责把代码分成 `apps`、`orchestration`、`skills`、`adapters`、`drivers`、`core` 六层，以降低这些模块之间的耦合。

### 在代码里长什么样

分层图、各层允许的 import 和运行调用流程见 [`04-系统架构与分层.md`](04-系统架构与分层.md)，这里只列各层职责与典型文件：

| 层 | 职责 | 典型文件 |
|---|---|---|
| `core` | 定义接口与数据模型，提供通用工具 | `core/interfaces/i_hardware.py`、`core/domain/result.py` |
| `drivers` | 与 SDK / 硬件通信的底层封装 | `drivers/leju/kuavo_humanoid_sdk/`（submodule） |
| `adapters` | 把具体硬件实现成 `IHardware` | `adapters/hardware/leju_wheeled/hardware.py` |
| `skills` | 一个技能完成一段明确动作 | `skills/atomic/refactored_sdk/*.py` |
| `orchestration` | 节点 + 场景，把技能编排成流程 | `orchestration/nodes/`、`orchestration/scenarios/` |
| `apps` | 可独立执行的验证脚本 | `apps/test_kuavo_5w_sdk_adapter/` |

**收益**：更换硬件时主要改 `adapters`；新增动作在 `skills` 实现，再由 `orchestration/nodes/` 中的节点接入行为树；调整流程改场景 JSON；验证脚本放在 `apps`。

> 仓库现存三类历史例外（E1 / E2 / E3），逐条说明见 [`04-系统架构与分层.md`](04-系统架构与分层.md#四已知分层例外e1--e2--e3)。

## 二、PyTrees 编排：用行为树描述任务流程

### 解决的问题

用 `if-else` 编写多阶段任务时，嵌套层级会随流程增长，中途打断、失败回退和片段复用都难以实现；调整一处顺序往往需要读懂整段代码。

### 在代码里长什么样

LeTools 用 **`py_trees`** 承载树实例，用 **JSON** 描述结构，由 `BehaviorTreeFactory`
（`orchestration/engine/behavior_tree_factory.py`）解析成复合节点与叶子节点：

```text
编排名词            机器人语义
─────────────     ────────────────────────────────
Sequence          依次做，全成功才成功
Selector          依次试，一个成功就成功（fallback）
Parallel          同时跑（默认单线程依次 tick，需 Async 才真并行）
装饰器            改写调度或返回值（Async / ForEach / RepeatUntil / RunIfIndex / PressureDropGuard）
叶子节点          真正干活：调一个 Skill
黑板              节点间共享数据的全局键值存储
```

叶子节点是「薄」的：解析参数 → 调 Skill → 返回 `SUCCESS` / `RUNNING` / `FAILURE`。
真正的动作逻辑在 `skills/`，硬件通信在 `adapters/`。

**核心法则**：**JSON 管编排，Skill 管动作，Adapter 管底层通信。**

### 收益

| 对比项 | 普通 if-else 脚本 | 行为树 |
|---|---|---|
| 结构组织 | 代码硬编码，逻辑深层嵌套 | 树状节点组织，高度模块化 |
| 流程调整 | 修改 Python 代码，重新运行并回归测试 | 修改场景 JSON 即可调整节点顺序与参数；新增动作仍需编写节点或技能 |
| 打断与恢复 | 难以中途打断或优雅回退 | 内置 Selector/Parallel，支持抢占与中断 |

详见 [`1.7 行为树入门`](01-机器人基础通识.md#17-行为树入门必修) 与
[`../03-接口详细文档/05-orchestration-行为树编排.md`](../03-接口详细文档/05-orchestration-行为树编排.md)。

## 三、JSON 场景定义：调整流程与参数不改 Python 代码

### 解决的问题

同一条业务线（例如「单 Tag 取放」）在不同箱体尺寸、不同 Tag ID、不同现场标定下要反复调整。
若这些数值硬编码在 Python 里，每次调整参数都要修改代码、重新测试并发布。

### 在代码里长什么样

一个场景目录由四类文件构成：

| 文件 | 定位 | 缺了会怎样 |
|---|---|---|
| `py_tree.json` | **任务顺序**：主树，`tree` 必填 + `interface` 建议 | 启动器直接报「主树不存在」 |
| `py_tree_child.json` | **可复用段落的仓库**：KV 字典，`.json` 结尾的 `name` 引用，加载时 deepcopy | 引用了子树才会报错 |
| `board.json` | **运行时数据与物理参数 / 标定常量**：扁平 Dict，顶层 key 即黑板键名 | 节点读不到键会走默认值或报错 |
| `hardware_config.json` | **场景级硬件参数覆盖**（非行为树字段），真机路径下 merge 进硬件工厂配置 | 可选 |

**设计原则**：**物理参数与标定常量写 `board.json`，控制逻辑流写 `py_tree.json`。**

节点参数的 `source` 取值决定值的来源：

| source | 含义 |
|---|---|
| `CUSTOM` | 直接写在 JSON 里的常量 |
| `READ_BOARD` | 从黑板键动态读取 |
| `RESOLVED` | 已由宏替换引擎解析过的值 |
| `INPUT` | 未被替换的 `${宏}` |

`${宏}` 需在 `interface.inputs` 中声明，加载时替换 `source=INPUT` 的 `${var}`。

### 收益

- **改参数**（箱宽、Tag ID、关节轨迹数据）→ 只改 `board.json`；
- **改流程**（先导航还是先抓）→ 只改 `py_tree.json` / 子树的 `childs` 顺序（**不能**只靠改 board 数字改变拓扑）；
- **改新场景** → 复制一个场景目录改 JSON 即可，不动 Python。

## 四、SDK 版本锁定：在安装阶段发现版本错配

### 解决的问题

SDK 来自另一个仓库（`kuavo-ros-opensource`）。版本不匹配时，问题通常在运行期才暴露：
话题订阅失败、消息 md5sum 不一致，甚至段错误。在安装阶段校验版本，可以避免这类问题进入运行期。

### 在代码里长什么样

SDK 作为 **git submodule** 挂在 `drivers/leju/kuavo_humanoid_sdk`，配套版本由仓库自带的锁文件记录：

```bash
# scripts/kuavo_humanoid_sdk_tools/sdk_version.env
SDK_REPO_BRANCH="master"
SDK_REPO_TAG="1.4.5"
```

两个字段必须同时设置：`SDK_REPO_BRANCH` 指定来源分支，`SDK_REPO_TAG` 指定实际安装的固定版本。tag 对应的提交必须为该分支当前提交的祖先，或与其相同，不要求两个字段指向同一 commit；实际安装以 tag 为准。`scripts/install_sdk.sh` 在安装前会：

1. 校验两个字段齐全；
2. 校验 tag 对应提交是否为该分支当前提交的祖先，或与其相同（`git merge-base --is-ancestor`），不通过直接退出；
3. 初始化 submodule，切换到指定 tag，并 sparse-checkout 只取 `src/kuavo_humanoid_sdk/*`；
4. 调用 `setup_sdk.sh` 完成安装。

### 收益

- 用户无需自行选择 SDK 版本：配套版本随 LeTools 一起发版；
- 想临时换版本时用本地覆盖，不污染入库的锁文件；
- 自检脚本 `bash scripts/check_environment.sh` 会检查锁文件完整性（`E005`）。

参见 [`../02-环境安装/05-升级与卸载.md`](../02-环境安装/05-升级与卸载.md) 与
[`1.6 SDK 与 LeTools 分层`](01-机器人基础通识.md#16-sdk-与-letools-分层必修)。

## 五、三级运行环境

以上设计都按下面三个档位逐级验证：

| 档位 | 命令 | 能验证 | 不能证明 |
|---|---|---|---|
| **干跑 dry-run** | `--scenario <s> --dry-run --tick-once` | Python import、JSON 结构、节点加载、子树 key | ROS 服务、运动 |
| **仿真 MuJoCo** | 容器内起 `load_kuavo_mujoco_sim_wheel.launch` | ROS/SDK 链路、时序、数据流、部分运动 | 真实安全、负载、视觉与抓取精度 |
| **真机** | `load_kuavo_real_wheel.launch` + 坐标链 + 行为树 | 动力学、负载、精度、安全、稳定性 | — |

建议按「干跑 → 仿真 → 真机」的顺序验证，在上真机前排除配置、导入和数据流问题。
