# 05 开发者调用路径

[返回文档首页](../README.md) · [01-介绍](../01-介绍/) · [02-环境安装](../02-环境安装/)

> 本篇说明写代码时应 import 什么、调用什么：应用代码通过 `adapters` 暴露的 `IHardware` 标准接口调用硬件，
> 不直接使用 `drivers/` 与 SDK。分层规则的完整说明见 [`04-系统架构与分层.md`](04-系统架构与分层.md)。

## 一、标准调用链

```text
你的脚本 / 行为树节点
        ↓  只依赖抽象
core.interfaces.i_hardware.IHardware          ← 契约（不依赖其他层）
        ↓  由工厂创建、构造注入
adapters.hardware.factory.HardwareFactory
        ↓
adapters.hardware.leju_wheeled.hardware.LejuWheeledArmHardware   ← 具体实现
        ↓  适配器内部转换
ROS 话题 / 服务  或  Adapter 内部 SDK 管理服务 → kuavo_humanoid_sdk
        ↓
drivers / 运控 / 真机
```

最小示例（三种控制路径，标准接口推荐）：

```python
from adapters.hardware.factory import HardwareFactory
from core.domain.enums import FrameType, ArmSide
from core.domain.pose import Pose6D

hw = HardwareFactory.create_hardware(config={'robot_type': 'leju_wheeled'})
hw.initialize()

hw.control_head(yaw=30.0, pitch=15.0)                 # 头部（度，默认）
hw.arm_reset()                                        # 手臂归位
hw.send_base_velocity(vx=0.2, vy=0.0, vyaw=0.0)       # 底盘速度

left  = Pose6D(x=0.3, y=0.3,  z=0.8, roll=0, pitch=0, yaw=0)
right = Pose6D(x=0.3, y=-0.3, z=0.8, roll=0, pitch=0, yaw=0)
hw.send_both_ee_poses(left, right, frame=FrameType.WORLD)   # 双臂末端（Pose6D 内部始终弧度）

hw.send_timed_base_pose(x=0.5, y=0.0, yaw=0.0, desire_time=3.0)  # 带时间底盘（TimedCmd）
hw.shutdown()
```

## 二、三条控制路径：怎么选

`LejuWheeledArmHardware` 同时支持三类控制方式。命名规范：SDK 直调方法带 `_sdk` 后缀，TimedCmd 路径带 `_timed` 后缀，
标准接口不带后缀。

| 路径 | 方法特征 | 底层走哪 | 适合场景 |
|---|---|---|---|
| **标准接口** | `send_base_pose`、`control_head`、`arm_reset` | ROS 话题/服务，或封装后的 SDK | **普通应用、Skill、行为树（默认选它）** |
| **SDK 直调** | `control_head_sdk`、`send_base_velocity_sdk` | Adapter 内部 SDK 管理服务 → `kuavo_humanoid_sdk` | 高频控制、力控等对时延敏感的场景 |
| **TimedCmd（Ruckig）** | `send_timed_base_pose`、`*_timed` | `TimedCmdAPI` → ROS 服务，带时间参数 | 时间最优、运动平滑的定点运动 |

选择顺序建议：

1. **能用标准接口就用标准接口**——它最完整、错误信息最友好，也是 `IHardware` 契约定义的部分；
2. 需要更高频、更强实时性时，先用 `*_sdk`；
3. 需要「几秒内平滑到位」时，用 `*_timed`；
4. 三条路径的完整对照与决策表见
   [`../03-接口详细文档/09-控制路径与选型.md`](../03-接口详细文档/09-控制路径与选型.md)。

> **内部实现提示**：标准方法内部可能复用 `_sdk` 或 `_timed` 实现（例如 `control_head` 与 `control_head_sdk`
> 共用一套转换逻辑）。这是适配器内部的事，调用方不需要关心。

## 三、`drivers/` 与 SDK：不直接使用

`drivers/` 层为 `adapters` 提供底层支撑，**开发者无需直接调用**。具体来说：

- **不要**在自己的脚本或 Skill 里 `from kuavo_humanoid_sdk import KuavoRobot`；
- **不要**绕过 `IHardware` 去 import 具体适配器类（这是 E1 类越界，见下）；
- SDK 只应出现在 `adapters` 内部（SDK 管理服务 + 兼容层）。

| 需求 | 该怎么做 | 不该怎么做 |
|---|---|---|
| 让机器人做个动作 | 找 `IHardware` 里已有的方法；没有就先补接口 + 适配器实现 | 直接调 SDK |
| 用 SDK 的某个高级特性 | 在 `adapters` 里加一层封装暴露成标准接口 | 在 Skill / 节点里 import SDK |
| 只想快速验证硬件 | 用 `apps/` 下的示例脚本 | 写个临时脚本直接连 SDK |

绕过 `adapters` 会让上层代码与具体硬件/厂商耦合，换平台或升级 SDK 时改动会扩散到全仓。
`drivers/` 与 SDK 的说明见
[`../03-接口详细文档/07-drivers-与-SDK.md`](../03-接口详细文档/07-drivers-与-SDK.md)。

### 已有的越界：不要照抄

仓库现存 `skills` 对 `adapters` 具体类型的直连（如 `skills/atomic/manipulation/*/skill.py` import
`LejuWheeledArmHardware`），属历史遗留的 **E1** 类越界。**新代码不得再产生同类依赖**，逐条位置与成因见
[`04-系统架构与分层.md`](04-系统架构与分层.md#四已知分层例外e1--e2--e3)。

## 四、`adapters` 以 `.pyc` 分发：对你有什么影响

### 事实

在开源产物中，`adapters/` 下的 `.py` **源码不随包发布**，而是编译为 `.pyc`，放在对应模块所在目录分发；编译时产生的 `__pycache__/` 会被清理。

### 对你的实际影响

| 影响 | 说明 |
|---|---|
| **能正常调用** | `import adapters.hardware...`、调用 `IHardware` 方法都不受影响——Python 会直接加载字节码 |
| **看不到实现源码** | 开源包里不提供 `adapters/**/*.py` 源码 |
| **文档是人工维护的** | 不提供自动生成的 API 文档，接口说明以 [`../03-接口详细文档/03-adapters-硬件适配层.md`](../03-接口详细文档/03-adapters-硬件适配层.md) 为准 |
| **不要改产物里的字节码** | 改了不生效也不受支持；要改行为请改源码并重新走发布流程 |
| **接口契约以 `IHardware` 为准** | 只要 `core/interfaces/i_hardware.py` 的签名不变，`.pyc` 再生成不会破坏你的调用 |

> `.pyc` 分发只影响发布形态，不改变调用方式。你的代码仍然只应依赖 `core.interfaces` 里的抽象；
> 接口层单独放在不依赖其他层的 `core` 中，也是为了让调用方不受适配器实现形态的影响。

## 五、常见错误对照

| 症状 | 原因 | 正确做法 |
|---|---|---|
| `ModuleNotFoundError: kuavo_humanoid_sdk` | SDK 没装或解释器不对 | 跑 `scripts/install_sdk.sh`；确认 `python3` 指向系统 ROS Python |
| `ImportError: 具体适配器类` | 在产品包里想 import 源码 | 应改为通过 `IHardware` 调用；适配器源码不随开源包提供 |
| 想改适配器行为却改不动 | 拿到的是 `.pyc` 产物 | 到源码仓库改，走发布流程 |
| Skill 里 import 了 `adapters...hardware` | E1 类越界 | 改为依赖注入的 `IHardware` |
| 硬编码了某个后端（jiateng / jibot） | 绕过导航后端路由 | 走标准导航接口，由 `navigation_chassis_backend` 路由 |
