# 04 文档贡献规范

本篇是 LeTools 公开文档的写作规则：文档放在哪、能写什么、正文怎么写、改完怎么核对。它只管 `docs/` 下的公开文档；内部文档的维护要求不在此重复。

## 一、按读者决定放在哪

文档放哪里由「谁读它」决定，不由内容类型决定。

| 目录 | 读者 | 随开源产物发布 |
|---|---|---|
| `docs/` | 外部用户 | 是 |
| 内部目录（名称以 `_internal` 结尾） | 内部员工 | 否 |

判断顺序是先问这篇给谁看，再问它讲什么。外部用户需要的内容写进 `docs/`；只对内部员工有意义的流程、权限与基础设施说明留在内部目录，不搬进 `docs/`。

## 二、四条硬约束

公开文档受以下四条约束，不接受「这次先例外」的写法。

1. **公开文档不得链接或依赖任何内部目录。** 判定：页面里的 Markdown 链接目标或正文路径引用落在名称以 `_internal` 结尾的目录里，即为不合格。
2. **公开文档不得出现密钥、内网信息、客户信息、内部决策和未公开的商业信息。** 判定：出现令牌、密码、内网地址、客户名称、未公开的排期或定价，以及只在内部会议里形成的结论，即为不合格。
3. **内部文档可以链接公开文档，反向不允许。** 判定：只检查 `docs/` 一侧——它的链接目标落在内部目录里即为不合格；内部文档引用公开页面不受此限。
4. **同一主题只有一个权威页面。** 判定：动笔前先在 `docs/` 里搜同主题的现有页；已有就扩写它，不新建平行页。同一条规则在两篇里各写一遍，即为不合格。

## 三、正文怎么写

**语言**：正文默认中文。代码标识（模块名、类名、函数名、参数名）、命令、配置项和错误码保留英文原样，不翻译，也不改大小写。

**标题层级**：一个文件只有一个 H1，首个标题写成 `# <篇号> <篇名>`，与文件名对应，例如本篇的 `# 04 文档贡献规范`；其下的标题一律从 `##` 起。正文里再出现第二个 H1 即为不合格。

**不要做范围外的批量格式化**：修改一篇文档时只动与本次目的相关的行。整篇重排、表格对齐、全角半角替换会把 diff 淹掉，评审者分不清哪一处是这次真正要改的内容。

**命令与路径**一律用行内代码或围栏代码块包裹，保证能原样复制。

## 四、操作类文档四件齐全

讲「怎么做」的文档（安装、运行、部署、排障）必须写全四件事，缺一件读者就得自己反推。

| 要素 | 要写的内容 | 判定 |
|---|---|---|
| 前置条件 | 依赖、权限、必须先完成的步骤 | 读者不查别处就能判断自己能不能开始 |
| 步骤 | 按顺序编号的可执行命令 | 每条命令都带执行目录或路径基准 |
| 预期结果 | 成功时的输出、状态或可观察现象 | 给出可与实际输出对照的一行样例 |
| 失败处理 | 常见失败现象与对应处置 | 至少覆盖一个已知失败，不是「有问题再查」 |

**命令要可复现，并写清路径基准**：说明命令在哪个目录执行，例如「以下命令都在仓库根目录执行」。一篇文档里出现三处及以上以顶层目录（如 `apps/`、`scripts/`、`docs/`）起头的命令时，必须写明路径基准，否则 `tests/test_docs_path_baseline.py` 会把它判为不合格。

写法可对照 [安装步骤](../02-环境安装/03-安装步骤.md)，那篇把前置条件、步骤与验证输出分开写。

## 五、文档与代码同步

同步义务按文档类型区分：

| 文档类型 | 更新时机 |
|---|---|
| 契约文档（接口签名、数据结构、配置项、节点清单）与用户可见行为说明 | 与代码在同一个合并请求里更新，不允许先合代码再补文档 |
| 其他历史文档 | 增量迁移：改到哪篇就把哪篇迁到位，不做全库搬家 |

增量原则有四个例外，发现即改，不等到「顺手改到那篇」：**公开边界**（不该公开的内容出现在公开页）、**敏感信息**（密钥、内网地址、客户数据）、**危险指令**（可能造成设备损坏或人身风险的操作）、**错误契约**（与代码实际行为不符的接口说明）。

契约事实以代码为准。节点清单里的能力与参数，改代码时必须同批改文档，读者按文档调用失败属于文档缺陷。

## 六、决策与调研记录

写进仓库的决策与调研结论，用四个状态词标注，放在文首或元信息区，一条记录同一时间只有一个状态：

| 状态 | 含义 |
|---|---|
| `draft` | 起草中，结论还可能变 |
| `accepted` | 已采纳，当前有效 |
| `deprecated` | 仍可查，但不建议再按它做新决定 |
| `superseded` | 已被更新的记录取代，需写明取代它的是哪一条 |

状态变了要改标注，不能只改正文。被取代的记录保留原文，标注 `superseded` 并指向前一条，读者才能看清当时为什么这样定、后来又为什么改。

## 七、写完怎么自检

提交前按本章《测试与质量检查》里的文档检查命令跑一遍，再回头逐条核对本篇的四条硬约束和正文写法；检查命令与通过判据都在那一篇，本篇不重复。
