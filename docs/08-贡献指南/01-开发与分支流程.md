# 01 开发与分支流程

一个改动从切分支到合入，走的是「从 `dev` 切出 → 在功能分支上改 → 提合并请求合回 `dev`」这条链路。本篇只讲分支怎么建、怎么命名、什么时候不能动；提交信息怎么写、合并请求要填哪些内容，另有一篇专门讲，这里不重复。

## 一、三条分支的分工

| 分支 | 定位 | 贡献者怎么参与 |
|---|---|---|
| `dev` | 集成分支，所有改动先合到这里，也是仓库远端的默认分支 | 从它切出功能分支，再通过合并请求合回它 |
| `master` | 发布线，由维护者维护，内容来自已经在 `dev` 上验证过的提交 | 不面向贡献者：不改它、不对它提合并请求、不推送它 |
| 功能分支 | 一次改动的独立工作区 | 自己创建、自己提交，合并后自己删 |

仓库远端的默认分支是 `dev`，正常克隆下来就停在 `dev` 上。`master` 的推进由维护者负责，贡献者不需要为它做任何事。

## 二、切分支前先对齐 HEAD

功能分支必须从 `dev` 的最新提交切出。顺序固定为「先同步、再切」：从本地旧 `dev` 上切出的分支带着过期提交，合并时会混进与本次改动无关的差异。

以下命令都在仓库根目录执行：

```bash
git fetch origin
git checkout dev
git pull --ff-only
git checkout -b <名字>/<type>/<主题>
```

`git pull --ff-only` 在本地 `dev` 与远端分叉时直接报错，不会替你造一个合并提交。报错说明本地 `dev` 上有远端没有的提交，先查清它们的来源，不要用 `git reset` 或强制拉取绕过。

## 三、分支命名：三段式

分支名统一写成 `<名字>/<type>/<主题>`，全部小写，三段之间用 `/` 分隔：

| 段 | 内容 | 例 |
|---|---|---|
| 名字 | 你的固定前缀，同一个人始终用同一个 | `lin` |
| type | 这次改动的类型 | `fix` |
| 主题 | 这次改什么，用连字符分词 | `mtbf-seq` |

合起来形如 `lin/fix/mtbf-seq`。三段分别回答「谁」「哪类改动」「改了什么」，从分支列表里就能看出归属和主题。

`type` 取 `feat` / `fix` / `docs` / `test` / `refactor` / `perf` / `ci` / `chore` 之一。这八个取值与提交信息里的 `type` 是同一套，各自含义见讲提交信息的那一篇，不要另起一套缩写。

分支改名或换目标主线之后，之前在这个分支上跑过的验证结论不能直接沿用：分支指向的 HEAD 已经变了，要在当前 HEAD 上重跑，再把新结果写进合并请求。

## 四、一条分支只对应一条目标主线

一条功能分支只通向一条主线，本次改动也只做一件事。

- **目标主线变了**：重新确认当前 HEAD，重跑验证，旧结论作废。不要拿一条分支同时往两条主线提合并请求。
- **范围变大了**：新开一条分支。同一分支上混两件不相关的事，合并请求的标题没法一句话说清，评审也判断不了范围。
- **分支换了持有人**：接手的人同样从当前 HEAD 重新验证，不能直接引用前一个人的结果。

## 五、不能做的动作

- **不直接往 `dev` 或 `master` 推提交。** 这两条是保护分支，改动只能通过合并请求进入。
- **不对共享分支 force push。** 改历史影响的是所有基于该分支工作的人。共享分支既包括 `dev`、`master`，也包括已经推送、已有评审或其他人在看的功能分支。
- **不删别人正在用的分支。**

## 六、合并与清理

合并默认用 squash：功能分支上的多个提交在合并时压成一个提交进入目标分支。这条默认值有两个直接后果：

1. 合并请求的标题和描述要能独立说明这次改动。squash 之后留在目标分支上的只有那一条提交信息，分支上的中间提交读者看不到。
2. 分支上的提交怎么拆分、按什么顺序排，不必精心设计，但也别指望它们替你传达信息。

功能分支归属于创建它的人。合并完成后，远端分支由平台清理，一般不用手工删；本地分支在确认已合并后自己删：

```bash
git branch -d <名字>/<type>/<主题>
```

`git branch -d` 在分支尚未合并时会拒绝删除。它报错说明本地 `dev` 还没拿到合并结果，先同步再删，不要用 `-D` 绕过检查。

合并请求关闭或被合并之前不要删分支：它是请求的来源，删掉请求就作废了。

## 七、接下来读什么

本篇只讲分支，同一章节还有四篇按顺序接在后面：

1. 提交信息与合并请求：标题格式、描述要写清的字段。
2. 测试与质量检查：提交前该跑哪些检查、结果怎么写。
3. 文档贡献规范：改 `docs/` 时要遵守的写作要求。
4. 版本与兼容性：改动影响对外行为时怎么处理。
