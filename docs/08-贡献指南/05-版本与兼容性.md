# 05 版本与兼容性

> 本篇面向要改动 LeTools 的贡献者：版本由什么决定、哪些改动会破坏别人的使用、怎么在合并请求里把这类改动交代清楚。维护者的发版操作不在本篇。
> 文中命令与相对路径都以 LeTools 仓库根目录为路径基准。

## 一、LeTools 与 SDK 的版本对应关系

LeTools 自身没有仓库级版本号（原因见第六节），真正被锁定的是配套的 SDK。权威口径只有一个文件：

`scripts/kuavo_humanoid_sdk_tools/sdk_version.env`

其中承担版本语义的是两个字段：

```bash
grep -n '^SDK_REPO' scripts/kuavo_humanoid_sdk_tools/sdk_version.env
```

```text
26:SDK_REPO_BRANCH="master"
27:SDK_REPO_TAG="1.4.5"
```

两个字段必须同时设置，且 tag 必须是该分支的祖先——脚本不做「尽力而为」的兼容，不配对就直接失败。`scripts/install_sdk.sh` 在安装前会读取锁文件并校验这一点（匹配判断在 `scripts/install_sdk.sh` 第 66 行），所以「改了锁文件但装不上」是能被当场发现的。

查安装后的实际版本，可以对照子模块当前所在 tag：

```bash
git -C drivers/leju/kuavo_humanoid_sdk describe --tags --exact-match
```

有三个地方看起来像版本源，其实不是：

- `SDK_DEFAULT_VERSION` 只是安装标识。`scripts/kuavo_humanoid_sdk_tools/init_config.sh` 第 116 行的注释明确写了它不是版本权威源；`setup_sdk.sh` 只在无法从上游取到版本时拿它兜底。
- `.gitmodules` 里子模块的 `branch` 不决定安装版本，只在执行 `git submodule update --remote` 时用来选更新目标。用这条命令对齐版本，会把子模块带到分支末端而不是锁定的 tag。
- `scripts/kuavo_humanoid_sdk_tools/sdk_config.sh` 可以临时覆盖上面两个字段，但该文件被 `.gitignore` 第 107 行忽略。临时值只能留在本机，不能当作提交内容。

### 依赖变更要写清楚什么

改动依赖时，合并请求里至少要有三项：

1. 改了什么：哪个文件、哪个包、从什么版本到什么版本；
2. 为什么改：哪个功能需要它，或者修了什么问题；
3. 兼容影响：谁会因此被迫升级，旧环境继续用会怎样。

几条仓库里的硬约束：

- 根目录 `requirements.txt` 与 `ci_scripts/requirements.txt` 必须逐字节一致：前者随开源产物交给下游用户，后者是 CI 实际安装的那份，只改一份就会让两边装出不同依赖。守卫 `tests/test_release_consistency.py` 会拦住这种漂移。
- `numpy` 不在两份 `requirements.txt` 里，需要单独约束到 1.x 范围，边界与原因见 [依赖版本清单](../02-环境安装/02-依赖版本清单.md) 第三节。
- 改 `sdk_version.env` 等于改全仓的 SDK 配套版本，属于下面第二节的破坏性变更，要按那一节的要求标注并给出验证方式。

## 二、什么算破坏性变更

判断标准只有一条：别人按旧的文档或旧代码写好的用法，升级后还成不成立。下面这些改动一旦删字段、改语义或改默认值，都算破坏性变更。

| 类别 | 具体指什么 | 在仓库里的位置 |
|---|---|---|
| 公共接口签名 | `IHardware` / `ISkill` / `ICamera` / `IPerception` 的方法名、参数名、参数默认值、返回类型 | `core/interfaces/` |
| 配置项 | `config/` 下 yaml 的键名、取值枚举、必填性，例如 `camera.enable_head`、`camera.color_fps` | `config/` |
| 节点清单条目 | 节点类名，以及 `params` 里的键名与默认值 | `orchestration/nodes/`、[节点清单](../03-接口详细文档/11-节点清单.md) |
| 行为树契约 | 场景 JSON 里节点 `name`、`params` 的写法与 `board.json` 的键 | `orchestration/scenarios/<场景名>/py_tree.json` |
| 数据格式 | 既有场景 JSON、`board.json`、用户手上配置文件的格式变更 | 同上 |

「改默认值」容易被当成小事：调用方不传这个参数，行为却在升级后变了，排查成本比删参数还高。

这类改动通常先撞上仓库里的守卫，再到评审：

- `tests/test_hardware_contract.py` 要求适配器实现与 `IHardware` 的签名一致，参数名和默认值都要对上；
- `tests/test_docs_code_sync.py` 要求节点清单条目与 `@define_manifest` 注册的类双向相等，技能总表与 `skills/atomic/refactored_sdk/` 下的文件双向相等。删了一个节点却没动清单，或者新增了节点却没进清单，两个方向都会报出来。

守卫只覆盖它能机械判定的部分，判断「这算不算语义变更」仍然是人的事。合并请求里要把破坏性改动显著标出来，并给出迁移方式：旧写法对应哪个新写法、旧配置要改哪几行、有没有过渡期。

## 三、兼容性承诺的边界

下面这些改动按向后兼容处理，不需要走破坏性变更的流程：

- 给公共方法或技能参数增加带默认值的可选参数，不传时行为与原来一致；
- 新增技能；新增节点并同步补进节点清单；
- 新增配置项且有默认值，旧配置文件不写这一项也能跑；
- 修正内部实现，公共行为不变。

下面这些不承诺兼容，改动前不必为它们保留旧形态：

- 下划线开头的私有函数与属性；
- 未被文档化的实现细节，例如日志文本、内部数据结构、临时文件命名；
- 只在内部使用的模块与其导入路径。

边界怎么划：如果一用法能从 `docs/` 和节点清单里查到，它就是公共面；查不到的，改动方自己承担。仓库不维护仓库级版本号，「某个版本以后仍然兼容」这种跨版本承诺没有依据，以文档写明的公共面为准。

## 四、风险等级联动

改动按低、中、高三档定级，取三者中的最高值，定级规则见本章《提交信息与合并请求》。其中两类直接按最高档处理：

- 破坏性变更；
- 机器人控制相关的改动，包括运动指令、伺服、急停与安全参数。

最高档意味着合并请求里要写清验证命令、真实结果和没有覆盖到的范围；涉及真机的改动，要说明是在仿真还是实机上验证的。

## 五、废弃方式

不要直接删。先标注废弃并给出替代路径，到期再删。

仓库里现成的写法是 docstring 里的 `.. deprecated::` 段，写完要让读者知道三件事：为什么废弃、替代是什么、旧调用还能用多久。两个真实例子：

- `adapters/hardware/leju_wheeled/mixins/sdk_control_mixin.py` 第 524 行的 `robot_sdk` 属性：越过 `IHardware` 契约直连 SDK，替代是 `get_arm_joint_positions` / `solve_ik` / `get_transform`，原文写明「本属性只为存量调用保留，不移除」。
- `adapters/hardware/leju_wheeled/mixins/mode_service_mixin.py` 第 17 行的 `set_mpc_mode`：在当前固件下没有实际控制效果，原文说明了实际控制行为该由什么决定。

删掉已标注废弃的东西是单独一次改动，删的时候同样按破坏性变更处理。

决策类文档（架构选择、弃用决定这类）用 `draft` / `accepted` / `deprecated` / `superseded` 四态标注。状态变了要改标注本身，不能只在正文里追加一句说明——只改正文，标注就会和结论对不上。

## 六、版本变化在哪里看

仓库不维护根 `CHANGELOG.md`，也没有仓库级版本号：根目录不存在这个文件，`git tag` 为空。`__version__` 也不只一处，用 `grep -rn --include=*.py -E '^__version__[[:space:]]*=' .` 实测：未检出 `drivers/leju/kuavo_humanoid_sdk/` 子模块时命中 5 处，检出该子模块后命中 9 处，多出的 4 处都在子模块内，分属三份 `python-can 3.3.4` 打包副本和 `nio-isaac`。命中全部落在适配器、随仓携带的第三方或内部代码里，例如 `adapters/vacuum_control/__init__.py` 第 10 行的适配器版本、`third_party/basket_vision/basket_gdrnpp/lib/pysixd/transform.py` 第 200 行的 pysixd 版本。这些都不是 LeTools 自身的版本号。

所以版本以 commit 为准。要记录或复现某个状态，直接取 commit：

```bash
git rev-parse HEAD
git log --oneline -20
```

想知道 SDK 配套版本是怎么变过来的，查锁文件的提交历史：

```bash
git log --oneline -- scripts/kuavo_humanoid_sdk_tools/sdk_version.env
```

提问题时也一样：反馈模板里有一项「LeTools 分支与 commit」，见 [开闭源与文档](../06-常见问题FAQ/07-开闭源与文档.md) 第四节。只写「最新版」无法定位。
