# 02 提交信息与合并请求

一次改动进入仓库要过三关：本地写出合格的 commit、推送前跑完自检、在合并请求里把改动说清楚。本篇按这个顺序说明三关各自的要求。GitLab 上叫 MR（Merge Request），GitHub、GitCode 上叫 PR（Pull Request），本文统一用 MR。

文中命令默认在仓库根目录执行。

## 一、提交信息格式

标题一行，需要时再加正文：

```text
<type>(<scope>): <description>

<可选正文>
```

- `<type>` 必填，小写，从第二节的八类里选。
- `(<scope>)` 可选，小写，写受影响的模块，取法见第三节。
- `<description>` 必填，冒号后只留一个空格，一句话说清改了什么。不要写「update」「fix bug」这类看不出内容的描述。
- 正文与标题之间空一行，用来交代现象、修法和验证方式。改动原因不显然时再写，不必为凑格式强行补。
- 标题里可以不写 issue 单号，关联关系填在 MR 的「关联 issue」字段。

## 二、type 的八类取值

| type | 什么时候用它 |
|---|---|
| `feat` | 新增用户能感知的功能或能力 |
| `fix` | 修复缺陷，让不符合预期的行为恢复正常 |
| `docs` | 只改文档，不改变代码行为 |
| `test` | 只增改测试用例或测试辅助代码 |
| `refactor` | 重构，代码结构调整而对外行为不变 |
| `perf` | 性能优化，例如减少耗时、内存占用或重复计算 |
| `ci` | 持续集成、构建脚本与流水线配置 |
| `chore` | 杂项维护，例如依赖、脚本、配置文件的常规更新 |

不要自造第九类。需要表达行为调整，用 `fix` 或 `refactor`；纯配置或依赖变动，用 `chore`。历史提交不必回头改写。

## 三、scope 怎么取

scope 取受影响的模块目录名，小写。常用取值：

```text
core  drivers  adapters  skills  orchestration  apps
```

一次改动跨多个模块时用逗号分隔：

```text
fix(pallet_detect,pallet_servo): 探针落在画布外一律跳过
```

改动只局限在某个子目录或某个场景时，写到下一级目录名或场景名，比写整个 `adapters` 更准确。不要用个人名、issue 单号，也不要用 `misc`、`other` 这类无法定位的标签。各目录的职责见[目录结构总览](../01-介绍/06-目录结构总览.md)。

## 四、一个 commit 一个逻辑改动

每个 commit 只做一件事，并且这件事单独看 `git log` 也能读懂。把顺手修的东西塞进同一个 commit，会让 `git bisect` 失准、让评审看不出重点、让回滚变成整段回退。

同一个 commit 里不允许出现：

- 密钥、令牌、密码等任何形式的凭据；
- 运行日志、缓存、构建产物；
- 临时调试代码和 `print()` 调试语句；
- 没有来源说明的大体积二进制文件；
- 遗留的死代码。这次改动自己产生的孤儿（没用的 import、变量、函数）要在同一个 commit 里清掉。

## 五、推送前自检

推送前逐项做完，每项都按实际结果记录：

| 检查 | 怎么做 |
|---|---|
| 提交信息格式 | 人工对照第一、二节。仓库没有提交信息 lint，格式靠评审把关 |
| 相关测试 | `bash scripts/pre_push_tests.sh`。脚本跑 `tests`、`core/common/tests`、`adapters/hardware/leju_wheeled/tests`；改动落在这三处之外时，显式跑对应目录的用例 |
| 文档守卫 | `python3 -m pytest tests/test_docs_links.py tests/test_docs_structure.py tests/test_docs_path_baseline.py tests/test_docs_code_sync.py -q` |
| 空白与冲突标记 | `git diff --check`。它只报行尾空白、空白前制表符和遗留的冲突标记，不检查缩进与行长 |
| 代码格式 | 仓库没有统一的格式化工具，按代码规范人工自查 PEP 8、行长、嵌套层级 |

`scripts/pre_push_tests.sh` 会 import 项目模块。SDK 子模块未检出时，相关用例在收集阶段就会报错，先按[安装步骤](../02-环境安装/03-安装步骤.md)装好 SDK 再跑。

脚本没覆盖到的目录不等于不用测。改了哪一层，就跑哪一层的用例，跑法见[测试与调试](../05-进阶开发指南/07-测试与调试.md)。

结果按实际情况写。没执行、执行失败，就不能在 MR 里写「通过」。当前 HEAD 必须完成与改动风险相称的验证：改了接口却只跑了文档守卫，不算验证过。

## 六、MR 标题与范围

标题格式：

```text
<ISSUE-KEY>: <type>: <一句话说明>
```

示例：`DOCS-154: docs: 落地文档、提交与 MR 冻结规范`。

- `<ISSUE-KEY>` 取关联单号。
- `<type>` 与提交信息用同一套八类取值，不要写成 `feat[doc]` 这类自定义写法。
- 一句话说明写这次改动做了什么，不写「优化」「修复若干问题」这类无法核对的说法。

一个 MR 只做一件事。混进第二件事的改动拆成独立 MR。经验值是约 400 行有效改动，超过先想想能不能拆；但这是拆分提示，不是机械行数上限，跨文件的一致性修正本来就该一起合。

MR 标题和 commit 标题是两套格式，不要混用：前者带 issue 单号，后者不带。

## 七、MR 模板字段与填写口径

仓库的默认 MR 模板会在新建 MR 时自动带入，字段与填写要求如下。模板文件本身不随开源产物发布，字段口径以本篇为准。

| 字段 | 填写要求 |
|---|---|
| 关联 issue | 关联单号；确实没有单号的改动，写明来源 |
| 目的 | 这次改动解决什么问题，一到两句 |
| 方案与不包含范围 | 怎么做，以及明确不做什么。不写清边界，评审没法判断范围是否失控 |
| 目标主线与合并路径 | 目标主线是哪条，从哪条分支切出、合到哪里 |
| 风险等级及理由 | 低、中、高，附一句理由，规则见第八节 |
| 接口、配置、部署、安全影响 | 四类逐项写。无影响写 `N/A` 加原因，不留空 |
| 验证命令、结果与未覆盖范围 | 只写实际执行过的命令与真实输出；没跑的用例、没验证的环境必须列出来 |
| 文档同步 | 同 MR 更新了哪篇契约文档或行为说明；没涉及写 `N/A` 加原因 |
| 版本记录与用户可见变化 | 用户能感知的变化摘要 |
| 回滚 | 怎么回退，回退后要在当前 HEAD 上重新验证什么 |
| 依赖变更硬约束 | 模板顶部的固定提示，内容见第九节 |
| 自查清单 | 代码质量、错误处理与日志、测试、文档四段，逐项勾选 |

模板里还有一段「其他说明」，用于记录已知问题、后续计划或需要评审特别注意的地方，按需填写。

低风险项可以写 `N/A` 加原因，但不能留空。空字段和「评估过、确认无影响」是两回事，评审看到空字段只能理解成没评估。

## 八、风险等级

风险分低、中、高三档，由作者初判，并在 MR 里写一句理由。以下任一项命中，一律按高风险处理：

- 公共接口：`core` 对外数据结构、`adapters` 公开方法、技能与节点签名；
- 状态机与并发：行为树状态迁移、多线程或异步路径；
- 权限与鉴权；
- 数据迁移：既有配置、场景 JSON、持久化数据的格式变更；
- 机器人控制路径：运动指令、伺服、急停、安全参数；
- 安全边界与危险操作文档。

高风险不等于不能合，但要求更严的验证证据：验证命令、真实结果和未覆盖范围都要写全；涉及真机的，写清是在仿真还是实机验证。

判不了等级时往上取，不要往低走。影响面看不清的按高风险处理，并把还不确定的点写进 MR。

## 九、依赖变更

不要直接修改根目录的 `requirements.txt`。新增或升级依赖，在 MR 描述里写明「包名 + 版本约束」，由维护者写入受保护的依赖清单。

只接受这几种写法：`包名`、`包名==版本`、`包名>=x,<y`、`包名[extras]`。

下列写法会被拒绝：`-e`、`-r`、URL、`git+…`、本地路径、`--index-url`。它们能让 pip 在构建期执行任意代码，或者把安装源换到别处，所以依赖只能来自受审查的清单。

## 十、合并、回滚与分支清理

合并由维护者评审后执行。合并前，CI 的自动化检查要通过，分支与目标主线没有冲突，也没有未解决的阻塞意见。

默认使用 squash 合并。squash 后的主提交信息由 MR 标题与描述决定，要能独立读懂。

合并后由平台清理源分支，不手工删远端分支。

发现问题需要回滚时，优先用 revert 提交回退，不要 force push 改历史。回退后要在当前 HEAD 上重新跑验证，不能假定回到之前的状态就没问题。
