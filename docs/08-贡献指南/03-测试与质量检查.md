# 03 测试与质量检查

改完代码要能自证：没有弄坏既有行为，也没有绕过应当遵守的约束。这篇给出三层验证的分工，以及贡献者自己要跑的那些命令。下文命令的路径基准都是仓库根目录，即包含 `pytest.ini` 的那一级目录，在子目录里执行命令前请先回到那里。

## 一、三层验证的关系

| 层次 | 谁执行 | 做什么 | 结果怎么记录 |
|---|---|---|---|
| 本地推送前门禁 | 贡献者 | 跑门禁脚本，按改动范围补跑文档守卫 | 门禁不过就不要提 MR |
| 提交后复核 | 维护者 | 读 diff、复跑守卫、核对文档与代码 | 由维护者在 MR 里给结论 |
| 仿真 / 实机验证 | 有环境的人 | 在 MuJoCo 或真机上跑通受影响场景 | 没做就写「未在仿真/实机验证」 |

三层不能互相替代。本地全绿只说明这台机器、这套环境里选中的用例通过；仿真通过也只说明仿真里的行为符合预期，和实机安全是两件事。

## 二、推送前门禁

```bash
bash scripts/pre_push_tests.sh
```

脚本先用 `git rev-parse --show-toplevel` 定位仓库根并 `cd` 过去，所以在哪个子目录执行都等价。之后的行为按顺序是：

1. 找不到 `python3`：向 stderr 打印 `pre-push: 找不到 python3，跳过单测门禁`，退出码 0（跳过，不算失败）。
2. 仓库根没有 `pytest.ini`：直接退出码 0，不打印任何提示。
3. 否则执行 `python3 -m pytest tests core/common/tests adapters/hardware/leju_wheeled/tests -q`。注意只跑这三个目录，`pytest.ini` 的 `testpaths` 里还有第四个 `adapters/hardware/leju_wheeled/services/sdk_manager/tests`，门禁脚本没有带上它。
4. 全绿退出 0；有任何失败退出 1，并打印 `pre-push: 单测不过，推送已中止（--no-verify 可跳过，CI 仍会拦）。`

适配器目录的用例在模块顶层 import 适配器，适配器包会连带 `import rospy`，没有 ROS 的开发机上会在收集阶段直接报错，门禁以退出码 1 结束。实测缺 `rospy`、`tf`、`message_filters` 时是 4 个文件收集失败（`Interrupted: 4 errors during collection`），这属于环境缺失，不是你这次改动引入的失败。先按 [03-安装步骤](../02-环境安装/03-安装步骤.md) 补齐环境；只想验文档改动时，用第三节的 `python3 -m pytest tests -q` 就够，不必走整条门禁。

## 三、直接跑测试与标记语义

```bash
python3 -m pytest tests -q
```

只收集 `tests/` 下的用例，不依赖 ROS，秒级完成。当前仓库实测输出 `37 passed, 2 skipped`，两个跳过都来自环境缺失：契约测试需要 ROS，SDK 版本一致性用例需要检出子模块。跳过不等于通过，MR 里描述结果时请原样区分。

不带路径直接跑 `python3 -m pytest` 会按 `pytest.ini` 的 `testpaths` 收集全部四个目录，其中适配器相关用例同样要求 ROS 环境。

`pytest.ini` 登记了三个标记：

| 标记 | 语义 | 什么时候跑 |
|---|---|---|
| `unit` | 单元测试，不需要实机 | 随时 |
| `integration` | 集成测试，需要仿真或实机 | 有环境时；没有环境不要跑，也不要把「没跑」写成「通过」 |
| `slow` | 慢速测试，耗时较长 | 默认会被选中；只想快速过一遍时用 `-m "not slow"` 排除 |

`--strict-markers` 已开启，用了没在 `pytest.ini` 里登记的标记会直接报错。

没有环境时想看某个标记会选中哪些用例，用 `--collect-only`，它只收集不执行：

```bash
python3 -m pytest tests -m integration --collect-only -q
```

## 四、文档守卫四件套

文档改动和代码改动一样要过守卫。四个文件都在 `tests/` 下，纯文件系统扫描，不拉起 ROS。

| 文件 | 守什么 |
|---|---|
| `tests/test_docs_links.py` | 链接可达性与篇目数：相对链接的目标文件必须存在（外链、纯页内锚点、绝对路径除外）；跨文件的 `#锚点` 必须命中目标文件的标题；带空格的链接目标必须写成 `<路径>` 或把空格转成 `%20`；01 至 08 各章的顶层篇目数等于配置值，首页存在 |
| `tests/test_docs_structure.py` | 目录结构：8 个章节目录都存在且集合与预期一致，首页 `docs/README.md` 存在且非空，另有几条防回归断言（ADR 目录不再入库、旧素材目录已移除、`docs/` 下不放 `.sh` / `.py` 脚本） |
| `tests/test_docs_path_baseline.py` | 路径基准：同一篇文档里出现 3 处及以上「以裸顶层目录开头的命令」却没有写明相对谁、在哪执行，判失败；写明「仓库根目录」这类基准即豁免 |
| `tests/test_docs_code_sync.py` | 文档与代码的一致性：E1 例外的文件数等于实测值、节点清单与 `@define_manifest` 注册的类双向相等、技能总表与 `skills/atomic/refactored_sdk/` 下的文件双向相等、行内编号交叉引用指向真实篇目、正文不出现裸 `<JSON>`、契约覆盖率分母的扫描范围没有被悄悄改动 |

一次跑完四件套：

```bash
python3 -m pytest tests/test_docs_links.py tests/test_docs_structure.py tests/test_docs_path_baseline.py tests/test_docs_code_sync.py -q
```

当前仓库实测 `36 passed`。守卫只检查形态与集合，不判断正文说得对不对：全绿不等于文档与代码已经同步，语义仍需人读。

## 五、提交前的机械检查

```bash
git diff --check
git status --short
```

`git diff --check` 报行尾空格、Tab 与空格混用这类空白错误，没有输出且退出码为 0 才算干净。`git status --short` 里应当只有你打算提交的文件，缓存、日志、临时文件不该出现；出现了先清理再提交。

有一处仓库现状需要留意：`.pytest_cache/` 目前是被跟踪的，跑过 pytest 之后 `git status --short` 会显示它被修改。那不是你的改动，别把它一并提交，也别为了「让工作区干净」去删它。

## 六、区分既有失败与新增失败

只看最后一次运行结果分不清哪些是本此改动引入的。做法是把同样的命令在基线 HEAD 上先跑一遍留档，再在改动后跑一遍，对比失败清单：

1. 动手前，在当前 HEAD 上跑要用的命令并把输出存到文件，例如 `python3 -m pytest tests -q > before.log 2>&1`。`*.log` 已在 `.gitignore` 内，不会误提交。
2. 改完后再跑同一命令，存成 `after.log`。
3. 对比两份失败用例名。只出现在 `after.log` 里的才归本次改动，两边都有的属于既有失败。
4. MR 里只声明「本次没有新增失败」，并附上两份失败清单。不要把既有失败写成通过，也不要用「全部通过」概括一次带既有失败的运行。

## 七、安全红线

- 不要为了让测试通过去执行真机运动入口。已知的禁止入口有 `arm_ee_timed_cmd`、`qiangnao_hand_control`、`arm_ee_traj_*` 三个，这不是完整清单，同类入口一律按禁区处理。
- 不跑 `integration` / `slow` 标记的用例，也不为了「跑通」去启动仿真环境。
- 仿真通过不等于实机验证。真机验证只由具备安全条件的人执行，贡献者在 MR 里如实写「未做」即可。
