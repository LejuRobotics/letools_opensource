# 04 预期输出

**难度**：⭐

**适合读者**：跑完命令、想确认「我这样算成功吗」的人。

**前置知识**：读过 [02-执行命令](02-执行命令.md)。

**学习目标**：三种运行方式各自的成功输出、退出码含义，以及「成功了但其实不对」的识别办法。

---

## 一、成功判据：dry-run 与仿真 / 真机不同

`apps/test_upper_init/run_behavior_tree_json.py` 和 `orchestration/main.py` 在两种运行方式下的判据不同：

| 运行方式 | 怎么判断成功 | 退出码的含义 |
|---|---|---|
| dry-run（`--dry-run --tick-once`） | 输出中的 `tick 后根状态: Status.SUCCESS` | 加载失败（导入错误、JSON 错误、节点名错误等）时为非 0；**加载成功后总是 0，不反映 tick 结果** |
| 仿真 / 真机（不加 `--dry-run`） | 退出码为 `0`，且日志中没有 `ERROR` / `FATAL` | 按根节点最终状态：`SUCCESS`=0、`FAILURE`=1、其它（未达终态或收尾异常）=2 |

因此 dry-run 时不能只看退出码：即使根节点 tick 后为 `FAILURE` 或 `RUNNING`，进程仍以 0 退出。

```bash
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/studio_smoke_v1 --dry-run --tick-once
# 判据：输出包含 tick 后根状态: Status.SUCCESS
```

## 二、成功输出长什么样

### 2.1 干跑（`--dry-run`）

已实测的 `studio_smoke_v1` 输出（截取 `[apps]` 前缀的行）：

```text
[apps] 启动参数
  - workdir: /path/to/LeTools
  - tree: .../studio_smoke_v1/py_tree.json
  - subtrees: .../studio_smoke_v1/py_tree_child.json
  - board: .../studio_smoke_v1/board.json
  - hardware config: .../studio_smoke_v1/hardware_config.json
[apps] 子树集合已加载：.../studio_smoke_v1/py_tree_child.json (count=0)
[apps][dry-run] 已加载树，根节点: studio_smoke_seq
[apps][dry-run] tick 后根状态: Status.SUCCESS
```

要点：

- `已加载树，根节点: <label>` —— 树的 label 正确，说明 JSON 解析 + 节点构造走通。
- `子树集合已加载… (count=N)` —— N 是该场景 `py_tree_child.json` 里的子树个数。`studio_smoke_v1` 是 0（无子树）。
- 只有加了 `--tick-once` 才会打印 `tick 后根状态`；只 `--dry-run` 不 tick 时看不到这一行。
- `- hardware config: ...` 这一行**即使文件不存在也会打印路径**（打印的是「将要用的路径」，不是「已加载」）。

其它场景已实测的 `count` 与根节点名：

| 场景 | 子树 count | 根节点 label |
|------|-----------|--------------|
| `studio_smoke_v1` | 0 | `studio_smoke_seq` |
| `jibot_nav_v1_sim` | 1 | `jibot_nav_v1_sim_seq` |
| `refactored_sdk_atomic_v1` | 3 | `refactored_sdk_atomic_v1_seq` |
| `grasp_mtbf` | 2 | `mtbf` |

### 2.2 真机 / 仿真（去掉 `--dry-run`）

ROS 模式下程序还会：

- 打印 `[apps] 硬件预热完成: <硬件类名>`；
- 每拍经 `py_trees` 走到根节点；
- 结束时按最终状态 `sys.exit(0/1/2)`；
- 若根节点 `FAILURE`，额外打印一行失败原因：`[apps] 行为树失败原因: <feedback_message>`。

成功判据是**退出码 0** + 日志里**没有 `ERROR` / `FATAL`**。

## 三、失败的输出形态

| 现象 | 说明 |
|------|------|
| 退出码 `1`（仿真 / 真机） | 树跑到 `FAILURE`。看 `[apps] 行为树失败原因:` 指向哪个节点 |
| 退出码 `2`（仿真 / 真机） | 未达终态（如中途异常、节点一直 `RUNNING` 不收敛） |
| dry-run 输出 `tick 后根状态: Status.FAILURE` | 某个节点在干跑下返回失败（例如需要的黑板键缺失）；此时退出码仍为 0 |
| 打印 traceback + 非 0 | 加载/导入阶段就崩了，最末一行是异常类型 |
| `RuntimeError: 主树 py_tree.json 不存在: <路径>` | `--scenario` 或 `--tree` 路径错 |
| `RuntimeError: dry-run 加载失败：root 不存在` | 树构建失败，多为类名/子树 key 拼错 |
| `ModuleNotFoundError: No module named 'X'` | 缺依赖或 `PYTHONPATH` 没设（见 [05-常见错误](05-常见错误.md)） |

## 四、「看起来成功、其实不对」

干跑有个天然局限：**运动节点与 `WaitForEnter` 在干跑下直接返回 `SUCCESS`**，所以「干跑 SUCCESS」只证明**能加载**，不证明**动作正确**。

典型陷阱：

- **假成功**：SDK 初始化失败时，头部动作会打 `ERROR` 但返回 `True`；日志里没有 `SDK 未初始化，请先调用 initialize()` 这类 ERROR，反而更容易误判。**必须同时看退出码和日志级别**。
- **到位不校验**：部分底盘控制是「按预计时间盲等」，不校验是否真的到位。判断机器人是否走到位，**仿真里靠肉眼看 MuJoCo 窗口**，不能只看日志的「完成」。

「假成功」的识别方法见 [06](06-头部顺序动作-instructional_case_01.md) 第六节；「到位不校验」的例子见 [09](09-头手躯干与底盘并行-instructional_case_04.md) 第三节的时间窗口说明。
