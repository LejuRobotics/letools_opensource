# 03 行为树最小示例

[返回文档首页](../README.md) · [04-简单案例运行](../04-简单案例运行/) · [03-接口详细文档](../03-接口详细文档/)

**难度**：⭐（跑通）→ ⭐⭐（改参数看现象）

**适合读者**：跑通了 [01-最小可运行示例](01-最小可运行示例.md)，想动手改一个参数、并且**亲眼看到现象变化**的人。

**前置知识**：知道行为树由「节点 + 参数」构成即可；ROS 知识不是必需（本例可纯干跑）。

**核心概念**：一个节点的行为由它的 `params` 决定；改 `params` 里的 `value` → 现象变化 → 参数生效方式（重启树 / 重启进程）各不相同。

**学习目标**：

1. 用 **`MoveHead` 节点**搭一棵只有一个节点的最小树并跑起来；
2. 修改 `MoveHead` 的 `yaw_deg` / `pitch_deg`，理解参数「改后会怎样」；
3. 分清四类配置文件（`py_tree.json` / `board.json` / `hardware_config.json` / `config/*.yaml`）分别改什么、怎么生效。

**由简到难进阶路线**：本篇（1 个节点）→ 06–09 篇的四个示教场景（头部顺序动作 → 加入双臂 → 加入躯干 → 加入底盘）→ [10-搬箱场景-grasp_mtbf](10-搬箱场景-grasp_mtbf.md)（主树 17 节点 + 2 子树）。

## 一、为什么选 `MoveHead`

`MoveHead`（`orchestration/nodes/move_head.py`）只有一个动作、参数少、不需要视觉与抓取，是「改一个参数、看一个现象」最合适的节点。

它的三种运行模式正好覆盖三种数据来源：

| `mode` | 头部角度从哪来 | 能否在仿真 / 真机运行 |
|--------|----------------|------------------|
| `smoke` | 节点参数 `yaw_deg` / `pitch_deg`，经 `HeadControlSkill` 调用 `hardware.control_head()` | ✅ 可以，本篇使用此模式 |
| `manual` | 节点参数 `head_search_yaws` / `head_search_pitchs` | ❌ 非干跑时依赖仓库外的 `shared_robot_sdk` 模块，会报 `ModuleNotFoundError` |
| `from_board` | 设计为从黑板读取，但当前实现不读取黑板 | ❌ 同 `manual`，非干跑时报 `ModuleNotFoundError` |

> 仓库现成的 `orchestration/scenarios/` 里没有使用 `MoveHead` 的场景（`MoveHead` 目前只出现在 `orchestration/config/trees/` 的默认树里）。所以本篇带你**自建一个最小场景目录**。

## 二、搭一个单节点最小场景

在仓库根下新建目录 `orchestration/scenarios/move_head_demo/`，放入一个 `py_tree.json`：

```json
{
  "tree": {
    "name": "Sequence",
    "label": "move_head_demo_seq",
    "params": { "memory": { "value": true, "source": "CUSTOM", "data_type": "bool" } },
    "childs": [
      {
        "name": "MoveHead",
        "label": "look_head",
        "params": {
          "mode":      { "value": "smoke", "source": "CUSTOM", "data_type": "string" },
          "yaw_deg":   { "value": 20.0,    "source": "CUSTOM", "data_type": "float" },
          "pitch_deg": { "value": 10.0,    "source": "CUSTOM", "data_type": "float" }
        },
        "childs": [],
        "childBoard": []
      }
    ],
    "childBoard": []
  },
  "interface": { "inputs": [], "outputs": [], "custom": [], "process": [] }
}
```

`name` 用 Python 类名 `MoveHead`，工厂会在 `orchestration/nodes/` 里按类名找到它（`move_head.py`）。`mode=smoke` 时，节点让头部转到 `yaw_deg` / `pitch_deg` 指定的角度（单位：度）。

跑起来：

```bash
cd /path/to/LeTools
export PYTHONPATH=$(pwd):$PYTHONPATH

# 干跑：只验证加载，不连 ROS
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/move_head_demo --dry-run --tick-once
```

预期输出：

```text
[apps][dry-run] 已加载树，根节点: move_head_demo_seq
[apps][dry-run] tick 后根状态: Status.SUCCESS
```

> **验证方式**：看到 `tick 后根状态: Status.SUCCESS` 即表示「节点找到了、参数解析了、树 tick 通了」。dry-run 下进程退出码为 0 只代表树加载成功，不代表 tick 结果，详见 [04-预期输出](04-预期输出.md)。
>
> 因为场景目录里只有 `py_tree.json`，运行时还会打印 `board.json 不存在，跳过` 和 `子树集合文件不存在，忽略` 两条 WARNING，这是正常现象。
>
> 想看到头部**真的动**，需要仿真或真机：按 [02-执行命令 · 运行前环境准备](02-执行命令.md#运行前环境准备仿真与真机共用) 启动控制器和 TF 转发后，去掉 `--dry-run --tick-once` 再运行。

## 三、`MoveHead` 参数表

下表依据 `orchestration/nodes/move_head.py` 的实现整理。本篇只使用 `smoke` 模式，`manual` / `from_board` 模式在仿真和真机上不可用（见第一节）。

| 参数 | 默认值 | 说明 | **改后现象** |
|------|--------|------|--------------|
| `mode` | `manual` | `smoke` / `manual` / `from_board` | 本篇固定为 `smoke`；不写时默认 `manual`，干跑能通过，但仿真 / 真机会报 `ModuleNotFoundError` |
| `yaw_deg` | `11.5` | `smoke` 模式的偏航角（度） | 改为 `30` → 头部向左转到 30°。SDK 限位为 ±80°，超出时打印警告并截断到限位，不会报错 |
| `pitch_deg` | `5.7` | `smoke` 模式的俯仰角（度） | 改为 `-10` → 头部转到 −10°。SDK 限位为 ±25°，超出时打印警告并截断到限位 |
| `head_search_yaws` / `head_search_pitchs` | `""` | 仅 `manual` 模式使用 | `smoke` 模式下不生效 |
| `head_event_timeout` | `20000` | 仅 `manual` / `from_board` 模式使用，原样传给 SDK 的 `EventHeadMoveKeyPoint`（SDK 按**秒**处理） | `smoke` 模式下不生效 |
| `count` | `0` | 当前实现不使用 | 改它无现象 |

**几个容易踩的点**：

- `yaw_deg` / `pitch_deg` **只在 `smoke` 模式生效**。
- 角度单位是度；适配器内部转换为弧度后下发。
- 干跑不会调用硬件，任何角度都会返回 `SUCCESS`；限位截断只在仿真 / 真机上发生，可在 SDK 日志中看到警告。

> 头部动作与其它控制路径的对照（标准接口 / SDK 直调 / TimedCmd），见
> [`../03-接口详细文档/09-控制路径与选型.md`](../03-接口详细文档/09-控制路径与选型.md)。

## 四、配置文件参数修改

四类文件各管一段，改错文件是「改了没反应」的头号原因。

### 4.1 `py_tree.json` —— 任务顺序与节点参数

- **改什么**：某个节点 `params` 里某项的 `value`（如上面的 `yaw_deg`）。
- **取值范围**：依节点而定，看该节点 `@define_manifest` 的声明（`options` 字段给出枚举）。
- **生效方式**：**重启行为树**（重新执行启动命令）。树在启动时一次性构建，运行中改文件不会热更。
- **常见报错**：`value` 的类型与 `data_type` 不符 → JSON 在加载/参数解析阶段报校验失败；节点 `name` 拼错 → `节点索引` 里找不到该类，报节点构造失败。

### 4.2 `board.json` —— 黑板初始值

- **改什么**：黑板键的初始值。例如 `studio_smoke_v1` 的 `ArmJointTrajectories`（手臂关节轨迹 `times` / `q_frames`），或单 tag 抓取场景的 `gripper_position`。
- **取值范围**：依键而定。键名必须是节点实际会读的那个（`READ_BOARD` 的 `board_key`，或节点 `inputs` 声明的 `default_key`）。
- **生效方式**：**启动时加载**一次，写进全局黑板；运行中改文件不生效。
- **常见报错**：**键名拼错不会报错**——节点读不到就回退到代码里的默认值，表现为「改了 board 却像没改」。这是最隐蔽的一类问题。

### 4.3 `hardware_config.json` —— 场景级硬件覆盖

- **改什么**：
  - `sdk_managers_whitelist`：字符串数组，只初始化列出的 SDK 管理器（如 `["timed"]` / `["arm","low"]`）；
  - `skip_camera` / `skip_end_effector` / `skip_state_manager` / `skip_force_publishers`：布尔，跳过对应硬件子系统的初始化。
- **取值范围**：布尔，或字符串数组。
- **生效方式**：**重启行为树**。启动器在创建 `IHardware` 之前把它 merge 进硬件工厂配置。
- **常见报错**：**跳过必需项** → 依赖该硬件的节点初始化时找不到硬件，节点报错/`FAILURE`。例如只用 `sdk_managers_whitelist: ["low"]` 时，手臂 SDK 节点会失败。
- **重要**：**并非每个场景都有这个文件**。`studio_smoke_v1`、`jibot_nav_v1`（以及 `dismantle_box` 系列）就没有——缺文件时这一项不是报错，只是没有覆盖。想给它们加覆盖，用 `--hardware-config <你的.json>` 显式传入。

### 4.4 `config/*.yaml` —— 进程级配置

- **改什么**：`config/robot_config.yaml`（机器人名、URDF 路径、关节限位）、`config/camera_config.yaml`（相机开关、分辨率、帧率、RGBD 同步）、`config/app_config.yaml`、`config/log_config.yaml` 等。
- **取值范围**：依字段而定。
- **生效方式**：**重启进程**（不是重启行为树——这些 yaml 由适配层/驱动在初始化时读一次）。
- **常见报错**：**YAML 缩进错误** → 解析失败，进程起不来；相机字段与硬件不匹配 → 相机初始化失败（可先 `skip_camera: true` 绕过）。

## 五、验证方式小结

| 层次 | 命令 | 看到什么算成功 |
|------|------|----------------|
| 加载/语法 | `--dry-run` | 打印根节点名（加载失败时进程以非 0 退出码结束） |
| 单拍 tick | `--dry-run --tick-once` | `tick 后根状态: Status.SUCCESS` |
| 真实动作 | 去掉 `--dry-run`（需仿真或真机） | 头部转到 `yaw_deg` / `pitch_deg` 指定角度；日志无 `ERROR` |
