## 一、两个入口，先分清

仓库里有**两个**能拉起行为树的入口，职责不同：

| 维度 | `apps/test_upper_init/run_behavior_tree_json.py` | `orchestration/main.py` |
|------|--------------------------------------------------|-------------------------|
| 定位 | **通用、场景无关**的 JSON 启动器，推荐新场景用它 | 阶段 1 的默认烟测入口 |
| `--scenario` 自动发现四个文件 | ✅ | ❌（要 `--tree` + `--board`） |
| 默认场景 | 无，**必须** `--scenario` | `orchestration/scenarios/studio_smoke_v1` |
| 子树加载 | 单文件 `py_tree_child.json` | 同左 |
| 干跑 | `--dry-run` | `--dry-run`（等价） |

本章的**场景篇一律用前者**。

---

## 二、`run_behavior_tree_json.py` 参数全集

```text
--scenario <目录>        场景文件夹。给了它就会自动取该目录下的
                         py_tree.json / py_tree_child.json / board.json，
                         并回退使用该目录下的 hardware_config.json
--tree <路径>            主树 py_tree.json 路径（与 --scenario 二选一）
--subtrees <路径>        子树集合 py_tree_child.json 路径（可选）
--board <路径>           黑板 board.json 路径（可选）
--hardware-config <路径> 硬件配置覆盖 JSON（可选）。**优先级高于**
                         scenario/hardware_config.json
--ros-node <名字>        ROS 节点名，默认 behavior_tree_main（仅 ROS 环境生效）
--dry-run                不初始化 ROS，只校验加载/导入
--tick-once              与 --dry-run 合用：只执行一拍
--spin                   树跑完后 rospy.spin，保持 ROS 节点
--parallel-load          启用并行构树（可能触发 Python import 死锁，默认关闭）
--action-groups <列表>   只运行指定动作组，逗号分隔，如 '1,3,5'；不指定则全跑
```

## 三、`orchestration/main.py` 参数

```text
--dry-run       无 ROS/实机：仅验证 import 与加载 studio_smoke_v1
--tick-once     与 --dry-run 合用：执行一次 tick
--tree <路径>   主树路径，默认 orchestration/scenarios/studio_smoke_v1/py_tree.json
--board <路径>  黑板路径，默认该场景的 board.json
--spin          树跑完后保持 ROS 节点（供 stop/pause 服务），默认跑完即退出
```

`main.py` 没有 `--scenario`，也没有 `--hardware-config`。

## 四、三种目标对应的命令

### 只做离线校验（CI / 无硬件）

```bash
cd /path/to/LeTools
export PYTHONPATH=$(pwd):$PYTHONPATH

python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/studio_smoke_v1 \
  --dry-run --tick-once
```

### 运行前环境准备（仿真与真机共用）

dry-run 不需要以下准备；在仿真或真机上运行行为树前，每个新开的**行为树终端**都要完成：

```bash
cd ~/letools_opensource                 # 按实际克隆位置调整
source /opt/ros/noetic/setup.bash
source infrastructure/ros_packages/devel/setup.bash
export PYTHONPATH="$PWD/infrastructure/ros_packages/src/kuavo_common/python:$PWD:$PYTHONPATH"
echo "$ROBOT_VERSION"                   # 必须与目标机器人一致，见 02-环境安装/01-系统要求
rosservice list | grep republish_tfs    # 必须有输出
```

| 检查项 | 为什么需要 | 缺失时的表现 |
|---|---|---|
| `source` ROS 与 LeTools 工作空间 | 提供 `rospy`、`kuavo_msgs` 等消息包 | `No module named 'rospy'` / `kuavo_msgs` |
| `PYTHONPATH` 包含 `kuavo_common/python` | SDK 需要从这里导入 `robot_version` | `ModuleNotFoundError: No module named 'robot_version'` |
| `/republish_tfs` 服务存在 | SDK 初始化时等待该服务 | `SDK 初始化失败`，之后的动作报 `SDK 未初始化` |

`/republish_tfs` 由 TF 转发服务提供：在控制器（仿真或真机）启动**之后**，另开一个终端运行：

```bash
cd ~/letools_opensource/infrastructure/ros_packages
source /opt/ros/noetic/setup.bash
source devel/setup.bash
./start_tf_republisher.sh                # 保持运行，不要关闭
```

因此仿真和真机通常需要 3 个终端：**终端 1** 控制器 → **终端 2** TF 转发 → **终端 3** 行为树。完整示例见 [06-头部顺序动作-instructional_case_01](06-头部顺序动作-instructional_case_01.md) 第五节。

### 仿真（MuJoCo）

先完成上面的「运行前环境准备」，再按顺序启动：

```bash
# 终端 1：仿真
roslaunch humanoid_controllers load_kuavo_mujoco_sim_wheel.launch

# 终端 2：TF 转发（见上文）
./start_tf_republisher.sh

# 终端 3：跑行为树
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/<场景>
```

### 真机

> ⚠️ 真机命令会让机器人实际运动。运行前先完成下面的「真机运行前安全检查」。

下位机走真机 launch，上位机命令与仿真相同：

```bash
# 终端 1：真机控制器（下位机）
roslaunch humanoid_controllers load_kuavo_real_wheel.launch

# 终端 2：确认 TF 转发服务存在（不存在时按上文启动）
rosservice list | grep republish_tfs

# 终端 3：跑行为树
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/<场景>
```

### 真机运行前安全检查

每次在真机上运行行为树或示例脚本前，逐项确认：

1. **物理急停**：急停按钮可随时触达，并已确认按下后机器人能停止；有专人看护，看护人知道急停位置。软件停止（如 `/stop_robot`）不能替代物理急停，区别见 [FAQ 06 第 5 条](../06-常见问题FAQ/06-性能与稳定性.md)。
2. **场地**：机器人底盘移动路径和手臂工作空间内无人员和障碍物，并预留足够的停止距离；仓库中没有经过验收的制动距离数据。
3. **先验证再上真机**：同一场景已通过 dry-run，能仿真的已在 MuJoCo 中跑通。
4. **核对配置**：`ROBOT_VERSION` 与机器人一致；检查场景 `board.json` 中的速度、距离、循环次数（如 `repeat_count`）和避障开关（如 `navigation_config.avoid_enabled`）是否适合当前场地。
5. **不使用虚拟目标**：确认 `use_virtual_tag`、`fallback_to_virtual` 未开启，避免机器人朝配置中的固定位姿移动和抓取。
6. **首次运行降低风险**：首次运行新场景或修改参数后，先降低速度和移动距离，单轮执行，确认动作方向和幅度符合预期后再恢复。
7. **出现异常立即停止**：动作方向与预期相反、关节保护触发、日志出现 `ERROR` 时，先按急停或停止程序，保存日志后再排查，不要直接重试。

### 只跑某几个动作组

```bash
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/<场景> \
  --action-groups 1,3,5
```

## 五、覆盖硬件配置

`--scenario` 会顺带读取该目录下的 `hardware_config.json`（如果存在）。要临时换成另一份配置：

```bash
python3 apps/test_upper_init/run_behavior_tree_json.py \
  --scenario orchestration/scenarios/<场景> \
  --hardware-config /path/to/your_hardware_config.json
```

显式 `--hardware-config` 优先于场景目录里的同名文件。

> 注意：**并非每个场景都有 `hardware_config.json`**（例如 06–09 篇的四个示教场景都没有，直接使用 `config/app_config.yaml` 的全局配置）。缺文件时这一项会自动跳过，不是报错。
