# 08 工具层：脚本与配置

> 本篇是运维与开发者查参数的地方：`scripts/` 下怎么装 SDK、`config/` 里每个 YAML 起什么作用、场景的四类 JSON 各管什么、`tasks/*.yaml` 是不是还在用。

## 08.01 scripts 运维脚本

| 脚本 | 用途 | 关键参数 | 退出码 |
|---|---|---|---|
| `install_sdk.sh` | 从远端按版本锁定清单安装 Kuavo Humanoid SDK（git submodule） | 无命令行参数；读 `scripts/kuavo_humanoid_sdk_tools/` 下的 pin 文件与 `sdk_config.sh` 覆盖 | `0` 成功；`1` 缺 pin 文件 / branch 与 tag 只设一个 / tag 不存在 / tag 不属于该分支 / submodule 有未提交本地修改 / SDK 安装失败 |
| `remove_local_sdk.sh` | 卸载 Python 环境中的 `kuavo-humanoid-sdk`，可选删源码 | `--remove-source`（同时删 `drivers/leju/kuavo_humanoid_sdk`）、`--yes`（跳过确认）、`-h`/`--help` | `0` 成功或用户取消；`1` 路径校验失败；`2` 未知参数 |
| `check_environment.sh` | 环境自检（发行版、依赖、路径等） | `--strict`（把 WARN 也算失败） | `0` 全通过；`1` 有 FAIL；`2` `--strict` 且有 WARN |
| `run_arm_trajectory.sh` | 运行手臂轨迹应用 | 无 | 透传被调脚本 |
| `run_camera_demo.sh` | 运行相机演示应用 | 无 | 透传被调脚本 |
| `run_smt_tray.sh` | 运行 SMT 托盘应用 | 无 | 透传被调脚本 |
| `setup_letools_learning.sh` | 配置 LeTools-Learning 工具链 | 无 | 见脚本 |

### `install_sdk.sh` 的校验链

1. 读版本锁定清单（pin 文件）。缺失 → `exit 1`。
2. pin 里 `SDK_REPO_BRANCH` 与 `SDK_REPO_TAG` **必须同时设置**，只设一个 → `exit 1`。
3. 若 `sdk_config.sh` 同时提供 branch + tag，则覆盖官方配套版本；只提供一项则打 WARNING 忽略。
4. 远程校验 tag 存在、分支存在、**tag 属于该分支（是其祖先）**，任一不满足 → `exit 1`。
5. `git submodule update --init --recursive`，初始化后仍不可用 → `exit 1`。
6. SDK 工作区有未提交修改导致无法切换 tag → `exit 1`（不会强切）。
7. 安装依赖失败 → `exit 1`。

### 三个 `run_*.sh` 的实际状态

这三个脚本只是**薄包装**，内容形如：

```bash
#!/bin/bash
cd "$(dirname "$0")/.."
if [ -f "/opt/ros/noetic/setup.bash" ]; then source /opt/ros/noetic/setup.bash; fi
python3 apps/arm_trajectory/main.py
```

`run_smt_tray.sh` 更短，直接 `python apps/smt_tray/main.py`。

> **实测：`apps/arm_trajectory`、`apps/camera_demo`、`apps/smt_tray` 三个目录当前在工作区中不存在。** 这三个脚本是**历史残留**，直接运行会因找不到目标文件而失败。要做手臂轨迹 / 相机 / SMT 验证，请走 [`06-apps-测试与示例应用.md`](./06-apps-测试与示例应用.md) 里列出的现行入口（`apps/test_upper_init/run_behavior_tree_json.py` 等）。

## 08.02 config 配置文件参考

`config/` 下入库 8 个文件，分「全局 YAML」与「ROS launch」两类。

| 文件 | 消费方 | 作用 |
|---|---|---|
| `app_config.yaml` | `core.common.app_config` → `HardwareFactory`、`shared_hardware` | **最主要的全局配置**：机器人类型、导航后端、各能力走哪条控制路径、相机开关 |
| `camera_config.yaml.template` | 复制为 `camera_config.yaml` 后由 `CameraAdapter` 读取（`apps/test_camera_adapter/test_camera_init.py` 默认读它） | 头部 / 手腕相机的分辨率、帧率、帧同步、启动超时 |
| `camera_config_carton.yaml` | `apps/test_camera_adapter/test_camera_carton.py` 默认读它 | 托盘链路专用变体：头部 640×480@30，左右腕相机按现场两台实机开启并写死序列号；其余字段与模板一致 |
| `log_config.yaml` | 统一日志 | 级别、格式、目录、轮转大小与备份数、控制台/文件开关 |
| `apriltag_config.yaml.template` | 复制为 `apriltag_config.yaml`，由 `perception_adapter.py` 传给 `apriltag_continuous.launch` | AprilTag 检测器参数与待检测标签合并在一个文件里 |
| `robot_config.yaml` | **当前无 Python 消费方** | 示例性配置（机器人名、URDF 路径、关节限位示例） |
| `apriltag_continuous.launch` | ROS launch | 连续 AprilTag 检测节点 |
| `camera_orbbec.launch` | ROS launch | Orbbec 相机驱动 |

`camera_config.yaml` 与 `apriltag_config.yaml` 是复制模板得到的实文件，被 `config/.gitignore` 忽略、不入库。换机器或换现场时重新复制再按现场改，仓库里查到的只有模板。

### `app_config.yaml`（逐字段）

```yaml
robot_type: leju_wheeled            # leju_wheeled / leju_bipedal
navigation_chassis_backend: jibot   # 导航底盘后端：jibot 等

backend:
  base_velocity: ros                # 底盘速度走哪条路径
  timed_commands: sdk               # TimedCmd 走哪条路径
  end_effector: ros                 # 末端执行器走哪条路径
  default: ros                      # 兜底

camera:
  use_orbbec: true
  enable_wrist_camera: true
```

- `robot_type` 是 `HardwareFactory.create_hardware()` 的必填项，缺失直接 `raise ConfigurationError`。
- `backend` 段决定每个能力族的默认实现通道；`default` 是未单独列出时的兜底。
- 该文件是 `shared_hardware.get_shared_hardware()` 读配置的入口（再被 `hardware_config.json` 的场景级覆盖叠加）。

### `log_config.yaml`（逐字段）

| 字段 | 默认 | 说明 |
|---|---|---|
| `logging.level` | `INFO` | `DEBUG` / `INFO` / `WARNING` / `ERROR` / `CRITICAL` |
| `logging.format` | `detailed` | `simple` / `detailed`（带 `[TRACE:xxx]`）/ `json` |
| `logging.log_dir` | `log` | 相对项目根或绝对路径 |
| `logging.max_bytes` | `10485760` | 单文件上限（10MB） |
| `logging.backup_count` | `5` | 轮转备份数 |
| `logging.console_output` | `true` | 输出到控制台 |
| `logging.file_output` | `true` | 输出到文件 |
| `logging.error_log_enabled` | `true` | ERROR 及以上单独记录 |

### `camera_config.yaml`（结构）

扁平结构，直接对应 `CameraAdapter` 接口：

| 段 | 字段（示例） | 说明 |
|---|---|---|
| 头部相机 | `enable_head`、`head_camera_type`（`orbbec_camera` / `realsense2_camera`） | 总开关与型号 |
| | `color_width`/`height`/`fps`（`1280`/`800`/`15`）、`depth_*` 同上 | 0 表示用驱动默认值 |
| | `head_enable_frame_sync`、`head_depth_registration`、`head_enable_point_cloud`、`head_enable_colored_point_cloud` | 驱动级帧同步 / 空间配准 / 点云 |
| | `driver_only` | `true` 时驱动只出图，Adapter 数据面参数不生效 |
| | `head_rgbd_sync`、`rgbd_sync_queue_size`（`5`）、`rgbd_sync_slop_sec`（`0.040`）、`rgbd_require_same_resolution` | **Adapter 级**时间戳配对（用原始 Header 时间戳近似同步，不改写时间戳） |
| | `camera_startup_timeout_sec`（`10.0`） | 完整 Adapter 模式等待首组 RGB/深度帧的超时；`driver_only` 模式不读 |
| 手腕相机 | `enable_wrist_camera`（总开关）、`has_left_wrist` / `has_right_wrist`（硬件是否装）、`left_wrist_camera_sn` / `right_wrist_camera_sn` | **某侧仅在总开关与该侧 `has_*` 同时为 true 时启动**；完全未安装时三项全设 false |

### `apriltag_config.yaml`（由模板复制）

检测器参数与待检测标签写在同一文件里。`perception_adapter.py` 把这个文件的绝对路径作为 `config_file` 传给 `apriltag_continuous.launch`，launch 用 `<rosparam command="load">` 在节点上顶层加载。下表默认值取自 `config/apriltag_config.yaml.template`：

| 字段 | 默认 | 说明 |
|---|---|---|
| `tag_family` | `'tag16h5'` | 可选 `tagStandard52h13` / `tagStandard41h12` / `tag36h11` / `tag25h9` / `tag16h5` / `tagCustom48h12` / `tagCircle21h7` / `tagCircle49h12` |
| `tag_threads` | `2` | |
| `tag_decimate` | `1.0` | 降采样 |
| `tag_blur` | `0.0` | |
| `tag_refine_edges` | `1` | |
| `tag_debug` | `0` | |
| `max_hamming_dist` | `0` | 注释说明默认建议 2；≥3 内存占用大 |
| `publish_tf` | `false` | |
| `transport_hint` | `"raw"` | `image_transport` 传输方式 |

模板里的标签段：

```yaml
standalone_tags:
  [
    {id: 1, size: 0.06, name: 'tag_1'},
    {id: 2, size: 0.06, name: 'tag_2'},
    {id: 3, size: 0.06, name: 'tag_1'},
    {id: 4, size: 0.06, name: 'tag_2'},
  ]
tag_bundles:
  []
```

两个必须记住的点：

1. **尺寸单位是米，`size` 指黑框外沿边长**（不是含白边的打印纸尺寸）。`apriltag_ros` 拿 `size` 反算 tag 到相机的距离：写成 `0.09` 而实物是 `0.18`，距离就差一倍，而下游**不会有任何报错** —— `T_pallet_tag` 照样是个合法刚体变换，只是托盘位姿整体偏了一截。上机前拿卡尺量黑框外沿。
2. **`NodePalletPose.tag_ids` 必须是本列表的子集**，否则那个 id 永远算不出托盘位姿。

## 08.03 场景定义文件格式

场景目录位置：`orchestration/scenarios/<场景名>/`。当前工作区共 **18** 个场景目录。

| 文件 | 定位 | 必填 |
|---|---|---|
| `py_tree.json` | **流程**：主行为树 | 是 |
| `py_tree_child.json` | **复用**：可被主树引用多次的子树库 | 有子树时必填（内容可为 `{}`） |
| `board.json` | **数据**：黑板运行时变量初值 | 建议 |
| `hardware_config.json` | **硬件裁剪**：场景级硬件工厂配置覆盖 | 可选 |
| `README.md` | 场景说明 | 建议 |

### 四类文件的差异

| 文件 | 管什么 | 改了会怎样 |
|---|---|---|
| `py_tree.json` | 步骤顺序、分支、并发、装饰器 | 改任务流程 |
| `py_tree_child.json` | 可复用子流程 | 影响所有引用它的主树 |
| `board.json` | Tag ID、箱子尺寸、虚拟标签开关等**数据** | 不动流程即可换参数 |
| `hardware_config.json` | 启用哪些 SDK 管理器、是否跳过力控 publisher 等 | 影响本场景的硬件初始化裁剪 |

### `py_tree.json`

顶层两个字段：`tree`（根节点定义）与 `interface`（对外可配置参数声明：`inputs` / `outputs` / `custom` / `process`）。

节点字段：`name` / `label` / `params` / `childs` / `childBoard`。

```json
{
  "tree": {
    "name": "Sequence",
    "label": "studio_smoke_seq",
    "params": { "memory": { "value": "True", "source": "CUSTOM", "data_type": "string" } },
    "childs": [
      { "name": "WaitForEnter", "label": "wait_enter",
        "params": { "message": { "value": "按 Enter 开始", "source": "CUSTOM", "data_type": "string" } },
        "childs": [], "childBoard": [] },
      { "name": "ChassisShortMove", "label": "chassis_short",
        "params": {
          "vx": { "value": "0.3", "source": "CUSTOM", "data_type": "float" },
          "vy": { "value": "0.0", "source": "CUSTOM", "data_type": "float" },
          "vyaw": { "value": "0.0", "source": "CUSTOM", "data_type": "float" },
          "duration_sec": { "value": "3.0", "source": "CUSTOM", "data_type": "float" }
        },
        "childs": [], "childBoard": [] }
    ],
    "childBoard": []
  },
  "interface": { "inputs": [], "outputs": [], "custom": [], "process": [] }
}
```

`name` 的四种含义：

```text
"Sequence" / "Selector" / "Parallel"   → 复合节点
"Async"                                 → 装饰器（必须有 childs）
"look_for_tag.json"                     → 引用子树（key 必须存在于 py_tree_child.json）
"CalcLegMove"                           → 叶子节点（映射到 orchestration/nodes/ 的类）
```

参数三元组 `value` / `source` / `data_type`、`${宏}` 优先级、`memory` / `policy` 等语义的完整说明见 [`05-orchestration-行为树编排.md`](./05-orchestration-行为树编排.md) 的 `05.03`。

### `py_tree_child.json`

顶层是 `文件名 -> 子树定义` 的 KeyValue 字典：

```json
{
  "look_for_tag.json": { "tree": { "name": "Parallel", "label": "look_tag", "params": {}, "childs": [] } },
  "walk_to_tag.json":  { "tree": { "name": "Sequence", "label": "walk_tag", "params": {}, "childs": [] } }
}
```

主树通过 `"name": "look_for_tag.json"` 引用。工厂加载时会**深拷贝**每个子树实例，保证多次引用之间状态隔离。参考：`studio_smoke_v1/py_tree_child.json` 内容就是 `{}`（该场景无子树）。

### `board.json`

推荐扁平 Dict：

```json
{ "pick_tag_id": 4, "use_virtual_tag": true, "box_length": 0.4 }
```

### `hardware_config.json`

在真机路径下、创建 `IHardware` 之前 merge 进硬件工厂配置：

```json
{ "skip_force_publishers": true, "sdk_managers_whitelist": ["timed", "arm", "low"] }
```

### 场景清单与运行档位

| 场景 | 档位线索 |
|---|---|
| `studio_smoke_v1` | 纯 SDK 冒烟，干跑 / 仿真 / 真机均可 |
| `refactored_sdk_atomic_v1`、`refactored_sdk_arm_v1` | 纯 SDK，演示子树引用、`Parallel` + `Async` |
| `refactored_sdk_single_tag_pick_v0` | 单 Tag 取放；真机下 30s 未识别到 tag 返回 FAILURE（仿真用 `board_sim.json` 注入虚拟 Tag） |
| `wheel_arm_single_tag_pick_v1` | MuJoCo 端到端（397 帧双臂轨迹） |
| `jibot_nav_v1` / `jibot_nav_v1_sim` | 含 `*JibotMove`，**仿真环境无 JiBot 服务，必须真机**（`_sim` 版为对标副本） |
| `grasp_mtbf` | 地图导航 + Tag 识别 + 双臂搬箱，可配置轮数；真机需导航服务与相机 |
| `dismantle_box*`、`pallet_servo_real_v1` | 产线场景，需真机与对应现场设备 |

判定场景属于哪一档要**按节点类名扫**（不要按文件名，也不要按目录名）：

```bash
grep -rho '"name"[[:space:]]*:[[:space:]]*"[^"]*"' \
  orchestration/scenarios/<场景>/*.json | sort -u
```

- 出现 `*JibotMove` → 真机 + JiBot；
- 出现 `*Percep` / `*Tag*` / `Apriltag*` / `Inference*` → 需真实相机或外部视觉服务；
- 力控 / 真空 / 爪类 → 需真实末端；
- 只有 `*SdkMove` → 仿真 / 真机均可；
- 任意组合 → 均可干跑。

反例：`dismantle_box_demo_action` 的子树名为 `demo_jibot_nav.json`，但里面全是纯 SDK 节点，实际不依赖 JiBot。

> 注意：`pallet_servo_real_v1` 的 `py_tree_child.json` 是 **0 字节**，读 JSON 时会直接报错。

## 08.04 tasks 任务配置

`orchestration/tasks/` 下三个 `task.yaml`。

| 目录 | 内容要点 |
|---|---|
| `arm_test/task.yaml` | `name: arm_control_test`；含 `parameters`（`tag_id`、`fake_tag_pos`、`fake_tag_euler`、`control_type: joint`、`total_time`）与 `tree`（Sequence：`SetFakeTag` → `TagToArmGoal` → `MoveArm`） |
| `arm_trajectory/task.yaml` | `name: arm_trajectory_task`；`tree.children` 里是 `initialize_hardware` + `execute_arm_trajectory`，后者带 `joint_names`（14 个）、`time_points`（`0.0/4.0/8.0/12.0`）与 `joint_angles_list` |
| `smt_tray/task.yaml` | SMT 托盘任务配置 |

### 这三份配置的实际状态

`TaskParser`（`orchestration.parser.task_parser`）是解析它们的组件，但**唯一引用它的地方是 `orchestration/engine/behavior_tree_engine.py`** —— 而 `behavior_tree_engine.py` 本身已被标记为**遗留**（"早期顺序执行引擎，不依赖 py_trees，已被 `BehaviorTreeFactory` + `BehaviorTreeController` 取代"）。

结论：

- **`tasks/*.yaml` 是历史格式**，现行主流程是 `scenarios/<场景>/{py_tree.json, board.json}`；
- 三份 YAML 里引用的节点名（`SetFakeTag`、`TagToArmGoal`、`MoveArm`、`initialize_hardware`）在当前 `orchestration/nodes/` 中**没有对应的公共节点**；
- 新任务不要照这个格式写。**新建场景请按 `08.03` 的目录结构走。**
