# 09 控制路径与选型

> 同一个「让手臂到某个位姿」，在 LeTools 里有**三条完全不同的路**可以走。本篇讲清楚三条路各自是什么、什么时候用哪条，以及它们和 `10-Skill→Node→场景 层级关系与选型建议.md` 的分工。

**分工：`09` 讲「选哪条路径」，`10` 讲「选哪个层级」。选型时先定层级，再定路径。**

## 09.01 三条路径总览

| 路径 | 方法后缀 | 实现位置 | 是否有反馈 | 控制频率 |
|---|---|---|---|---|
| 标准接口 | 无后缀 | Mixin 直接发 ROS 话题 / 服务 | 阻塞等待完成 | 单次调用 |
| SDK 直调 | `_sdk` | Mixin → `*SDKManager` → `robot_sdk.control.*` | 不阻塞，需自行循环 | 约 100Hz 由上层维持 |
| TimedCmd | `_timed` | Mixin → `TimedCmdManager` → 服务端 Ruckig 规划 | 按 `desire_time` 定时 | 单次下发，服务端按时间插值 |

三者的分界线是**谁负责「时间」**：

- 标准接口：**适配器**帮你等（内部订阅 `reach_time` 并阻塞）。
- SDK 直调：**你的循环**负责，适配器只发一拍。
- TimedCmd：**服务端的 Ruckig 规划器**负责，你只给目标位姿和期望耗时。

## 09.02 三条路径对照表

| 路径 | 调用形式 | 适用场景 | 优点 | 缺点 |
|---|---|---|---|---|
| 标准接口 | `hw.send_ee_pose(side, pose, frame)` | 常规控制 | 接口稳定、跨平台 | 功能有限 |
| SDK 直调 | `hw.send_ee_pose_sdk(left_pose, right_pose, frame)` | 需要更精细控制 | 能力强 | 与 SDK 版本耦合 |
| TimedCmd | `hw.send_arm_ee_world_timed(left_pose, right_pose, desire_time)` | 时序敏感动作 | 可精确控时 | 用法复杂 |

`send_ee_pose_sdk` 的 `left_pose`、`right_pose` 应传 `Pose6D` 或 `None`，不能传六元素列表；两者不能同时为 `None`。`frame` 使用字符串 `'world'` 或 `'base_link'`。`Pose6D` 的位置单位为米、姿态单位为弧度；TimedCmd 示例中的列表格式与此接口不同。

逐行说明：

**标准接口**（`send_ee_pose` / `send_both_ee_poses` / `send_base_velocity` / `send_torso_pose` / `control_end_effector` …）

- 走 ROS 话题或服务，**自动阻塞等待运动完成**（`send_ee_pose` 首次调用还会自动等 1.0s 建立 Publisher 连接，`send_torso_pose` 订阅 `/lb_torso_pose_reach_time` 拿到达时间后阻塞）。
- 「功能有限」具体指：粒度粗（一次一个目标位姿）、没有显式的时长参数、无法在同一拍里协调多个规划器。
- 单臂控制时另一臂会被**自动填安全默认值**（`x=0.1, y=±0.3, z=0.7`）。

**SDK 直调**（`send_ee_pose_sdk` / `send_arm_joint_positions_sdk` / `send_arm_ee_traj_sdk` / `send_base_velocity_sdk` / `control_head_sdk` …）

- **不阻塞**，只下发单次指令；要连续运动必须由上层自己维持循环（典型约 100Hz）。
- 「能力强」具体指：可以直接给关节角而不是笛卡尔目标、可以给多关键点轨迹（`send_arm_ee_traj_sdk` 带 `total_time` 自动插值）、可以只驱动单臂而不动另一臂。
- 「与 SDK 版本耦合」是真实代价：这些方法最终落到 `robot_sdk.control.*`，SDK 换版本时行为可能变。因此才有 `adapters/.../source_sdk_compat/` 兼容层。

**TimedCmd**（`send_arm_ee_world_timed` / `send_arm_ee_local_timed` / `send_torso_pose_timed` / `send_leg_joint_timed` / `send_base_pose_timed` …）

- 必须给 `desire_time`（秒），服务端 Ruckig 规划器在指定时间内完成运动，**这就是它能「精确控时」的原因**。
- 「用法复杂」具体指：
  - 要理解 **`planner_index` 0–9**（底盘 x/y/yaw、躯干 4 维、下肢 4 关节、左右臂世界系 6 维、左右臂本体系 6 维、左右臂上肢 7 关节），并发时要显式给 `send_timed_multi_commands` 每项的 `planner_index` / `desire_time` / `cmd_vec`；
  - 要理解 `is_sync` / `set_ruckig_planner_params` 的速度、加速度、急动度限值；
  - 还有离线轨迹模式（`set_offline_trajectory` + `enable_offline_trajectory`），首帧 `desire_time` 必须为 0 且时间严格递增。

### 三条路径都覆盖的常见能力

| 能力 | 标准 | SDK | TimedCmd |
|---|---|---|---|
| 末端位姿 | `send_ee_pose` / `send_both_ee_poses` | `send_ee_pose_sdk` | `send_arm_ee_world_timed` / `send_arm_ee_local_timed` |
| 手臂关节 | `send_arm_joint_trajectory` / `send_arm_ee_joint_space` / `publish_arm_joint_setpoint` | `send_arm_joint_positions_sdk` / `send_arm_joint_traj_sdk` | `send_arm_joint_timed` |
| 头部 | `control_head` | `control_head_sdk` | — |
| 躯干 | `send_torso_pose` | `send_torso_pose_sdk` / `send_torso_6dof_sdk` | `send_torso_pose_timed` |
| 下肢 | `send_leg_joint_command` | `send_leg_joint_sdk` | `send_leg_joint_timed` |
| 底盘 | `send_base_velocity` / `send_base_pose` | `send_base_velocity_sdk` / `send_base_position_*_sdk` | `send_base_pose_timed` / `send_base_velocity_timed` |
| 末端执行器 | `control_end_effector`（走 ROS，无后缀变体） | — | — |

方法签名与参数含义见 [`03-adapters-硬件适配层.md`](./03-adapters-硬件适配层.md)。

`publish_arm_joint_setpoint` 虽然也是标准接口（无后缀），却不阻塞：它收 14 个关节位置（左 7 右 7，单位度，无 `time_sec`），只把这一帧组进 `JointState` 发到 `/kuavo_arm_traj` 就返回，不 sleep、不等待到位。返回的 `Result.ok` 只说明发布调用完成，不表示控制器收到，也不表示关节到位。

它适用于 IK 逐帧设定点发布这类需要按固定帧率连续下发的场合；预备姿态与最终关节还原这类「下发并等到位」的步骤，仍用阻塞的 `send_arm_joint_trajectory`。两者可以出现在同一条技能链里，读代码时按调用点分别判断，不要因为其中一处非阻塞就认为整条链非阻塞。

## 09.03 决策树

```text
要做的是什么？
│
├─ 只是一次性发个指令，等它到位？ → 标准接口（无后缀）
│   例：hw.send_ee_pose(ArmSide.LEFT, pose)   ← 适配器内部等到达
│
├─ 需要 SDK 独有的能力？
│   （关节角直接下发 / 只驱动单臂 / 多关键点轨迹 / 自建控制频率）
│   → SDK 直调（_sdk）
│   例：hw.send_ee_pose_sdk(left_pose=..., right_pose=None)
│
└─ 对完成时刻有要求？
    （必须 3 秒内到位 / 腿臂躯干底盘要在同一时间窗内协同完成）
    → TimedCmd（_timed）
    例：hw.send_arm_ee_world_timed(left_pose, right_pose, desire_time=3.0)
```

更短的口诀：

| 需求 | 选它 |
|---|---|
| 要跨平台复用，不关心底层实现 | **标准接口** |
| 需要 SDK 专有能力 | **SDK 直调** |
| 要求精确时序 | **TimedCmd** |

**混合使用是常态。** 同一个场景里不同节点走不同路径完全正常 —— 例如 `refactored_sdk_atomic_v1` 里头部用 SDK，末端姿态用 TimedCmd。真正要避免的是「同一条控制链路在同一时段被两条路径同时驱动」。

## 09.04 与 MPC 模式的关系

标题里的 `MPC` 是 `MPCControlMode` 枚举（`core.domain.enums`）：

```python
class MPCControlMode(Enum):
    NO_CONTROL = 0
    ARM_ONLY = 1
    BASE_ONLY = 2
    BASE_ARM = 3
    ARM_EE_ONLY = 4
```

> ⚠ **模式值不决定当前固件的控制分支。** `set_mpc_mode(mode)` 会调用 ROS 服务，服务接收并回显模式值，但主循环中按该值选择分支的代码已被注释。`set_mpc_mode_sdk(mode_name)` 仍会执行外部控制准备及 SDK 控制流设置；不要将整个调用视为空操作。`get_mpc_control_mode()` 读到的值不等于实际控制分支，也不能把它当成三条路径的开关。
>
> 该行为以当前仓库记录的固件为准；更换运控版本时需重新验证。枚举及接口说明见 [`02-core-接口与数据模型.md`](./02-core-接口与数据模型.md)。

真正生效的模式通道是**快速模式 / 手臂控制模式**这一组：

| 方法 | 作用 |
|---|---|
| `enable_quick_mode(enable)` | 手臂 / 下肢快速模式（绕过 MPC） |
| `set_arm_quick_mode(quick_mode:int)` | 手臂快速模式参数 |
| `set_arm_control_mode(control_mode:int)` | 手臂控制模式切换（`1`=重置到初始位置，`2`=外部控制器模式） |

`apps/` 的脚手架在后置复位后都会调 `set_arm_control_mode(2)`，注释写明原因：**避免上次 teardown 后控制模式不明导致指令被静默忽略**。这是三条路径共同的隐性前置。

三条路径与这几组模式的对应关系：

| 路径 | 典型前置 / 收尾 |
|---|---|
| 标准接口 | `arm_reset()` 内部会自动处理模式设置与恢复；`send_ee_pose` 需要末端跟踪焦点（`set_focus_ee`） |
| SDK 直调 | `send_arm_ee_traj_sdk` 等会自动做 MPC 管理（`move_eef_traj_auto`）；单发类需要自己保证控制模式正确 |
| TimedCmd | `prepare_arm_control` / `release_arm_control` 参数控制是否自动做前置 / 收尾（默认都 `True`） |

## 09.05 与层级的关系

```text
Skill（实现 ISkill）   ← 封装「一个动作」，不关心谁调它
   ↓
Node（继承 Behaviour） ← 封装「JSON 参数 + py_trees 生命周期」，薄封装
   ↓
场景（py_tree.json）   ← 决定「什么时候调哪个 Node」
```

**层级与路径是正交的两个维度**：

- **层级**决定「代码放在哪、由谁调度」—— 见 [`10-Skill→Node→场景 层级关系与选型建议.md`](./10-Skill→Node→场景%20层级关系与选型建议.md)。
- **路径**决定「这个动作最终怎么落到硬件上」—— 就是本篇。

所以正确的选型顺序是：

```text
1. 先定层级：这个能力要不要被行为树复用？
   ├─ 要 → 写成 Skill + Node（走 09 的新增三层流程）
   └─ 不要，只是一次性验证 → 直接写 apps/ 下的脚本调 hw.
2. 再定路径：这个动作是「常规」「需要 SDK 能力」还是「时序敏感」？
   └─ 按 09.03 的决策树三选一
3. 最后写代码：Skill 内部用 getattr(self.hardware, "<对应方法>", None) 取方法。
```

`refactored_sdk/` 目录名下**同时**存在 `_sdk` 技能（`arm_joint_traj_sdk.py`）、`_timed` 技能（`arm_ee_dual_timed.py`）和标准接口技能（`arm_ee_pose_jibot.py` 走 `send_ee_pose`）—— 目录名是「重构后的 SDK 直调架构」的历史叫法，**不代表里面只能用 SDK 路径**。

## 09.06 常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 用 `_sdk` 方法发一次就以为会动到目标 | 只动了一拍，机器人几乎不动 | 上层维持约 100Hz 循环，或改用标准接口 / `*_traj_sdk` |
| 用 `_timed` 但把 `desire_time` 设成 0 | 时序规划退化为瞬时目标，失去精确控时意义 | 按物理可行时间给 `desire_time` |
| 并发用 TimedCmd 但没有正确的 `planner_index` | 两条指令打到同一个规划器，互相覆盖 | 按规划器表分配 index（左臂世界系 4、右臂 5 …），或直接用 `send_timed_multi_commands` |
| 把 `MPCControlMode` 当三层路径的开关 | 设了不生效，指令被静默忽略 | 用 `enable_quick_mode` / `set_arm_control_mode` 这组接口 |
| 标准接口和 SDK 直调同时驱动同一条链路 | 目标互相覆盖 | 同一时段只让一条路径驱动一条链路 |
| 以为 `Parallel` 就等于硬件真并行 | 仍是单线程顺序 tick | `Parallel(policy="success_on_all")` + `Async` 装饰器 |

## 09.07 调用示例

### 三条路径做同一件事：把左臂末端移到 `(0.3, 0.25, 0.5)`

```python
from math import radians
from core.domain.pose import Pose6D
from core.domain.enums import ArmSide, FrameType

# ① 标准接口：适配器内部等到达
hw.send_ee_pose(
    side=ArmSide.LEFT,
    pose=Pose6D(x=0.3, y=0.25, z=0.5, yaw=0.0, pitch=-1.5708, roll=0.0),
    frame=FrameType.WORLD,
)

# ② SDK 直调：参数为 Pose6D（位置为米，姿态为弧度）；单次下发，需上层维持循环
hw.send_ee_pose_sdk(
    left_pose=Pose6D(x=0.3, y=0.25, z=0.5, yaw=0.0, pitch=radians(-90.0), roll=0.0),
    right_pose=None,
    frame='world',
)

# ③ TimedCmd：3 秒内到位（列表用度）
hw.send_arm_ee_world_timed(
    left_pose=[0.3, 0.25, 0.5, 0, -90, 0],
    right_pose=[0.3, -0.25, 0.5, 0, -90, 0],
    desire_time=3.0,
)
```

### 按决策树挑技能

```text
要做「双臂末端 3 秒内同时到位」         → skills/atomic/refactored_sdk/arm_ee_dual_timed.py（TimedCmd）
要做「14 关节多关键点轨迹，自己控节奏」 → .../arm_joint_traj_sdk.py（SDK）
要做「单臂末端一次到位，等它完成」      → .../arm_ee_pose_jibot.py（标准接口）
```

### 行为树里怎么体现

同一个 `Parallel` 下混用两条路径：

```json
{
  "name": "Parallel",
  "label": "leg_arm_sync",
  "params": { "policy": { "value": "success_on_all", "source": "CUSTOM", "data_type": "string" } },
  "childs": [
    { "name": "Async", "label": "async_leg",
      "params": { "tick_hz": { "value": "50.0", "source": "CUSTOM", "data_type": "float" } },
      "childs": [ { "name": "LegJointTimedMove", "label": "leg", "params": {}, "childs": [] } ] },
    { "name": "Async", "label": "async_arm",
      "params": { "tick_hz": { "value": "50.0", "source": "CUSTOM", "data_type": "float" } },
      "childs": [ { "name": "ArmJointTrajSdkMove", "label": "arm", "params": {}, "childs": [] } ] }
  ]
}
```

`Async` 只保证**编排层**不阻塞，**不保证底层硬件真能同时执行两条链路**。
