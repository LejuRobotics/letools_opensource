### 2.1 `ArmEeBurstTimedMove`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/arm_ee_burst_timed_move.py` |
| 类名 | `ArmEeBurstTimedMove` |
| label | 连发末端航点（TimedCmd） |
| 底层 | `ArmEEBurstTimedSkill` → `send_timed_single_command` |

**作用**

`ArmEeBurstTimedMove` 用于**单臂连续发送多个末端航点**。

它会循环调用 timed single command，让同一侧手臂依次经过多个目标点。


特点：

- 只控制单侧手臂。
- 支持多个航点连续执行。
- 每个航点都会独立下发一次 TimedCmd。
- 每段运动都有独立的 `desire_time`。
- 每段结束后可以通过 `settle_time` 额外等待。
- 可选开启静差检查。
- 躯干 / 底盘不参与。

末端航点格式：[x, y, z, yaw, pitch, roll]

单位：`x/y/z`：米，`yaw/pitch/roll`：度

适用于：

- 单臂多点调试。
- 验证一组末端轨迹点是否可达。
- 做简单的抓取前接近、下探、抬起等连续动作。
- 不需要双臂同步，只需要单侧手臂连续移动的场景。

**参数**

- "side": "left"

  - 控制哪一侧手臂：
  
    - `"left"`：左臂
    - `"right"`：右臂
- "frame": "world"

  - 目标航点所在坐标系：
  - `"world"`：世界系
  - `"local"`：本体 / 局部系
- "waypoints": [  [0.3, 0.25, 0.5, 0, -90, 0],  [0.4, 0.25, 0.5, 0, -90, 0],  [0.4, 0.25, 0.7, 0, -90, 0]  ]

  - 末端航点列表。每个航点格式：[x, y, z, yaw, pitch, roll]
  - 注意：
  
    - `waypoints` 不能为空。
    - `waypoints` 必须至少是二维数组：[  [x, y, z, yaw, pitch, roll],  [x, y, z, yaw, pitch, roll]  ]，不要写成单个点：[x, y, z, yaw, pitch, roll]
    - 可以传 JSON 数组，也可以传 JSON 字符串。
    - 如果解析失败或为空，节点会失败，并提示：arm_ee_burst_timed: missing or empty waypoints
- "desire_time": 3.0

  - 每一段航点运动的期望执行时间，单位秒。
  - 例如有 3 个航点：[ wp0,  wp1,  wp2 ]，那么每个航点都会以 `desire_time` 指定的时间执行一次。
- "settle_time": 1.0
- 每段运动完成后的额外等待时间，单位秒。

  - 用途：等机械臂稳定。等控制器收敛。给静差检查留出时间。避免连续下发过快导致控制器忙。
- "check_reach": false

  - 是否在每个航点执行后检查实际末端是否到达目标附近。
  
    - `true`：开启静差检查
    - `false`：不开启静差检查
    - 代码中 bool 解析支持：true / 1 / yes / on
- "reach_linear_tol": 0.01

  - 静差检查的位置容差，单位米。默认 `0.01`，表示位置误差小于 1cm 认为到达。
- "reach_angular_tol": 0.05

  - 静差检查的姿态容差，单位弧度。默认 `0.05 rad`，约等于 2.86°。

**行为树中如何使用**

示例一：左臂 world 系连续执行 3 个航点（JSON 配置见本节末尾）


示例二：右臂 local 系连续移动，并开启静差检查（JSON 配置见本节末尾）


示例三：放在 `Sequence` 中作为单臂调试流程（JSON 配置见本节末尾）

### 2.2 `ArmEeDualTimedMove`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/arm_ee_dual_timed_move.py` |
| 类名 | `ArmEeDualTimedMove` |
| label | 双臂单次末端位姿（TimedCmd/躯干不参与） |
| 底层 | `ArmEEDualTimedSkill` |

**作用**

`ArmEeDualTimedMove` 用于执行**双臂单次末端位姿 TimedCmd**。

它一次控制左臂和右臂各到一个目标点。


特点：

- 双臂同步执行。
- 默认躯干不参与末端解算。
- 默认执行前切换到手臂外部控制模式。
- 执行后可以释放外部控制。
- 不做手臂物理复位。
- 不复位躯干。

末端位姿格式：[x, y, z, yaw, pitch, roll]

- 单位：`x/y/z`：米，`yaw/pitch/roll`：度

适合用于：

- 双臂同时到达接近点
- 双臂同时下探
- 抓取 / 放置中的单阶段双臂移动
- 替代双侧分别调用 `ArmEeSingleTimedMove`

**参数**

- "frame": "world"

  - 坐标系：
  
    - `"world"`：世界系
    - `"local"`：本体系 / 局部系
- "left_pose": [0.5, 0.25, 0.7, 0, -90, 0]

  - 左臂单点末端位姿。
- "right_pose": [0.5, -0.25, 0.7, 0, -90, 0]

  - 右臂单点末端位姿。
  
    - "left_waypoints": [[...], [...]]
    - "right_waypoints": [[...], [...]]
    - 兼容 `ArmEeTimedCmdMove` 的 waypoints 模式。  
    如果提供 waypoints，则会根据 `waypoint_index` 选取其中一个点作为本次目标。
- "waypoint_index": 0

  - 使用 waypoints 中第几个点：
  
    - `0`：常用于上方接近点
    - `1`：常用于下探抓取点
- "desire_time": 2.0

  - 期望执行时间，单位秒。
- "focus_ee": false

  - 是否启用末端焦点。当前默认 `False`，含义是，躯干优先，躯干不被末端目标带动
- "focus_z": false

  - 是否启用 Z 轴焦点跟随。默认 `False`，表示禁用 Z 轴焦点跟随。
- "prepare_arm_control": true

  - 执行前是否切换到手臂外部控制模式：set_arm_control_mode(2)，默认 `True`。
- "release_arm_control": true

  - 执行完成后是否释放外部末端保持
- set_arm_control_mode(0)

  - 默认 `True`。

**行为树中如何使用**

方式一：直接使用 `left_pose` / `right_pose`。（JSON 配置见本节末尾）


方式二：使用 waypoints，并通过 `waypoint_index` 选择目标点。（JSON 配置见本节末尾）


方式三：使用 waypoints 的第二个点，比如下探抓取点。（JSON 配置见本节末尾）

### 2.3 `ArmEeLocalRelativeTimedMove`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/arm_ee_local_relative_timed_move.py` |
| 类名 | `ArmEeLocalRelativeTimedMove` |
| label | 双臂末端 local 相对补偿（TimedCmd） |
| 底层 | `ArmEELocalRelativeTimedSkill` → `send_arm_ee_local_timed` |

**作用**

`ArmEeLocalRelativeTimedMove` 用于执行**双臂末端 local / base_link 系相对补偿**。它不是直接给绝对目标点，而是基于当前双臂末端位姿做相对偏移。


适用于：

- 双臂末端微调
- 抓取前后局部补偿
- 已经到达目标附近后做小范围修正
- 不想重新规划整条轨迹，只想基于当前位姿偏移一点

注意：

- 该节点是**双臂同步补偿**。
- 参数只暴露 6 个核心参数。
- 其他参数如 `desire_time`、TF、topic、frame、release_after 等固定在 skill 内部，与测试脚本保持一致。
- 代码中实际还读取了 `timeout`，但 manifest 中未显式声明，默认值为 `30.0` 秒。

**参数**

- "offset_x": 0.05

  - local x 方向偏移，单位米。
  
    - 正值：向前
    - 负值：向后
- "offset_y": 0.0

  - local y 方向偏移，单位米。
  
    - 正值：向左
    - 负值：向右
- "offset_z": -0.05

  - local z 方向偏移，单位米。
  
    - 正值：向上
    - 负值：向下
- "fixed_yaw": 0.0

  - 目标 yaw，单位度。
- "fixed_pitch": -90.0

  - 目标 pitch，单位度。默认 `-90.0`，常用于末端朝下的抓取姿态。
- "fixed_roll": 0.0

  - 目标 roll，单位度。
- "timeout": 30.0

  - 超时时间，默认 30 秒。代码中会读取该参数，但 `define_manifest` 中没有展示。

**行为树中如何使用**

方式一：直接写固定参数。（JSON 配置见本节末尾）


方式二：从黑板读取参数。（JSON 配置见本节末尾）


常见流程示例：先移动到接近位，再做 local 下探补偿。（JSON 配置见本节末尾）

通过 TimedCmd 服务控制双臂末端位姿。

- 支持多关键点。
- 支持从黑板读取动态 waypoints。
- 坐标系可选 `world` 或 `local`。

格式：

[x, y, z, yaw, pitch, roll]

单位：

- 位置：米
- 姿态：度

**参数**

### 2.17 `CheckArmEeReachErrorMove`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/check_arm_ee_reach_error_move.py` |
| 类名 | `CheckArmEeReachErrorMove` |
| label | 手臂末端到位检查 |
| 底层 | `hardware.get_ee_pose_reach_error()`（服务 `/mobile_manipulator_ee_pose_reach_error`） |

**作用**

轮询硬件接口判断手臂末端是否**到位**，并把到位静差向量写进黑板供后续节点使用。

判定口径只有一条：**该服务的 `success` 即控制器的「末端运动已完成」判定**。节点不另设阈值——避免出现「控制器说到了、节点说没到」的矛盾；误差数值只作输出上报，不参与判定。

- 全部待检查侧到位 → 返回 `SUCCESS`，终端 feedback 里报一份误差向量，并写黑板。
- 超过 `timeout` 仍未到位 → 返回 `FAILURE`，feedback 里列出未到位的侧别。
- 静差向量维度不是 6 → 判 `FAILURE`。

### 3.11 `NodeChassisServoExec`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/node_chassis_servo_exec.py` |
| 类名 | `NodeChassisServoExec` |
| label | 底盘伺服执行 |
| 底层 | `ChassisServoExecSkill` → `base_move_relative_jibot`；`chassis_direct` 通道走 `start_cmd_vel_stream` / `update_cmd_vel_setpoint` / `stop_cmd_vel_stream` / `get_motion_gate` |

**作用**

读黑板上的 `ServoCommand` → 下发给底盘执行 → 轮询等这一步走完 → 写回 `task_id` 与节拍门禁 `servo_exec_idle`。速度模式下带观测看门狗：超过 `obs_timeout_s` 没收到新观测即发零速，避免视觉断线后盲跑。

速度模式有两条执行通道（`command_channel`）：

- `humanoid`（默认）：每 tick 由技能单发一帧 `/cmd_vel`，与引入该参数前逐字一致。
- `chassis_direct`：`initialise()` 起一条后台速度流（默认 100 Hz），每 tick 只更新目标速度，由适配器线程按频率重发，不再逐帧单发。`cmd_vel_topic` / `publish_rate_hz` 只在这条通道生效；位置模式不碰流。

**参数**

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `command_key` | `string` | `latest_servo_command` | 读 `ServoCommand` 的黑板键名 |
| `task_id_key` | `string` | `current_task_id` | 写 `task_id` 的黑板键名 |
| `idle_key` | `string` | `servo_exec_idle` | 写节拍门禁的黑板键名（`True`=底盘空闲） |
| `obs_key` | `string` | `latest_servo_error` | 读观测版本号的黑板键名（速度模式看门狗用） |
| `obs_timeout_s` | `float` | `0.5` | 观测看门狗(s)：超时未更新即发零速 |
| `velocity_timeout_s` | `float` | `10.0` | 速度模式连续运行上限(s)，超时停车退出（失控保险丝） |
| `position_threshold` | `float` | `0.08` | 位置到达阈值(m)：剩余距离小于它判到达 |
| `angle_threshold` | `float` | `0.1` | 角度到达阈值(rad) |
| `linear_velocity` | `float` | `0.15` | 线速度(m/s) |
| `angular_velocity` | `float` | `0.25` | 角速度(rad/s) |
| `allow_rotation` | `bool` | `True` | 是否允许旋转 |
| `wait_arrival` | `bool` | `True` | 是否轮询 `check_arrived` 等这一步走完 |
| `arrival_timeout` | `float` | `20.0` | 单步等到达上限(s)，超时放行 |
| `arrival_poll_interval` | `float` | `0.2` | 轮询 `check_arrived` 的最小间隔(s) |
| `command_channel` | `string` | `humanoid` | 速度模式通道：`humanoid` / `chassis_direct`；位置模式不看此字段 |
| `cmd_vel_topic` | `string` | `/move_base/base_cmd_vel` | 仅 `command_channel='chassis_direct'` 生效：底盘原生速度话题 |
| `publish_rate_hz` | `float` | `100.0` | 仅 `chassis_direct` 生效：后台速度流频率(Hz) |

**`chassis_direct` 的运动门控**

门控只在 `chassis_direct` 下评估，每 tick 读一次 `get_motion_gate()`：

- 从未收到 `BaseCmdVelStatus`（`effective_age_s is None`）→ 视为有效，不阻断。该话题真机可能没有发布者。
- 收到消息则按 `cmd_vel_effective` 判：连续 5 帧为 `false` 才判失败（第 4 帧仍放行）；中途变回 `true` 则计数清零。
- 判失败时先停车再返回 `FAILURE`，并闩锁：后续 tick 直接返回 `FAILURE`、不发任何非零速度，需重新 `initialise()` 才恢复。
- `effective_age_s` 只写日志，不参与阻断；`RobotStatus.mode` 不参与门控。

**`chassis_direct` 的停车时序**

任何退出路径（收敛、超限、看门狗、门控失败、`terminate()`）都走同一个顺序：目标速度置零并保持 0.2 s → `stop_cmd_vel_stream()` → 返回。顺序不可调换，先停流会让底盘停在最后一条非零速度上。

`enable_vel_control` 的还原不在本节点，由树里的 `NodeEnableVelControl` 负责：先停流、后还权，交还控制权时不允许还有本节点的非零速度在流里。`terminate()` 只在 `chassis_direct` 下无条件停流（幂等），`humanoid` 下维持「本节点发过速度指令才发零速」的原行为。

### 3.16 `NodeMotionGate`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/node_motion_gate.py` |
| 类名 | `NodeMotionGate` |
| label | 运动闸门（人工确认） |
| 底层 | 无 Skill；只读黑板与终端 stdin |

**作用**

接在视觉出数与底盘运动之间的人工检查点：等黑板上出现有效观测，把三个误差量打到终端，然后等操作员按回车。回车之前节点返回 `RUNNING`，树不往下走。

**每个 tick 都读一次黑板**，不是"先死等固定时长再检查"。等待分两个窗口并行计时：激活窗口（`settle_after_slot_s`，要盖住上游 `call` 档位服务的整段流程）和出数窗口（`valid_timeout_s`）。有效观测任何时刻出现都立刻进入确认环节；两个窗口都用尽仍没有才返回 `FAILURE`。2026-10-21 真机踩过：固定等待到期的那一刻上游正好发出 `call`，闸门早一步判了超时。

读 stdin 放在后台线程里，`update()` 立刻返回。这是本节点的关键：行为树主循环是 50 Hz，视觉节点靠 `update()` 持续发数、发叠加图、发心跳；如果在 `update()` 里同步调 `input()`，主循环一停，操作员看到的是一屏冻结的旧数据，等于在确认一个过期的画面。

`stdin` 不是终端（`nohup`、`systemd`、重定向 stdin）时，第一 tick 就返回 `FAILURE`，而不是挂在那里等一个永远不会来的回车。现场必须用终端直接跑。

**参数**

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `obs_key` | `string` | `latest_servo_error` | 读观测量的黑板键，须与上游写入的键一致 |
| `settle_after_slot_s` | `float` | `22.0` | 激活窗口：从闸门第一 tick 起，等有效观测的第一段预算（要盖住上游 `call` 档位服务的整段流程）；环境变量 `VISION_GATE_SETTLE_S` 优先 |
| `valid_timeout_s` | `float` | `8.0` | 出数窗口：激活窗口用尽后，再给这么多秒等有效观测，仍没有则返回 `FAILURE`；环境变量 `VISION_GATE_VALID_TIMEOUT_S` 优先 |
| `confirm` | `bool` | `True` | 是否真的等回车。`False`=观测有效就放行，供离线用例与无人值守使用 |
| `confirm_message` | `string` | 见下 | 按回车前的提示语 |

`confirm_message` 默认值是「确认三个误差量合理后按 Enter 启动底盘伺服（Ctrl+C 中止）」。

**行为树中如何使用**

```json
{
  "name": "NodeMotionGate",
  "label": "motion_gate",
  "params": {
    "obs_key": {"value": "latest_servo_error", "source": "CUSTOM", "data_type": "string"},
    "settle_after_slot_s": {"value": 22.0, "source": "CUSTOM", "data_type": "float"},
    "valid_timeout_s": {"value": 8.0, "source": "CUSTOM", "data_type": "float"},
    "confirm": {"value": true, "source": "CUSTOM", "data_type": "bool"}
  },
  "childs": []
}
```

> 闸门要和后面的运动节点放进同一个 `Sequence`（建议 `memory=True`），不能并列挂在 `success_on_one` 的 `Parallel` 下：`Parallel` 只决定何时算成功，闸门返回 `RUNNING` 时同级节点照样会被 tick。

> `NodeServoErrorFromTopic` 只把有效帧写进黑板，所以「黑板上有观测」基本等价于 `valid=true`。节点仍会判一次 `valid`，是为了兼容直接写 `ServoError`（没有该字段，按 `True` 处理）的旧场景。

| label | 计算并控制躯干/腿 |
| 底层 | `send_torso_pose_timed` |

**作用**

`CalcLegMove` 用于计算并控制机器人躯干 / 腿部姿态。它会根据不同模式生成躯干目标位姿，并调用硬件接口下发：hw.send_torso_pose_timed(...)

执行前会调用 `hw.set_mpc_mode(MPCControlMode.ARM_ONLY)`；当前固件不按此模式值选择控制分支，实际动作由后续控制指令决定。

**参数**

- "leg_mode": "target"

  - 腿部控制模式。支持：target、leg
  
    - target:  根据 latest_tag\_<tag_id>、stand_in_tag_pos、stand_in_tag_euler 计算目标躯干位姿
    - leg:  不依赖 tag，直接把 offset_x / offset_y / offset_z / offset_yaw / offset_pitch  当作 base 系躯干目标
- "tag_id": 4

  - 当 `leg_mode="target"` 时，读取黑板：latest_tag\_<tag_id>，例如：latest_tag_4
- "stand_in_tag_pos": "[0.0, 0.1, 0.2]"

  - 站立 / 躯干目标在 tag 坐标系下的位置。仅 `leg_mode="target"` 时使用。
- "stand_in_tag_euler": "[-1.57, 1.57, 0.0]"

  - 站立 / 躯干目标在 tag 坐标系下的姿态，单位弧度。仅 `leg_mode="target"` 时使用。
- "offset_x": 0.0

  - X 方向偏移，单位米。在 `leg_mode="target"` 中，会叠加到 `stand_in_tag_pos[0]`。在 `leg_mode="leg"` 中，会作为 base 系目标 x。
- "offset_y": 0.0

  - Y 方向偏移，单位米。在 `leg_mode="target"` 中，会叠加到 `stand_in_tag_pos[1]`。在 `leg_mode="leg"` 中，会作为 base 系目标 y。
- "offset_z": 0.25

  - Z 方向偏移，单位米。常用于控制躯干高度：较小值：蹲下；较大值：抬高 / 站起
- "offset_yaw": 0.0

  - 偏航角偏移，单位度。在 `leg_mode="leg"` 中会转换为弧度作为目标 yaw。
- "offset_pitch": 0.0

  - 俯仰角偏移，单位度。正值表示前倾。
- "control_base": false

  - 保留参数，当前代码中暂不实际控制底盘。
- "total_time": 3.0

  - 躯干 TimedCmd 执行时间，单位秒（服务端 Ruckig 规划时长）。

### 7.3 `Async`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/async_decorator.py` |
| 类名 | `Async` |
| label | 异步执行(Async) |

**作用**

`Async` 是一个异步执行装饰器节点，用来把它的子节点放到后台线程中执行。

主要用途：

- 避免阻塞型节点卡住主行为树 tick。
- 在 `Parallel` 组合节点中，让多个动作从编排层面上“同时启动”。
- 适合包装 `sleep`、轨迹执行、等待类节点等可能阻塞主线程的行为。

**注意**：

- `Async` 只是让行为树层面并行，并不保证底层硬件真的能同时执行多条控制链路。
- 如果多个异步节点同时读写黑板或调用 ROS / SDK，需要自行确认线程安全。

**参数**

参数：`"tick_hz": 50.0`

含义：

- `tick_hz`：后台线程 tick 子节点的频率，默认 `50.0 Hz`。
- 如果设置过低，子节点状态更新不够及时。
- 如果设置过高，会增加线程调度负担。

**行为树中如何使用**

`Async` 是装饰器节点，必须有一个子节点。

示例：异步执行手臂复位。（JSON 配置见本节末尾）

### 7.6 `MultiTimedCommandMove`

| 项 | 值 |
|---|---|
| 文件 | `orchestration/nodes/multi_timed_command_move.py` |
| 类名 | `MultiTimedCommandMove` |
| label | 多规划器组合控制（TimedCmd） |
| 底层 | `MultiTimedCommandSkill` → `hardware.send_timed_multi_commands()` |

**作用**

把配置中的多个 planner 目标通过一次 TimedCmd 请求下发。组合不写死，可使用
`2/8/9`、`3/8/9` 或 `3/6/7` 等组合；同一请求避免了多个线程分别调用
TimedCmd 时对控制器主循环的竞争。

**参数**

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `commands` | `json` | `[]` | 指令数组，每项包含 `planner_index` 和 `cmd_vec`，可选 `desire_time` |
| `desire_time` | `float` | `3.0` | 单条命令未指定执行时间时采用的默认值（秒） |
| `is_sync` | `bool` | `true` | 是否让所有 planner 同时完成 |
| `focus_ee` | `bool` | `false` | 专注末端解算时躯干可能随动；false 尽可能不动躯干，精度可能降低；focus_z 内部跟随该值 |
| `prepare_arm_control` | `bool` | `true` | 含 planner 2–9 时，发令前调用 set_arm_control_mode(2)，失败不下发；false 由外部保证模式 |
| `settle_time` | `float` | `0.5` | 运动完成后的额外等待（秒） |

模式准备在原子技能执行时完成，不在构树或 dry-run 中操作硬件。只切到模式 2（外部控制），不经模式 1（物理复位），结束后不自动切回模式 0（保持当前位置）。纯底盘 planner 0/1 不触发手臂模式切换。`focus_ee/focus_z` 与手臂控制模式不同，设置焦点不能代替模式准备。此处检查切换接口的返回结果，不额外读取模式状态；直接调用 Adapter 的 TimedCmd 接口不会获得技能层的前置准备。

**行为树中如何使用**

```json
{
  "name": "MultiTimedCommandMove",
  "label": "lower_body_and_arms",
  "params": {
    "commands": {
      "value": [
        {"planner_index": 3, "cmd_vec": [29.0, -41.11, 32.21, 20.0]},
        {"planner_index": 8, "cmd_vec": [0, 0, 0, 0, 0, 0, 0]},
        {"planner_index": 9, "cmd_vec": [0, 0, 0, 0, 0, 0, 0]}
      ],
      "source": "CUSTOM",
      "data_type": "json"
    },
    "desire_time": {"value": 3.0, "source": "CUSTOM", "data_type": "float"}
  },
  "childs": []
}
```
